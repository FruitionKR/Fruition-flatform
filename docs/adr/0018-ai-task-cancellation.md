# AI 작업 취소와 저장한 변경의 복구

## 맥락

AI 작업은 모델 호출 사이에 문서·폴더·Wiki·Skill을 여러 번 저장한다. 실행만 멈추면
사용자가 취소한 작업의 일부가 남는다. core DB, AI DB, MinIO에 걸친 실행을 하나의
장시간 DB 트랜잭션으로 묶을 수 없으므로, 취소 시 이미 커밋한 변경도 복구해야 한다.

## 결정

Python이 실행 기록으로 역작업을 정하고, backend는 업무 데이터의 원자적 복구를 수행한다.
Agent 도구는 변경 전 snapshot과 원래 승인에 연결된 역작업 인자·멱등키를 저장한다.
일반 AI 작업은 각 DB의 trigger로 변경 전후 값을 같은 트랜잭션에 기록한다.
MinIO는 쓰기 전에 원본과 예정 결과를 영속 기록한다.

취소 상태를 먼저 저장해 후속 쓰기를 막고, 실행 중인 handler가 끝난 뒤 자식부터 역순 복구한다.
Agent 턴과 복구는 같은 PostgreSQL 실행 잠금을 사용한다. worker 연결이 종료되면 잠금이
해제되므로 남은 `executing` 기록이 복구를 막지 않는다. 복구는 모델 설정이나 호출 없이 실행한다.
현재 값과 후속 참조를 확인하며 다른 작업의 변경을 덮어쓰지 않는다. 전체 복구를 확인해야
`cancelled`가 된다. 충돌이나 불명확한 실행 결과는 `rollback_failed`로 남겨 재시도한다.
본문 복구는 새 revision으로 저장해 늦은 이벤트가 원문을 다시 덮어쓰지 못하게 한다.

## 대안과 기각 사유

- 실행 중단만 처리: 이미 저장한 변경도 복구한다는 제품 합의를 충족하지 못한다.
- 모델에 반대 작업 요청: 원래 값·승인 범위·멱등성을 보장하지 못한다.
- 서비스 전체를 단일 트랜잭션으로 잠금: 모델·HTTP·객체 저장소의 장시간 실행과 장애를 감당하기 어렵다.

## 결과

사용자에게 보이는 내용·이름·부모·순서는 복원하고 버전·감사·멱등 기록은 유지한다.
구버전 작업에는 snapshot이 없으므로 배포 전 실행과 큐를 비워야 한다.
공개 제품 경로를 공통 취소에 등록하며 운영용 단발 내부 HTTP 호출은 자동 등록하지 않는다.
API와 검증 범위는 [AI 작업 취소 계약](../api/ai-task-cancellation.md)을 따른다.
