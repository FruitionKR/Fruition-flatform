# Fruition User Story

Fruition의 요구사항을 사용자가 직접 수행하거나 확인하는 **사용자 스토리**와, 이를 보장하기 위한 **시스템 조건**으로 구분한다.

## 1. 사용자

### 1.1 회원가입

#### 사용자 스토리

- 사용자는 이메일을 인증한 후 이메일, 비밀번호, 닉네임으로 회원가입할 수 있다.

#### 제약조건

- 이메일은 올바른 이메일 형식이어야 한다.
- 이메일은 앞뒤 공백을 제거하고 소문자로 변환한다.
- 이미 가입된 이메일은 다시 사용할 수 없다.
- 회원가입에 사용한 이메일과 인증을 완료한 이메일은 같아야 한다.
- 비밀번호는 8자 이상 72자 이하여야 한다.
- 닉네임 입력값은 최대 50자까지 허용하며, 사용할 때 앞뒤 공백을 제거한다.
- 프론트엔드는 닉네임을 필수로 입력받지만 백엔드는 닉네임이 없거나 공백인 요청을 허용한다.
- 닉네임이 없거나 공백이면 이메일 앞 3글자를 닉네임으로 사용한다.
- 닉네임 중복은 허용한다.
- 인증번호는 기본 5분 동안 유효하며 최대 5회까지 잘못 입력할 수 있다.
- 인증번호는 이메일과 인증 목적별로 기본 60초 후 다시 요청할 수 있으며, 24시간 동안 기본 5회까지 요청할 수 있다.
- 새 인증번호를 발급하면 같은 이메일과 인증 목적의 기존 미사용 인증번호를 만료시킨다.
- 인증 완료 후 발급되는 회원가입 인증 token은 기본 10분 동안 유효하며 한 번만 사용할 수 있다.
- 사용자, 기본 워크스페이스, `OWNER` 멤버십은 하나의 트랜잭션으로 생성한다.
- 기본 워크스페이스에는 초기 Markdown 문서 생성을 시도하며 실패하면 오류를 기록하고 건너뛴다.
- 회원가입 API는 로그인 token을 발급하지 않는다.
- 프론트엔드는 회원가입 성공 후 같은 이메일과 비밀번호로 자동 로그인한다.

#### 성공 시나리오

- 가입되지 않은 올바른 이메일로 인증번호를 요청한 경우 인증 요청을 생성하고 인증번호를 발송한다. (`202 Accepted`)
- 유효한 인증번호를 입력한 경우 1회용 회원가입 인증 token을 발급한다. (`200 OK`)
- 유효한 회원가입 정보를 제출한 경우 사용자와 기본 워크스페이스 및 `OWNER` 멤버십을 생성한다. (`201 Created`)
- 닉네임이 없거나 공백인 경우 이메일 앞 3글자를 닉네임으로 사용해 회원가입한다. (`201 Created`)
- 프론트엔드의 자동 로그인까지 성공한 경우 token을 저장하고 워크스페이스 준비 화면으로 이동한다.

#### 실패 시나리오

- 이메일, 비밀번호 또는 회원가입 인증 token이 공백인 경우 회원가입에 실패한다. (`400 Bad Request`)
- 이메일 형식이 올바르지 않은 경우 인증번호 요청 또는 회원가입에 실패한다. (`400 Bad Request`)
- 비밀번호가 8자 미만이거나 72자를 초과한 경우 회원가입에 실패한다. (`400 Bad Request`)
- 닉네임 입력값이 50자를 초과한 경우 회원가입에 실패한다. (`400 Bad Request`)
- 이미 가입된 이메일로 인증번호를 요청하거나 회원가입하는 경우 실패한다. (`409 Conflict`)
- 인증번호가 틀렸거나 만료됐거나 입력 횟수를 초과한 경우 인증에 실패한다. (`400 Bad Request`)
- 존재하지 않는 인증 요청을 확인하는 경우 인증에 실패한다. (`404 Not Found`)
- 재요청 대기 시간 또는 24시간 요청 횟수를 초과한 경우 인증번호 요청에 실패한다. (`429 Too Many Requests`)
- 인증번호 메일 발송에 실패한 경우 인증번호 요청에 실패한다. (`502 Bad Gateway`)
- 인증한 이메일과 다른 이메일로 가입하거나 만료됐거나 이미 사용한 인증 token을 제출한 경우 회원가입에 실패한다. (`400 Bad Request`)
- 기본 워크스페이스 생성에 실패한 경우 사용자 생성을 포함한 회원가입을 취소한다.
- 초기 Markdown 문서 생성에 실패한 경우 해당 생성을 건너뛰고 오류를 기록한다.
- 회원가입 후 자동 로그인에 실패한 경우 계정은 생성됐을 수 있지만 프론트엔드는 현재 회원가입 실패로 표시한다.

### 1.2 이메일 로그인

#### 사용자 스토리

- 사용자는 이메일과 비밀번호로 로그인할 수 있다.

#### 제약조건

- 이메일과 비밀번호는 공백일 수 없다.
- 이메일은 앞뒤 공백을 제거하고 소문자로 변환한 뒤 비교한다.
- 가입되지 않은 이메일, 잘못된 비밀번호, 비밀번호가 없는 OAuth 전용 계정의 로그인 실패를 동일한 응답으로 처리한다.
- 프론트엔드는 발급받은 token을 브라우저 `localStorage`에 저장한다.

#### 성공 시나리오

- 가입된 이메일과 올바른 비밀번호를 제출한 경우 access token과 refresh token을 발급한다. (`200 OK`)
- 프론트엔드는 token을 저장하고 워크스페이스 준비 화면으로 이동한다.

#### 실패 시나리오

- 이메일 또는 비밀번호가 공백인 경우 로그인에 실패한다. (`400 Bad Request`)
- 가입되지 않은 이메일이나 잘못된 비밀번호를 입력한 경우 로그인에 실패한다. (`401 Unauthorized`)
- 비밀번호가 없는 OAuth 전용 계정으로 이메일 로그인을 시도한 경우 로그인에 실패한다. (`401 Unauthorized`)
- 프론트엔드는 이메일이나 비밀번호 중 어느 값이 잘못됐는지 구분하지 않고 동일한 오류를 표시한다.

### 1.3 OAuth 로그인

#### 사용자 스토리

- 사용자는 Google, Naver, Kakao 계정으로 로그인할 수 있다.

#### 제약조건

- 기존에 연결된 OAuth 계정은 제공자와 제공자 사용자 ID로 사용자를 식별한다.
- 처음 연결하는 OAuth 계정은 제공자가 이메일을 제공해야 한다.
- OAuth 이메일은 앞뒤 공백을 제거하고 소문자로 변환한다.
- OAuth 이메일이 기존 회원의 이메일과 같으면 기존 계정에 OAuth 계정을 연결한다.
- 가입되지 않은 이메일이면 비밀번호가 없는 새 사용자를 생성한다.
- 신규 OAuth 사용자에게는 기본 워크스페이스와 `OWNER` 멤버십을 생성하고 초기 Markdown 문서 생성을 시도한다.
- OAuth 로그인 결과로 발급되는 교환 code는 60초 동안 유효하며 한 번만 사용할 수 있다.
- 프론트엔드는 교환 code를 access token과 refresh token으로 교환한다.

#### 성공 시나리오

- 기존에 연결된 OAuth 계정으로 인증한 경우 연결된 사용자로 로그인한다.
- 기존 회원이 같은 이메일의 OAuth 계정으로 처음 인증한 경우 기존 계정에 OAuth 계정을 연결한다.
- 가입되지 않은 이메일의 OAuth 계정으로 처음 인증한 경우 사용자와 기본 워크스페이스 및 `OWNER` 멤버십을 생성한다.
- 유효한 OAuth 교환 code를 제출한 경우 access token과 refresh token을 발급한다. (`200 OK`)
- 프론트엔드는 발급받은 token을 저장하고 워크스페이스 준비 화면으로 이동한다.

#### 실패 시나리오

- OAuth 인증에 실패한 경우 `error=oauth_failed`와 함께 프론트엔드로 이동한다.
- 처음 연결하는 OAuth 제공자가 이메일을 제공하지 않은 경우 OAuth 인증에 실패한다.
- OAuth 교환 code가 공백인 경우 로그인에 실패한다. (`400 Bad Request`)
- OAuth 교환 code가 유효하지 않거나 만료됐거나 이미 사용된 경우 로그인에 실패한다. (`401 Unauthorized`)
- 신규 OAuth 사용자의 기본 워크스페이스 생성에 실패한 경우 사용자 생성을 포함한 OAuth 가입을 취소한다.
- 초기 Markdown 문서 생성에 실패한 경우 해당 생성을 건너뛰고 오류를 기록한다.

### 1.4 로그인 공통 시스템 조건

#### 구현 범위

- 백엔드: refresh token을 이용한 token 갱신 API가 구현되어 있다.
- 프론트엔드: 자동 token 갱신이 구현되어 있지 않아 access token이 만료되면 다시 로그인해야 한다.

#### 시스템 조건

- 로그인에 성공하면 access token과 refresh token을 발급한다.
- access token은 기본 15분, refresh token은 기본 14일 동안 유효하다.
- 서버는 refresh token 원문 대신 SHA-256 해시를 저장한다.
- 유효한 refresh token으로 갱신하면 기존 token을 폐기하고 새로운 token 쌍을 발급한다.
- 만료됐거나 폐기된 refresh token은 갱신에 사용할 수 없다.

### 1.5 로그아웃

#### 사용자 스토리

- 로그인한 사용자는 로그아웃할 수 있다.

#### 구현 범위

- 백엔드: refresh token을 폐기하는 로그아웃 API가 구현되어 있다.
- 프론트엔드: 브라우저의 인증 정보와 세션 캐시를 제거하는 로그아웃이 구현되어 있다.
- 연동 상태: 프론트엔드는 백엔드 로그아웃 API를 호출하지 않으므로 프론트엔드에서만 로그아웃하면 서버의 refresh token은 폐기되지 않는다.

#### 제약조건

- 백엔드 로그아웃 API는 refresh token을 받아 저장된 token을 폐기한다.
- 백엔드 로그아웃 API는 token의 만료 여부나 기존 폐기 여부를 별도로 검사하지 않는다.
- 프론트엔드 로그아웃은 저장된 access token, refresh token, 워크스페이스 ID와 채팅 세션 캐시를 제거한다.

#### 성공 시나리오

- 저장된 refresh token으로 백엔드 로그아웃을 요청한 경우 해당 token을 폐기한다. (`204 No Content`)
- 프론트엔드에서 로그아웃한 경우 로컬 인증 정보와 세션 캐시를 제거하고 로그인 화면으로 이동한다.

#### 실패 시나리오

- 백엔드 로그아웃 요청의 refresh token이 공백인 경우 실패한다. (`400 Bad Request`)
- 서버에 존재하지 않는 refresh token으로 로그아웃을 요청한 경우 실패한다. (`401 Unauthorized`)

### 1.6 비밀번호 재설정

#### 사용자 스토리

- 사용자는 이메일 인증을 거쳐 비밀번호를 재설정할 수 있다.

#### 제약조건

- 이메일은 올바른 이메일 형식이어야 하며 앞뒤 공백을 제거하고 소문자로 변환한다.
- 비밀번호 재설정 인증번호 요청은 계정 존재 여부와 관계없이 동일하게 처리한다.
- 인증번호의 유효기간, 오입력 횟수, 재요청 대기 시간과 24시간 요청 제한은 회원가입 인증과 같다.
- 인증 완료 후 발급되는 비밀번호 재설정 token은 기본 10분 동안 유효하며 한 번만 사용할 수 있다.
- 새 비밀번호는 8자 이상 72자 이하여야 한다.
- 프론트엔드는 새 비밀번호와 비밀번호 확인 값이 같은지 검사한다.
- 비밀번호를 재설정하면 해당 사용자의 활성 refresh token을 모두 폐기한다.

#### 성공 시나리오

- 올바른 이메일로 인증번호를 요청한 경우 계정 존재 여부를 노출하지 않고 인증 요청을 생성한다. (`202 Accepted`)
- 유효한 인증번호를 입력한 경우 1회용 비밀번호 재설정 token을 발급한다. (`200 OK`)
- 유효한 token과 새 비밀번호를 제출한 경우 비밀번호를 변경하고 기존 활성 refresh token을 모두 폐기한다. (`204 No Content`)
- 프론트엔드는 비밀번호 재설정 성공 후 로그인 화면으로 이동한다.

#### 실패 시나리오

- 이메일 형식이 올바르지 않거나 새 비밀번호 또는 인증 token이 공백인 경우 실패한다. (`400 Bad Request`)
- 새 비밀번호가 8자 미만이거나 72자를 초과한 경우 실패한다. (`400 Bad Request`)
- 프론트엔드에서 새 비밀번호와 확인 값이 다르면 API를 요청하지 않고 실패를 표시한다.
- 인증번호가 틀렸거나 만료됐거나 입력 횟수를 초과한 경우 인증에 실패한다. (`400 Bad Request`)
- 존재하지 않는 인증 요청을 확인하는 경우 실패한다. (`404 Not Found`)
- 인증번호 요청 제한을 초과한 경우 실패한다. (`429 Too Many Requests`)
- 인증번호 메일 발송에 실패한 경우 실패한다. (`502 Bad Gateway`)
- 이메일, 인증 목적 또는 유효기간이 일치하지 않는 재설정 token을 제출한 경우 실패한다. (`400 Bad Request`)
- 가입되지 않은 이메일로 최종 비밀번호 변경을 요청한 경우 계정 존재 여부를 별도로 노출하지 않고 token 오류로 처리한다. (`400 Bad Request`)

### 1.7 내 정보 조회

#### 사용자 스토리

- 로그인한 사용자는 자신의 정보를 조회할 수 있다.

#### 제약조건

- 유효한 access token이 필요하다.
- 응답에는 사용자 ID, 이메일, 닉네임, 가입 시각을 포함한다.
- 프론트엔드 사이드바에는 닉네임을 표시하고, 닉네임이 없으면 이메일을 표시한다.
- 사용자 정보 조회에 실패하면 프론트엔드는 `사용자`라는 기본 이름을 표시한다.

#### 성공 시나리오

- 유효한 access token으로 요청한 경우 로그인한 사용자의 정보를 반환한다. (`200 OK`)

#### 실패 시나리오

- access token 없이 요청한 경우 실패한다. (`401 Unauthorized`)
- token의 사용자 ID에 해당하는 사용자가 없는 경우 실패한다. (`404 Not Found`)

## 2. 워크스페이스

### 2.1 워크스페이스 생성

#### 사용자 스토리

- 로그인한 사용자는 새로운 워크스페이스를 생성할 수 있다.

#### 제약조건

- 워크스페이스 이름은 공백일 수 없으며 입력값 기준 255자 이하여야 한다.
- 워크스페이스 이름은 저장할 때 앞뒤 공백을 제거한다.
- 같은 이름의 워크스페이스를 여러 개 생성할 수 있다.
- 생성할 수 있는 워크스페이스 개수에는 별도 제한이 없다.
- 생성 요청에는 멱등성을 적용하지 않으므로 같은 요청을 반복하면 별도 워크스페이스를 생성한다.
- 워크스페이스를 생성한 사용자는 해당 워크스페이스의 `OWNER`가 된다.
- 워크스페이스와 `OWNER` 멤버십은 하나의 트랜잭션으로 생성한다.
- 새 워크스페이스에는 편집 가능한 초기 Markdown 문서 `새 노트.md` 생성을 시도한다.
- 초기 Markdown 문서 생성 중 예외가 발생하면 오류를 기록하고 생성을 건너뛴다.
- 프론트엔드에서 워크스페이스를 추가하면 `새 워크스페이스`라는 이름으로 생성한다.

#### 성공 시나리오

- 올바른 이름으로 요청한 경우 워크스페이스와 `OWNER` 멤버십을 생성한다. (`201 Created`)
- 워크스페이스 생성 후 초기 Markdown 문서 생성을 시도한다.
- 프론트엔드에서 생성한 경우 새 워크스페이스를 선택하고 화면을 다시 불러온다.
- 초기 Markdown 문서 생성에 실패한 경우 오류를 기록하고 해당 문서 생성을 건너뛴다.

#### 실패 시나리오

- 로그인하지 않은 사용자가 생성을 요청한 경우 실패한다. (`401 Unauthorized`)
- 이름이 공백이거나 255자를 초과한 경우 실패한다. (`400 Bad Request`)
- 프론트엔드의 생성 요청이 실패한 경우 오류를 표시한다.

### 2.2 워크스페이스 목록 조회

#### 사용자 스토리

- 로그인한 사용자는 자신이 소유하거나 멤버로 참여한 워크스페이스 목록을 조회할 수 있다.

#### 제약조건

- 삭제되지 않은 워크스페이스만 반환한다.
- 사용자가 `OWNER` 또는 `MEMBER`로 참여한 워크스페이스만 반환한다.
- 목록은 생성 시각이 최신인 순서로 반환한다.
- 목록 응답에는 사용자의 역할을 포함하지 않는다.

#### 성공 시나리오

- 참여한 활성 워크스페이스가 있는 경우 최신 생성 순서로 반환한다. (`200 OK`)
- 참여한 활성 워크스페이스가 없는 경우 빈 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 목록을 요청한 경우 실패한다. (`401 Unauthorized`)
- 프론트엔드에서 목록 조회에 실패한 경우 오류와 재시도 기능을 표시한다.

### 2.3 워크스페이스 전환

#### 사용자 스토리

- 사용자는 자신이 참여한 다른 워크스페이스로 전환할 수 있다.

#### 구현 범위

- 프론트엔드: 선택한 워크스페이스 ID를 브라우저에 저장하는 전환 기능이 구현되어 있다.
- 백엔드: 워크스페이스 전환을 위한 별도의 API는 없다.

#### 제약조건

- 워크스페이스를 전환하면 전체 화면을 다시 불러온다.
- 워크스페이스 준비 화면에서는 목록의 첫 번째 워크스페이스를 자동 선택한다.
- 참여한 워크스페이스가 없으면 `나의 워크스페이스`를 자동 생성하고 선택한다.

#### 성공 시나리오

- 사이드바에서 워크스페이스를 선택한 경우 해당 ID를 저장하고 화면을 다시 불러온다.
- 워크스페이스 준비 화면에서 참여한 워크스페이스가 있는 경우 가장 최근에 생성된 워크스페이스를 선택하고 홈 화면으로 이동한다.
- 참여한 워크스페이스가 없는 경우 `나의 워크스페이스`를 생성하고 홈 화면으로 이동한다.

#### 실패 시나리오

- 워크스페이스 목록 조회 또는 자동 생성에 실패한 경우 오류와 재시도 기능을 표시한다.
- 저장된 워크스페이스 ID가 없는 상태로 홈 화면에 접근한 경우 워크스페이스 준비 화면으로 이동한다.

### 2.4 워크스페이스 이름 변경

#### 사용자 스토리

- 워크스페이스 소유자는 워크스페이스 이름을 변경할 수 있다.

#### 구현 범위

- 백엔드: 워크스페이스 이름 변경 API가 구현되어 있다.
- 프론트엔드: 워크스페이스 이름 변경 기능을 제공하지 않는다.

#### 제약조건

- `OWNER`만 이름을 변경할 수 있다.
- 삭제되지 않은 워크스페이스만 이름을 변경할 수 있다.
- 변경할 이름은 공백일 수 없으며 입력값 기준 255자 이하여야 한다.
- 이름은 저장할 때 앞뒤 공백을 제거한다.
- 다른 워크스페이스와 같은 이름으로 변경할 수 있다.

#### 성공 시나리오

- 소유자가 올바른 이름을 제출한 경우 이름을 변경한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 이름이 공백이거나 255자를 초과한 경우 실패한다. (`400 Bad Request`)
- 존재하지 않거나 소유하지 않은 워크스페이스의 이름을 변경하는 경우 실패한다. (`404 Not Found`)
- 삭제된 워크스페이스의 이름을 변경하는 경우 실패한다. (`404 Not Found`)

### 2.5 워크스페이스 삭제

#### 사용자 스토리

- 워크스페이스 소유자는 워크스페이스를 소프트 삭제할 수 있다.

#### 구현 범위

- 백엔드: 워크스페이스 소프트 삭제 API가 구현되어 있다.
- 프론트엔드: 워크스페이스 삭제 기능을 제공하지 않는다.

#### 제약조건

- `OWNER`만 워크스페이스를 삭제할 수 있다.
- 삭제하면 하위 데이터와 멤버십을 실제 삭제하지 않고 삭제 시각과 삭제 사용자를 기록한다.
- 삭제된 워크스페이스는 일반 목록과 멤버십 기반 콘텐츠 접근에서 제외한다.
- 삭제 요청에는 1자 이상 255자 이하의 `Idempotency-Key`가 필요하다.
- 같은 요청과 멱등 키를 24시간 안에 반복하면 기존 결과를 반환한다.
- 같은 멱등 키를 다른 워크스페이스 삭제에 사용하면 충돌로 거절한다.

#### 성공 시나리오

- 소유자가 활성 워크스페이스를 유효한 멱등 키로 삭제한 경우 소프트 삭제 상태를 반환한다. (`200 OK`)
- 같은 삭제 요청을 같은 멱등 키로 24시간 안에 반복한 경우 최초 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 존재하지 않거나 소유하지 않은 워크스페이스를 삭제하는 경우 실패한다. (`404 Not Found`)
- 이미 삭제된 워크스페이스를 새로운 요청으로 다시 삭제하는 경우 실패한다. (`404 Not Found`)
- 멱등 키가 없거나 공백이거나 255자를 초과한 경우 실패한다. (`400 Bad Request`)
- 같은 멱등 키를 다른 워크스페이스 삭제에 사용한 경우 실패한다. (`409 Conflict`)

### 2.6 삭제된 워크스페이스 조회

#### 사용자 스토리

- 워크스페이스 소유자는 자신이 삭제한 워크스페이스 목록을 조회할 수 있다.

#### 성공 시나리오

## 3. 문서

### 3.1 파일 업로드

#### 사용자 스토리

- 로그인한 사용자는 파일을 선택하거나 드래그하여 하나 이상의 PDF 또는 Markdown 파일을 업로드할 수 있다.

#### 구현 범위

- 백엔드: PDF·Markdown 업로드와 폴더 지정 저장이 구현되어 있다.
- 프론트엔드: 다중 파일 선택·드롭 업로드가 구현되어 있지만 `.txt`도 선택할 수 있고 폴더 ID는 전달하지 않는다.
- 연동 상태: PDF·Markdown의 최상위 업로드는 동작하지만 `.txt`와 폴더 지정은 양쪽 동작이 일치하지 않는다.

#### 제약조건

- 백엔드는 PDF와 Markdown 파일만 허용한다.
- Markdown 파일은 `.md` 또는 `.markdown` 확장자를 지원한다.
- 프론트엔드는 PDF, `.md`, `.txt` 파일을 선택 대상으로 허용하므로 `.txt` 파일은 백엔드에서 거절될 수 있다.
- 전체 multipart 요청 크기는 최대 50MB로 설정되어 있다.
- Markdown 본문은 올바른 UTF-8이어야 하며 최대 5MB까지 허용한다.
- 파일명은 앞뒤 공백을 제외하고 1자 이상 255자 이하여야 한다.
- 파일명에는 `/`, `\`, null 문자를 사용할 수 없다.
- 업로드 요청에는 1자 이상 255자 이하의 `Idempotency-Key`가 필요하다.
- 같은 요청과 멱등 키를 24시간 안에 반복하면 기존 결과를 반환한다.
- PDF와 Markdown 문서는 `uploaded` 상태로 저장하며 자동으로 Wiki ingest하지 않는다.
- Markdown은 즉시 편집 상태를 생성하고 PDF는 원본만 저장한다.
- 프론트엔드는 여러 파일을 각각 별도 요청으로 병렬 업로드한다.

#### 성공 시나리오

- 올바른 PDF 또는 Markdown 파일을 업로드한 경우 원본과 문서 정보를 저장한다. (`201 Created`)
- Markdown 파일을 업로드한 경우 즉시 편집 가능한 상태를 함께 생성한다. (`201 Created`)
- 여러 파일을 선택하거나 드롭한 경우 허용된 파일을 각각 업로드한다.
- 같은 요청을 같은 멱등 키로 반복한 경우 새 문서를 만들지 않고 기존 결과를 반환한다. (`201 Created`)

#### 실패 시나리오

- 파일이 없거나 비어 있는 경우 실패한다. (`400 Bad Request`)
- 지원하지 않는 파일 형식인 경우 실패한다. (`415 Unsupported Media Type`)
- Markdown이 올바른 UTF-8이 아니거나 파일명이 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- Markdown 본문이 5MB를 초과한 경우 실패한다. (`413 Payload Too Large`)
- 멱등 키가 없거나 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 같은 멱등 키를 다른 요청에 사용한 경우 실패한다. (`409 Conflict`)
- 원본 저장이나 DB 저장에 실패한 경우 저장된 원본을 정리하고 업로드에 실패한다. (`500 Internal Server Error`)

### 3.2 Markdown 문서 생성

#### 사용자 스토리

- 로그인한 사용자는 빈 Markdown 문서 또는 AI가 생성한 Markdown 초안을 새 문서로 만들 수 있다.

#### 제약조건

- 직접 생성 API는 빈 Markdown 본문을 허용한다.
- 문서 이름은 앞뒤 공백을 제거하며 확장자를 포함해 255자 이하여야 한다.
- 빈 이름, `.`, `..`, 경로 구분 문자와 제어 문자는 사용할 수 없다.
- Markdown 본문은 UTF-8 기준 5MB 이하여야 한다.
- 생성 요청에는 유효한 `Idempotency-Key`가 필요하다.
- 직접 생성한 문서는 `completed`, `version 1`의 편집 문서로 저장한다.
- 프론트엔드의 빈 문서와 AI 초안 생성은 직접 생성 API가 아니라 Markdown 파일 업로드 API를 사용한다.
- AI 초안은 미리보기·재생성·취소할 수 있지만 생성 전에 본문을 직접 편집할 수는 없다.

#### 성공 시나리오

- 올바른 이름과 Markdown을 제출한 경우 지정한 폴더 또는 최상위에 편집 문서를 생성한다. (`201 Created`)
- 빈 본문으로 요청한 경우에도 편집 가능한 문서를 생성한다. (`201 Created`)
- AI 초안 생성을 수락한 경우 초안을 Markdown 파일로 업로드하고 새 문서로 연다.

#### 실패 시나리오

- 문서 이름이나 Markdown 본문이 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- Markdown 본문이 5MB를 초과한 경우 실패한다. (`413 Payload Too Large`)
- 지정한 폴더가 존재하지 않는 경우 실패한다. (`404 Not Found`)
- 같은 멱등 키를 다른 생성 요청에 사용한 경우 실패한다. (`409 Conflict`)

### 3.3 문서 목록 조회

#### 사용자 스토리

- 로그인한 사용자는 워크스페이스의 활성 문서 목록을 조회할 수 있다.

#### 제약조건

- 사용자가 멤버로 참여한 워크스페이스만 조회할 수 있다.
- 소프트 삭제된 문서는 제외한다.
- 문서는 `sort_order`, ID 순으로 반환한다.
- 처리 상태, 처리 단계, 편집 가능 여부와 현재 version을 포함한다.

#### 성공 시나리오

- 활성 문서가 있는 경우 정렬된 문서 목록을 반환한다. (`200 OK`)
- 활성 문서가 없는 경우 빈 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 참여하지 않은 워크스페이스를 조회한 경우 실패한다. (`404 Not Found`)

### 3.4 문서 계층 탐색

#### 사용자 스토리

- 로그인한 사용자는 폴더와 문서를 계층 구조로 탐색할 수 있다.

#### 구현 범위

- 백엔드: 폴더·문서 계층, 하위 항목 및 breadcrumb 조회 API가 구현되어 있다.
- 프론트엔드: 백엔드 계층 API를 사용하지 않고 `localStorage` 트리와 평면 문서 목록을 병합한다.
- 연동 상태: 백엔드 계층 정보와 프론트엔드 트리가 연결되어 있지 않다.

#### 제약조건

- 전체 트리 조회와 특정 폴더의 하위 항목 조회를 지원한다.
- 폴더와 문서는 같은 부모 안에서 `sort_order`, ID 순으로 정렬한다.
- 소프트 삭제된 폴더와 문서는 제외한다.
- 조회 결과에는 동시 변경 확인을 위한 현재 version을 포함한다.

#### 성공 시나리오

- 전체 트리를 요청한 경우 활성 폴더와 문서를 중첩 구조로 반환한다. (`200 OK`)
- 최상위 또는 특정 폴더를 요청한 경우 바로 아래의 폴더와 문서를 반환한다. (`200 OK`)
- 문서나 폴더의 경로를 요청한 경우 최상위부터 대상까지의 breadcrumb를 반환한다. (`200 OK`)

#### 실패 시나리오

- 참여하지 않은 워크스페이스나 존재하지 않는 폴더를 요청한 경우 실패한다. (`404 Not Found`)
- breadcrumb 요청에 폴더와 문서를 모두 지정하거나 모두 지정하지 않은 경우 실패한다. (`400 Bad Request`)

### 3.5 문서 및 폴더 검색

#### 사용자 스토리

- 로그인한 사용자는 이름으로 문서와 폴더를 검색할 수 있다.

#### 구현 범위

- 백엔드: 현재 워크스페이스의 활성 문서와 폴더를 검색하는 계층 검색 API가 구현되어 있다.
- 프론트엔드: 백엔드 검색 API를 호출하지 않고 현재 불러온 트리의 문서와 Wiki 항목을 검색한다.
- 연동 상태: 백엔드와 프론트엔드의 검색 대상과 결과가 서로 다르다.

#### 제약조건

- 백엔드는 대소문자를 구분하지 않고 이름의 일부가 일치하는 항목을 찾으며 문서 본문은 검색하지 않는다.
- 백엔드 검색 결과에는 대상 항목의 breadcrumb를 포함한다.
- 프론트엔드는 현재 불러온 트리에서 문서와 Wiki 항목만 검색하며 폴더는 검색하지 않는다.
- 프론트엔드는 검색 결과를 최대 8개까지 표시하고 나머지 결과 개수를 안내한다.

#### 성공 시나리오

- 백엔드에서 검색어와 일치하는 활성 문서와 폴더를 반환한다. (`200 OK`)
- 백엔드에서 일치하는 항목이 없으면 빈 결과를 반환한다. (`200 OK`)
- 프론트엔드에서 검색 결과를 선택하면 해당 문서 또는 Wiki 페이지를 연다.
- 프론트엔드 검색 결과가 8개를 초과하면 8개만 표시하고 나머지 결과 개수를 안내한다.

#### 실패 시나리오

- 백엔드 검색어가 공백인 경우 실패한다. (`400 Bad Request`)
- 참여하지 않은 워크스페이스를 백엔드에서 검색한 경우 실패한다. (`404 Not Found`)

### 3.6 문서 상세 조회

#### 사용자 스토리

- 로그인한 사용자는 문서 상세 정보와 연결된 Wiki 페이지를 조회할 수 있다.

#### 제약조건

- 문서 상태, 처리 단계, 편집 가능 여부, 현재 version, Markdown 편집본과 편집 잠금 상태를 반환한다.
- 소프트 삭제된 문서는 조회하지 않는다.
- Markdown 문서는 필요한 경우 기존 원본에서 편집 상태를 초기화한다.

#### 성공 시나리오

- 활성 문서를 요청한 경우 상세 정보와 연결된 Wiki 페이지를 반환한다. (`200 OK`)

#### 실패 시나리오

- 존재하지 않거나 삭제된 문서를 요청한 경우 실패한다. (`404 Not Found`)
- 참여하지 않은 워크스페이스의 문서를 요청한 경우 실패한다. (`404 Not Found`)

### 3.7 원본 문서 조회

#### 사용자 스토리

- 로그인한 사용자는 업로드한 원본 문서를 조회하거나 내려받을 수 있다.

#### 제약조건

- PDF와 text 형식은 브라우저에서 바로 표시할 수 있도록 반환한다.
- 그 외 형식은 첨부 파일로 반환한다.
- 직접 생성하거나 복제한 Markdown 문서는 별도의 원본 파일을 갖지 않는다.
- 현재 직접 생성 문서처럼 원본 경로가 없는 문서를 원본 API로 요청하면 정상적인 `404` 처리가 보장되지 않는다.

#### 성공 시나리오

- 저장된 원본이 있는 경우 해당 파일을 스트리밍한다. (`200 OK`)

#### 실패 시나리오

- 문서나 원본 파일이 없는 경우 실패한다. (`404 Not Found`)
- 원본 경로가 없는 문서 요청은 현재 서버 오류가 발생할 수 있다.

### 3.8 Markdown 내보내기

#### 사용자 스토리

- 로그인한 워크스페이스 멤버는 편집 가능한 Markdown 문서의 최신 본문과 문서에서 사용하는 이미지를
  로컬에서 열 수 있는 파일로 내려받을 수 있다.

#### 구현 범위

- 백엔드: 이미지가 없으면 `.md`, 관리 이미지가 있으면 Markdown과 이미지를 포함한 ZIP을 반환한다.
- 프론트엔드: Markdown·ZIP 내보내기를 실행하는 UI는 아직 제공하지 않는다.
- 연동 상태: API는 사용할 수 있지만 사용자가 화면에서 내보내기를 시작할 수는 없다.

#### 제약조건

- 관리 이미지가 없으면 최신 편집본을 UTF-8 `.md` 파일로 반환한다.
- 관리 이미지가 있으면 최신 Markdown과 `assets/` 이미지를 ZIP으로 반환한다.
- ZIP의 Markdown은 관리 이미지 주소를 `./assets/<filename>` 상대 경로로 바꿔 로컬에서도 표시한다.
- 같은 이름의 이미지는 파일명 suffix로 구분하고 같은 asset은 한 번만 포함한다.
- 외부 `http`·`https` 이미지는 원문 주소를 유지하며 서버가 대신 내려받지 않는다.
- ZIP에는 이미지 최대 100개·합계 100MB까지만 포함할 수 있다.
- PDF 등 읽기 전용 원본은 내보낼 수 없다.

#### 성공 시나리오

- 편집 가능한 문서를 요청한 경우 최신 본문을 `.md` 파일로 반환한다. (`200 OK`)
- 관리 이미지가 있는 편집 문서를 요청한 경우 Markdown과 이미지를 완성된 ZIP으로 반환한다. (`200 OK`)

#### 실패 시나리오

- 문서가 없거나 편집 가능한 Markdown 문서가 아닌 경우 실패한다. (`404 Not Found`)
- 참조한 이미지가 없거나 읽을 수 없는 경우 불완전한 ZIP을 반환하지 않고 실패한다. (`422 Unprocessable Entity`)
- 이미지가 100개 또는 합계 100MB를 초과한 경우 실패한다. (`422 Unprocessable Entity`)

### 3.9 원본 block 조회

#### 사용자 스토리

- 로그인한 사용자는 인용 근거를 확인하기 위해 원본 문서의 block 목록을 조회할 수 있다.

#### 제약조건

- block은 block ID 순으로 반환한다.
- 저장된 block이 없으면 빈 목록을 반환한다.

#### 성공 시나리오

- 활성 문서를 요청한 경우 원본 block 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 존재하지 않거나 삭제된 문서를 요청한 경우 실패한다. (`404 Not Found`)

### 3.10 문서 이름 변경

#### 사용자 스토리

- 문서 소유자는 문서의 표시 이름을 변경할 수 있다.

#### 구현 범위

- 백엔드: `display_name`과 `base_version`을 받는 이름 변경 API가 구현되어 있다.
- 프론트엔드: 이름 변경 요청은 구현되어 있지만 `filename`만 전달한다.
- 연동 상태: 요청 규격이 달라 현재 프론트엔드의 이름 변경 요청은 실패한다.

#### 제약조건

- 기존 확장자는 유지한다.
- 이름은 앞뒤 공백을 제거하며 확장자를 포함해 255자 이하여야 한다.
- 빈 이름, `.`, `..`, 경로 구분 문자와 제어 문자는 사용할 수 없다.
- 같은 워크스페이스에서 중복된 문서 이름을 허용한다.
- 현재 version이 일치해야 한다.
- 본문과 연결된 Wiki 페이지 제목은 변경하지 않는다.

#### 성공 시나리오

- 소유자가 올바른 이름과 현재 version을 제출한 경우 표시 이름을 변경한다. (`200 OK`)
- 기존 이름과 같은 이름을 제출한 경우 version을 변경하지 않고 기존 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- 이름이나 base version이 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 문서 소유자가 아닌 경우 실패한다. (`403 Forbidden`)
- 문서가 없거나 삭제된 경우 실패한다. (`404 Not Found`)
- 현재 version과 일치하지 않는 경우 실패한다. (`409 Conflict`)

### 3.11 폴더 생성

#### 사용자 스토리

- 워크스페이스 멤버는 폴더와 하위 폴더를 생성할 수 있다.

#### 구현 범위

- 백엔드: 폴더 및 하위 폴더 생성 API가 구현되어 있다.
- 프론트엔드: 폴더를 `localStorage`에만 생성한다.
- 연동 상태: 프론트엔드에서 만든 폴더는 서버에 저장되지 않는다.

#### 제약조건

- 폴더 이름은 앞뒤 공백을 제거하고 1자 이상 255자 이하여야 한다.
- 같은 이름의 폴더를 여러 개 생성할 수 있다.
- 생성한 폴더는 지정한 부모의 마지막 위치에 배치한다.
- 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 올바른 이름으로 요청한 경우 폴더를 생성한다. (`201 Created`)
- 부모 폴더를 지정한 경우 해당 폴더 아래에 생성한다. (`201 Created`)

#### 실패 시나리오

- 이름이나 멱등 키가 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 부모 폴더가 존재하지 않는 경우 실패한다. (`404 Not Found`)
- 같은 멱등 키를 다른 요청에 사용한 경우 실패한다. (`409 Conflict`)

### 3.12 폴더 이름 변경

#### 사용자 스토리

- 워크스페이스 멤버는 폴더 이름을 변경할 수 있다.

#### 구현 범위

- 백엔드: version과 멱등 키를 검사하는 폴더 이름 변경 API가 구현되어 있다.
- 프론트엔드: `localStorage`의 폴더 이름만 변경한다.
- 연동 상태: 프론트엔드의 이름 변경은 서버에 반영되지 않는다.

#### 제약조건

- 폴더 이름은 앞뒤 공백을 제거하고 1자 이상 255자 이하여야 한다.
- 현재 version과 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 올바른 이름과 현재 version을 제출한 경우 폴더 이름을 변경한다. (`200 OK`)

#### 실패 시나리오

- 이름이나 멱등 키가 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 폴더가 없는 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)

### 3.13 문서와 폴더 이동

#### 사용자 스토리

- 워크스페이스 멤버는 문서와 폴더를 다른 폴더나 최상위로 이동하고 순서를 변경할 수 있다.

#### 구현 범위

- 백엔드: 문서·폴더 이동과 형제 순서 재계산 API가 구현되어 있다.
- 프론트엔드: 드래그 결과를 `localStorage`에만 반영한다.
- 연동 상태: 프론트엔드의 이동과 순서 변경은 서버에 반영되지 않는다.

#### 제약조건

- 현재 version과 유효한 `Idempotency-Key`가 필요하다.
- 위치를 생략하면 대상 폴더의 마지막에 배치한다.
- 범위를 벗어난 위치는 첫 번째 또는 마지막 위치로 보정한다.
- 폴더를 자기 자신이나 자신의 하위 폴더로 이동할 수 없다.
- 문서와 폴더가 공유하는 형제 순서를 다시 계산한다.

#### 성공 시나리오

- 유효한 대상과 version으로 요청한 경우 항목을 이동하고 형제 순서를 갱신한다. (`200 OK`)

#### 실패 시나리오

- 이동할 항목이나 대상 폴더가 없는 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)
- 폴더를 자기 자신이나 하위 폴더로 이동하는 경우 실패한다. (`409 Conflict`)

### 3.14 폴더 삭제

#### 사용자 스토리

- 워크스페이스 멤버는 폴더를 소프트 삭제할 수 있다.

#### 구현 범위

- 백엔드: 폴더와 하위 항목의 소프트 삭제 API가 구현되어 있다.
- 프론트엔드: 서버 폴더 삭제 API를 호출하지 않는다.
- 연동 상태: 프론트엔드의 폴더 삭제는 서버에 반영되지 않는다.

#### 제약조건

- 빈 폴더는 모든 워크스페이스 멤버가 삭제할 수 있다.
- 하위 항목이 있는 폴더는 워크스페이스 `OWNER`만 삭제할 수 있다.
- 하위 폴더와 문서를 같은 삭제 작업 ID로 함께 소프트 삭제한다.
- 현재 version과 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 권한이 있는 사용자가 폴더를 삭제한 경우 하위 항목을 포함해 소프트 삭제한다. (`200 OK`)

#### 실패 시나리오

- 일반 멤버가 내용이 있는 폴더를 삭제하는 경우 실패한다. (`403 Forbidden`)
- 폴더가 없는 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)

### 3.15 폴더 복구

#### 사용자 스토리

- 워크스페이스 멤버는 삭제된 폴더를 복구할 수 있다.

#### 구현 범위

- 백엔드: 삭제 작업에 포함된 폴더와 문서를 함께 복구하는 API가 구현되어 있다.
- 프론트엔드: 폴더 복구 기능을 제공하지 않는다.

#### 제약조건

- 같은 삭제 작업에 포함된 하위 폴더와 문서도 함께 복구한다.
- 원래 부모가 활성 상태이면 원래 위치로 복구한다.
- 원래 부모가 삭제된 상태이면 최상위 마지막 위치로 복구한다.
- 현재 version과 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 삭제된 폴더를 요청한 경우 복구 대상 하위 항목과 함께 복구한다. (`200 OK`)

#### 실패 시나리오

- 삭제된 폴더를 찾을 수 없는 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)

### 3.16 Markdown 편집 및 저장

#### 사용자 스토리

- 문서 소유자는 Markdown 문서를 원문 편집기 또는 WYSIWYG 편집기로 편집하고 문서에 이미지를
  추가해 본문과 함께 저장할 수 있다.

#### 구현 범위

- 백엔드: Markdown·신규 이미지 원자 저장, 멤버 전용 이미지 조회와 편집 잠금
  획득·heartbeat·해제 API가 구현되어 있다.
- 프론트엔드: Markdown 자동 저장은 연결되어 있지만 편집 잠금 API는 사용하지 않는다.
- 프론트엔드: 이미지 선택/drop/paste, `attachment://` placeholder, 인증 Blob 표시와 수동 저장 UI는
  아직 구현되지 않았다.
- 연동 상태: 이미지 없는 일반 편집·자동 저장은 동작한다. 이미지 저장·표시와 다른 사용자의 편집 상태
  확인·읽기 전용 전환은 Backend 계약만 준비됐고 사용자 화면에서는 동작하지 않는다.

#### 제약조건

- 편집 가능한 Markdown 문서만 저장할 수 있다.
- 프론트엔드는 변경 후 800ms 동안 추가 입력이 없으면 자동 저장한다.
- 별도의 저장 버튼이나 `Ctrl+S` 저장 기능은 없다.
- 저장 시 현재 version을 검사한다.
- 같은 본문을 저장하면 새 version을 생성하지 않는다.
- Markdown 본문은 UTF-8 기준 5MB 이하여야 한다.
- 이미지는 PNG·JPEG·WebP·GIF만 허용하며 SVG는 허용하지 않는다.
- 이미지당 10MB, 한 번의 저장당 신규 이미지 20개·합계 100MB, 가로·세로 16,384px 제한을 적용한다.
- 본문의 임시 이미지 placeholder와 업로드 file은 정확히 1:1로 대응해야 한다.
- 본문·새 version·이미지 정보·문서의 이미지 참조는 함께 성공하거나 함께 실패한다.
- 저장에 실패하면 이번 요청에서 새로 저장한 이미지 object를 보상 삭제한다.
- 워크스페이스 멤버만 저장된 이미지를 조회할 수 있으며 다른 workspace나 비멤버에게는 존재를 노출하지 않는다.
- 문서에서 제거된 이미지는 7일 동안 보관하고 그 안에 다시 사용되지 않으면 자동 정리한다.
- 다른 사용자가 유효한 편집 잠금을 보유하면 저장을 거절한다.
- 편집 잠금의 기본 유효기간은 45초이다.

#### 성공 시나리오

- 변경된 본문과 현재 version을 저장한 경우 version을 1 증가시키고 변경 전후 스냅샷을 저장하며,
  서버가 확정한 최종 Markdown을 함께 반환한다. (`200 OK`)
- 신규 이미지와 본문을 함께 저장한 경우 서버가 확정한 이미지 주소로 Markdown을 치환하고 새 version과
  attachment–asset 매핑을 반환한다. (`200 OK`)
- 워크스페이스 멤버가 저장된 이미지를 요청하면 검증된 이미지 형식과 private cache 정책으로 반환한다. (`200 OK`)
- 현재 본문과 같은 본문을 저장한 경우 version을 변경하지 않으며, 서버가 보관 중인 현재 Markdown을 반환해
  클라이언트가 저장 기준을 맞출 수 있다. (`200 OK`)
- 프론트엔드는 저장 상태를 변경됨, 저장 중, 저장 실패, 저장 충돌로 표시한다.

#### 실패 시나리오

- 편집할 수 없는 문서나 잘못된 본문을 저장하는 경우 실패한다. (`400 Bad Request`)
- 문서 소유자가 아닌 경우 실패한다. (`403 Forbidden`)
- 문서가 없는 경우 실패한다. (`404 Not Found`)
- 현재 version이 일치하지 않는 경우 실패하고 프론트엔드는 이후 자동 저장을 중단한다. (`409 Conflict`)
- 다른 사용자가 유효한 편집 잠금을 보유한 경우 실패한다. (`423 Locked`)
- Markdown 본문이 5MB를 초과한 경우 실패한다. (`413 Payload Too Large`)
- 이미지 형식이 지원되지 않거나 이미지 bytes가 손상된 경우 실패한다. (`400 Bad Request` 또는 `415 Unsupported Media Type`)
- 이미지 개수·크기·dimension 제한을 초과한 경우 Markdown 용량 오류와 구분해 실패한다. (`413 Payload Too Large`)
- 다른 workspace의 이미지나 존재하지 않는 이미지를 본문에 참조하면 저장 전체가 실패한다. (`400 Bad Request`)

### 3.17 AI 문서 편집

#### 사용자 스토리

- 사용자는 AI에게 Markdown 문서의 선택 영역 또는 전체 문서 편집을 요청하고 결과를 적용하거나 취소할 수 있다.

#### 제약조건

- Markdown 원문 모드에서는 선택 영역을, WYSIWYG 모드에서는 문서 전체를 편집 대상으로 사용한다.
- AI 편집안의 요약, 변경 본문, 줄 단위 diff와 렌더링 결과를 표시한다.
- 사용자는 편집안을 수락, 취소 또는 재생성할 수 있다.
- 편집안을 미리보기에서 직접 수정할 수는 없다.
- 편집 대상 문서, 기준 version과 원문 스냅샷이 그대로인 경우에만 적용한다.
- AI 편집안을 적용하면 별도 대기 없이 즉시 자동 저장을 시작한다.
- Backend가 발급한 `apply_operation_id`가 저장 성공 요청과 일치할 때만 AI 편집 작업 이력으로 연결한다.
- 이미지가 포함된 AI 편집 저장도 본문과 이미지가 모두 성공한 뒤에만 문서와 작업 이력에 반영한다.
- 프론트엔드는 아직 서버 성공 전에 본문을 바꾸는 기존 적용 흐름을 사용하므로 `apply_operation_id` 기반
  서버 성공 후 반영으로 변경해야 한다.

#### 성공 시나리오

- 편집 대상이 변경되지 않은 상태에서 편집안을 수락하면 본문에 적용하고 자동 저장을 시작한다.
- 유효한 AI 적용 표로 저장이 성공하면 해당 문서 version을 AI 작업 이력과 연결한다.
- 편집안을 취소하면 현재 문서를 변경하지 않는다.
- 재생성을 요청하면 같은 편집 대상에 대한 새 편집안을 요청한다.

#### 실패 시나리오

- 편집안 생성 이후 문서나 선택 대상이 변경된 경우 적용에 실패한다.
- AI 편집 저장에 실패한 경우 실패 상태를 표시하고 다음 저장에서도 AI 편집 출처를 유지해 재시도한다.
- 기준 version이 충돌하면 AI 편집을 문서에 반영하지 않고 충돌 작업으로 기록한다. (`409 Conflict`)

### 3.18 문서 변경 이력 조회 및 비교

#### 사용자 스토리

- 문서 소유자는 Markdown 문서의 version 목록과 특정 version의 본문을 조회하고 두 version을 비교할 수 있다.

#### 구현 범위

- 백엔드: version 목록·본문·diff 조회 API가 구현되어 있다.
- 프론트엔드: AI 편집 전 상태를 `localStorage`에 저장하는 코드와 변경 이력 패널이 있지만 현재 화면 및 백엔드 API와 연결되지 않았다.
- 연동 상태: 사용자가 백엔드 변경 이력과 diff를 확인하는 end-to-end 경로가 없다.

#### 제약조건

- 실제 본문이 변경될 때 변경 전후 전체 Markdown 스냅샷을 저장한다.
- version 목록은 최신 순이며 본문을 제외한 메타데이터를 반환한다.
- diff는 줄 단위 `CONTEXT`, `DELETE`, `ADD`와 이전·이후 줄 번호를 반환한다.
- diff 계산 메모리 추정치가 16MB를 초과하면 비교를 중단한다.

#### 성공 시나리오

- 편집 문서의 version 목록이나 특정 version을 요청한 경우 해당 정보를 반환한다. (`200 OK`)
- 존재하는 두 version을 요청한 경우 추가·삭제 줄과 diff hunk를 반환한다. (`200 OK`)
- 두 version의 본문이 같으면 변경 수가 0인 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- 편집 가능한 Markdown 문서가 아닌 경우 실패한다. (`400 Bad Request`)
- 문서 또는 version이 없는 경우 실패한다. (`404 Not Found`)
- diff가 너무 커서 안전하게 계산할 수 없는 경우 실패한다. (`422 Unprocessable Entity`)

### 3.19 과거 version 복원

#### 사용자 스토리

- 문서 소유자는 과거 Markdown version을 현재 문서의 새 version으로 복원할 수 있다.

#### 구현 범위

- 백엔드: 과거 Markdown version을 새 version으로 복원하는 API가 구현되어 있다.
- 프론트엔드: version 복원 기능을 제공하지 않는다.

#### 제약조건

- 기존 이력을 삭제하지 않는 비파괴 방식으로 복원한다.
- 저장된 과거 전체 Markdown 본문을 현재 편집본으로 저장한다.
- 현재 version을 검사한다.
- 복원 대상 본문이 현재 본문과 같으면 새 version을 생성하지 않는다.

#### 성공 시나리오

- 유효한 과거 version과 현재 version을 제출한 경우 과거 본문을 새 version으로 저장한다. (`200 OK`)
- 현재 본문과 같은 version을 복원한 경우 version을 변경하지 않는다. (`200 OK`)

#### 실패 시나리오

- 편집 가능한 문서가 아닌 경우 실패한다. (`400 Bad Request`)
- 문서나 과거 version이 없는 경우 실패한다. (`404 Not Found`)
- 현재 version이 일치하지 않는 경우 실패한다. (`409 Conflict`)
- 다른 사용자가 편집 잠금을 보유한 경우 실패한다. (`423 Locked`)

### 3.20 Wiki ingest

#### 사용자 스토리

- 문서 소유자는 편집 가능한 Markdown 문서를 최신 편집본으로 Wiki ingest할 수 있다.

#### 구현 범위

- 백엔드: Markdown 문서의 Wiki ingest 시작 API가 구현되어 있다.
- 프론트엔드: 처리 상태 조회는 구현되어 있지만 ingest 시작 기능은 제공하지 않는다.
- 연동 상태: 프론트엔드에서 사용자가 Wiki ingest를 시작할 수 없다.

#### 제약조건

- 파일 업로드만으로 ingest를 자동 시작하지 않는다.
- 요청 시점의 최신 편집본으로 원본 파일을 덮어쓴다.
- ingest를 시작하면 문서를 `processing` 상태로 변경하고 처리 큐에 등록한다.
- PDF 등 읽기 전용 원본은 ingest할 수 없다.
- 처리 중인 문서는 다시 ingest할 수 없다.
- 다른 사용자가 유효한 편집 잠금을 보유하면 ingest할 수 없다.
- 프론트엔드는 `uploaded` 또는 `processing` 문서가 있으면 3초마다 상태를 조회한다.

#### 성공 시나리오

- 유효한 Markdown 문서를 요청한 경우 최신 편집본을 원본으로 반영하고 처리 큐에 등록한다. (`202 Accepted`)
- 처리 중인 문서는 프론트엔드에서 진행 상태와 처리 단계를 갱신한다.

#### 실패 시나리오

- 편집 가능한 Markdown 문서가 아닌 경우 실패한다. (`400 Bad Request`)
- 문서 소유자가 아닌 경우 실패한다. (`403 Forbidden`)
- 문서가 없는 경우 실패한다. (`404 Not Found`)
- 이미 처리 중인 경우 실패한다. (`409 Conflict`)
- 다른 사용자가 편집 잠금을 보유한 경우 실패한다. (`423 Locked`)

### 3.21 문서 복제

#### 사용자 스토리

- 문서 소유자는 편집 가능한 Markdown 문서를 복제할 수 있다.

#### 구현 범위

- 백엔드: Markdown 문서 복제 API가 구현되어 있다.
- 프론트엔드: 문서 복제 기능을 제공하지 않는다.

#### 제약조건

- 최신 Markdown 편집본을 복제한다.
- 복제본은 같은 폴더의 마지막 위치에 `version 1`로 생성한다.
- 이름은 `복사본`, `복사본 (2)` 순으로 충돌하지 않게 생성한다.
- PDF 등 읽기 전용 원본은 복제할 수 없다.
- 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 복제 가능한 문서를 요청한 경우 새 ID를 가진 복제본을 생성한다. (`201 Created`)
- 같은 요청을 같은 멱등 키로 반복한 경우 기존 복제본을 반환한다. (`201 Created`)

#### 실패 시나리오

- 문서 소유자가 아니거나 편집 문서가 아닌 경우 실패한다. (`403 Forbidden`)
- 문서가 없는 경우 실패한다. (`404 Not Found`)
- 멱등 키가 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 같은 멱등 키를 다른 복제 요청에 사용한 경우 실패한다. (`409 Conflict`)

### 3.22 문서 삭제

#### 사용자 스토리

- 문서 소유자는 문서를 소프트 삭제할 수 있다.

#### 구현 범위

- 백엔드: `base_version`과 `Idempotency-Key`가 필요한 소프트 삭제 API가 구현되어 있다.
- 프론트엔드: 삭제 요청은 구현되어 있지만 요청 본문과 멱등 키를 전달하지 않는다.
- 연동 상태: 현재 프론트엔드의 문서 삭제 요청은 실패한다.

#### 제약조건

- 원본과 편집 상태는 유지하고 삭제 시각과 삭제 사용자를 기록한다.
- 삭제된 문서는 일반 목록과 문서 트리에서 제외한다.
- 문서에서 생성된 source Wiki 페이지는 소프트 삭제 대상에 포함하지 않는다.
- 현재 version과 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 소유자가 현재 version으로 요청한 경우 문서를 소프트 삭제한다. (`200 OK`)
- 같은 요청을 같은 멱등 키로 반복한 경우 기존 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- base version이나 멱등 키가 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 문서 소유자가 아닌 경우 실패한다. (`403 Forbidden`)
- 문서가 없거나 이미 삭제된 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)

### 3.23 삭제된 문서 조회

#### 사용자 스토리

- 워크스페이스 멤버는 휴지통에서 삭제된 문서 목록을 조회할 수 있다.

#### 구현 범위

- 백엔드: 삭제된 문서 목록 조회 API가 구현되어 있다.
- 프론트엔드: 문서 휴지통 기능을 제공하지 않는다.

#### 제약조건

- 워크스페이스에서 삭제된 모든 문서를 반환하며 요청한 사용자가 소유한 문서로 제한하지 않는다.
- 삭제 시각이 최신인 순서로 반환한다.

#### 성공 시나리오

- 삭제된 문서가 있으면 최근 삭제 순서로 반환한다. (`200 OK`)
- 삭제된 문서가 없으면 빈 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 참여하지 않은 워크스페이스를 조회한 경우 실패한다. (`404 Not Found`)

### 3.24 삭제된 문서 복구

#### 사용자 스토리

- 문서 소유자는 삭제된 문서를 복구할 수 있다.

#### 구현 범위

- 백엔드: 삭제된 문서 복구 API가 구현되어 있다.
- 프론트엔드: 문서 복구 기능을 제공하지 않는다.

#### 제약조건

- 복구한 문서는 문서 역할별 최상위 마지막 위치에 배치한다.
- 원래 폴더 위치로 복구하지 않는다.
- 현재 version과 유효한 `Idempotency-Key`가 필요하다.

#### 성공 시나리오

- 소유자가 삭제된 문서를 현재 version으로 요청한 경우 복구한다. (`200 OK`)
- 같은 요청을 같은 멱등 키로 반복한 경우 기존 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- base version이나 멱등 키가 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 문서 소유자가 아닌 경우 실패한다. (`403 Forbidden`)
- 삭제된 문서가 아닌 경우 실패한다. (`404 Not Found`)
- 현재 version 또는 멱등 요청이 충돌한 경우 실패한다. (`409 Conflict`)

## 4. Wiki

### 4.1 Wiki 그래프 조회

#### 사용자 스토리

- 로그인한 사용자는 워크스페이스의 Wiki 페이지와 연결 관계를 그래프로 조회할 수 있다.

#### 제약조건

- 사용자가 멤버로 참여한 워크스페이스만 조회할 수 있다.
- 워크스페이스에 속한 모든 Wiki 페이지를 상태와 관계없이 노드로 반환한다.
- 그래프 연결은 양쪽 페이지가 모두 요청한 워크스페이스에 속한 경우에만 반환한다.
- source 페이지에는 연결된 원본 문서 ID와 파일명을 포함할 수 있다.
- 연결의 confidence가 없으면 `0.0`으로 반환한다.
- 프론트엔드는 문서 목록과 Wiki 그래프를 함께 조회한다.
- 프론트엔드 그래프는 원본 문서, source Wiki, concept Wiki 노드를 함께 구성한다.

#### 성공 시나리오

- Wiki 페이지가 있는 경우 페이지 노드와 연결 edge를 반환한다. (`200 OK`)
- Wiki 페이지가 없는 경우 빈 노드와 edge 목록을 반환한다. (`200 OK`)
- 프론트엔드에서 Wiki 노드를 선택하면 해당 페이지 상세 화면을 연다.

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스를 조회한 경우 실패한다. (`404 Not Found`)

### 4.2 Wiki 페이지 상세 조회

#### 사용자 스토리

- 로그인한 사용자는 Wiki 페이지의 내용과 연결된 원본 문서 및 관련 페이지를 조회할 수 있다.

#### 제약조건

- 사용자가 멤버로 참여한 워크스페이스의 페이지만 조회할 수 있다.
- 페이지 ID, 유형, 제목, slug, 요약, Markdown, 상태와 생성·수정 시각을 반환한다.
- 연결된 원본 문서와 해당 페이지에서 나가는 관련 페이지 연결을 반환한다.
- 원본 문서나 관련 페이지 정보가 없어도 연결 ID는 반환할 수 있다.
- MinIO에서 Markdown을 읽지 못하면 Markdown을 `null`로 두고 나머지 페이지 정보는 반환한다.

#### 성공 시나리오

- 요청한 페이지가 존재하는 경우 페이지 내용과 연결 정보를 반환한다. (`200 OK`)
- Markdown 원본을 읽지 못한 경우에도 조회 가능한 메타데이터와 연결 정보를 반환한다. (`200 OK`)
- 프론트엔드는 Markdown이 있으면 렌더링하고, 없으면 요약 또는 원본 문서 정보만 표시한다.

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스를 요청한 경우 실패한다. (`404 Not Found`)
- 요청한 워크스페이스에 Wiki 페이지가 없는 경우 실패한다. (`404 Not Found`)

### 4.3 Wiki 페이지 제목 및 slug 변경

#### 사용자 스토리

- 로그인한 사용자는 Wiki 페이지 제목을 변경하고 필요한 경우 slug도 함께 변경할 수 있다.

#### 구현 범위

- 백엔드: Spring 요청 진입점과 AI 파이프라인 위임 로직이 구현되어 있다.
- 프론트엔드: 제목 및 slug 변경 기능을 제공하지 않는다.
- AI 파이프라인: 백엔드가 요청하는 Wiki 페이지 이름 변경 endpoint가 구현되어 있지 않다.
- 연동 상태: 현재 코드베이스만으로는 end-to-end로 동작하지 않는다.

#### 제약조건

- 사용자가 멤버로 참여한 워크스페이스에서만 요청할 수 있다.
- 백엔드는 사용자 ID, 워크스페이스 ID, Wiki 페이지 ID, 제목과 `update_slug` 값을 파이프라인에 전달한다.
- 제목과 `update_slug`에는 Spring 백엔드 요청 검증이 적용되어 있지 않다.
- 백엔드에서 파이프라인 응답을 기다리는 기본 제한 시간은 30초이다.

#### 성공 시나리오

- 호환되는 외부 파이프라인이 구성되어 성공 응답을 반환한 경우, 백엔드는 변경 전·후 제목과 slug 정보를 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- 파이프라인이 요청을 거절한 경우 해당 오류를 전달한다. (`400 Bad Request`, `404 Not Found`, `409 Conflict` 또는 `422 Unprocessable Entity`)
- 파이프라인 응답이 없거나 시간 초과 또는 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

### 4.4 Wiki schema 미리보기

#### 사용자 스토리

- 로그인한 사용자는 Markdown으로 작성한 Wiki schema가 어떻게 적용될지 미리 확인할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: schema 정리 및 검사 API가 구현되어 있다.
- 프론트엔드: 백엔드 API 대신 정규식 기반 목업 결과를 표시한다.
- 연동 상태: 프론트엔드 미리보기와 실제 백엔드 검사 결과가 연결되어 있지 않다.

#### 제약조건

- schema Markdown은 공백일 수 없다.
- 사용자가 멤버로 참여한 워크스페이스에서만 요청할 수 있다.
- schema를 공통, 질의, 수집, 편집, 개념, 템플릿 영역으로 정리한다.
- 상위 지시 무시, 숨겨진 prompt 요청, 정책 약화, 권한 확대, 민감정보와 역할 변경 요청을 차단 이슈로 분류한다.
- 모호한 설정은 확인 필요 이슈로 분류한다.
- 개념 생성 규칙에는 문서 근거 확인 조건을 적용한다.
- 백엔드에서 pipeline을 기다리는 기본 제한 시간은 60초이다.

#### 성공 시나리오

- 올바른 Markdown을 제출한 경우 정리된 schema 조각, 이슈와 미리보기를 반환한다. (`200 OK`)
- 차단 또는 확인 필요 이슈가 있는 경우 해당 이슈와 이유를 함께 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- Markdown이 공백인 경우 실패한다. (`400 Bad Request`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- pipeline이 요청을 거절한 경우 해당 오류를 전달한다. (`400 Bad Request` 또는 `422 Unprocessable Entity`)
- pipeline 응답이 없거나 시간 초과 또는 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

### 4.5 Wiki schema draft 저장

#### 사용자 스토리

- 로그인한 사용자는 Markdown으로 작성한 Wiki schema를 draft로 저장할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: schema draft 서버 저장이 구현되어 있다.
- 프론트엔드: schema를 `localStorage`에만 저장한다.
- 연동 상태: 프론트엔드에서 저장한 draft는 서버에 저장되지 않는다.

#### 제약조건

- schema Markdown은 공백일 수 없다.
- 이름을 생략하면 pipeline에서 `default`를 사용한다.
- 공백으로만 구성된 이름은 사용할 수 없다.
- schema는 요청한 사용자와 워크스페이스 범위로 저장한다.
- 저장할 때 schema 정리와 보안·모호성 검사를 다시 수행한다.
- 차단 이슈가 있어도 draft 저장 자체는 허용한다.
- 프론트엔드 목업은 빈 이름을 `default`로 바꾼다.
- 프론트엔드 저장소는 사용자나 워크스페이스별로 구분되지 않는다.

#### 성공 시나리오

- 올바른 Markdown과 이름을 제출한 경우 `draft` 상태의 schema를 저장한다. (`200 OK`)
- 이름을 생략한 경우 `default` 이름으로 저장한다. (`200 OK`)
- 프론트엔드 목업에서 저장한 경우 최근 schema를 목록의 앞에 추가한다.

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- Markdown이나 이름이 유효하지 않은 경우 실패한다. (`400 Bad Request`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- pipeline이 요청을 거절한 경우 해당 오류를 전달한다. (`400 Bad Request` 또는 `422 Unprocessable Entity`)
- pipeline 응답이 없거나 시간 초과 또는 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

### 4.6 Wiki schema 목록 조회

#### 사용자 스토리

- 로그인한 사용자는 자신이 저장한 Wiki schema 목록을 조회할 수 있다.

#### 구현 범위

- 프론트엔드: `localStorage`에 저장된 목업 schema 목록 조회가 구현되어 있다.
- 백엔드·AI 파이프라인: schema 목록 조회 API가 없다.

#### 제약조건

- 프론트엔드 목록은 사용자나 워크스페이스별로 구분되지 않는다.

#### 성공 시나리오

- 브라우저에 저장된 schema가 있는 경우 해당 목록을 반환한다.
- 저장된 schema가 없는 경우 빈 목록을 표시한다.

#### 실패 시나리오

- 저장된 값이 올바른 배열이 아니거나 읽을 수 없는 경우 오류를 표시하지 않고 빈 목록으로 처리한다.

### 4.7 Wiki schema 활성화

#### 사용자 스토리

- 로그인한 사용자는 저장된 Wiki schema를 활성화할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: 저장된 schema 활성화가 구현되어 있다.
- 프론트엔드: 서버 API를 호출하지 않고 `localStorage`의 상태만 변경한다.
- 연동 상태: 프론트엔드의 활성 schema와 서버의 활성 schema가 연결되어 있지 않다.

#### 제약조건

- 한 사용자와 워크스페이스 범위에서는 하나의 schema만 활성 상태로 유지한다.
- 새 schema를 활성화하면 기존 활성 schema를 `draft`로 되돌린다.
- 프론트엔드 목업은 차단 이슈가 있는 schema의 활성화를 막는다.
- 백엔드와 pipeline은 차단 이슈가 있는 schema의 활성화를 별도로 막지 않는다.
- 백엔드는 요청 URL의 워크스페이스 멤버십을 검사하지만 schema ID가 해당 워크스페이스와 사용자의 것인지 검증하지 않는다.
- pipeline은 전달받은 schema ID에 저장된 사용자와 워크스페이스 범위를 기준으로 활성화한다.

#### 성공 시나리오

- 존재하는 schema를 활성화한 경우 해당 schema를 `active`로 변경한다. (`200 OK`)
- 같은 사용자와 워크스페이스에 기존 활성 schema가 있으면 기존 schema를 `draft`로 변경한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- schema ID가 존재하지 않는 경우 실패한다. (`404 Not Found`)
- pipeline 응답이 없거나 시간 초과 또는 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

### 4.8 활성 Wiki schema 조회

#### 사용자 스토리

- 로그인한 사용자는 현재 활성화된 Wiki schema를 조회할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: 사용자·워크스페이스별 활성 schema 조회가 구현되어 있다.
- 프론트엔드: 서버 API 대신 `localStorage` 목록에서 활성 schema를 찾는다.
- 연동 상태: 프론트엔드에 표시되는 활성 schema와 서버 상태가 연결되어 있지 않다.

#### 제약조건

- 요청한 사용자와 워크스페이스에 속한 활성 schema만 조회한다.
- 활성화 시각과 수정 시각이 가장 최근인 schema 하나를 반환한다.

#### 성공 시나리오

- 활성 schema가 있는 경우 해당 schema를 반환한다. (`200 OK`)
- 활성 schema가 없는 경우 `null`을 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- pipeline 응답 시간이 초과되거나 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

### 4.9 Wiki maintenance lint 실행

#### 사용자 스토리

- 로그인한 사용자는 워크스페이스의 Wiki 상태를 검사하고 필요한 유지보수 작업을 실행할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: Wiki maintenance lint 실행이 구현되어 있다.
- 프론트엔드: Wiki maintenance lint 기능을 제공하지 않는다.

#### 제약조건

- 사용자가 멤버로 참여한 워크스페이스만 검사할 수 있다.
- 요청 본문을 생략할 수 있다.
- `dry_run`의 기본값은 `true`이고 `materialize_promotions`의 기본값은 `false`이다.
- dry run에서는 reconciliation, 로그 기록과 concept 승격을 실제 반영하지 않는다.
- `dry_run=false`이면 reconciliation을 반영하고 lint 로그를 기록한다.
- concept 승격은 `materialize_promotions=true`이면서 `dry_run=false`인 경우에만 반영한다.
- 결과에는 cluster, source ref, 고아 참조, 승격 후보, 검토 대상, relation과 reconciliation 결과를 포함한다.
- 백엔드에서 pipeline을 기다리는 기본 제한 시간은 200초이다.

#### 성공 시나리오

- 기본 요청으로 실행한 경우 변경을 적용하지 않고 Wiki 검사 결과를 반환한다. (`200 OK`)
- 적용 옵션으로 실행한 경우 가능한 reconciliation과 concept 승격을 반영하고 결과를 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 사용자가 요청한 경우 실패한다. (`401 Unauthorized`)
- 참여하지 않은 워크스페이스에서 요청한 경우 실패한다. (`404 Not Found`)
- pipeline 설정이 없거나 요청을 처리할 수 없는 경우 실패한다. (`400 Bad Request` 또는 `422 Unprocessable Entity`)
- pipeline 응답이 없거나 시간 초과 또는 서버 오류가 발생한 경우 실패한다. (`503 Service Unavailable`)

## 5. 채팅

### 5.1 채팅 세션 생성

#### 사용자 스토리

- 로그인한 사용자는 자신이 참여한 워크스페이스에서 새로운 채팅 세션을 생성할 수 있다.

#### 제약조건

- 채팅 세션은 워크스페이스와 생성한 사용자에게 귀속한다.
- 세션은 워크스페이스 멤버별로 최대 10개까지 생성할 수 있다.
- 세션 제목은 선택값이다.
- 세션 제목은 DB에서 최대 255자까지 저장할 수 있지만, 백엔드 요청 검증은 적용되어 있지 않다.
- 프론트엔드는 새 채팅을 제목 없이 생성한다.
- 프론트엔드에서 사용할 세션이 하나도 없으면 첫 채팅 이용 시 세션을 자동으로 생성한다.

#### 성공 시나리오

- 사용자가 참여한 워크스페이스에서 세션 수가 10개 미만인 경우 새로운 채팅 세션이 생성된다. (`201 Created`)

#### 실패 시나리오

- 로그인하지 않은 경우 세션 생성에 실패한다. (`401 Unauthorized`)
- 사용자가 참여하지 않은 워크스페이스인 경우 세션 생성에 실패한다. (`404 Not Found`)
- 해당 워크스페이스에서 사용자가 생성한 세션이 이미 10개인 경우 생성에 실패한다. (`409 Conflict`)

### 5.2 채팅 세션 목록 조회

#### 사용자 스토리

- 로그인한 사용자는 현재 워크스페이스에서 자신이 생성한 채팅 세션 목록을 조회할 수 있다.

#### 제약조건

- `workspace_id`와 `user_id`가 모두 일치하는 세션만 반환한다.
- 다른 워크스페이스 또는 다른 사용자의 세션은 반환하지 않는다.
- 목록은 마지막 메시지 시각의 내림차순으로 정렬한다.
- 생성 시각, 마지막 메시지 시각과 선택적으로 저장된 제목을 반환한다.

#### 성공 시나리오

- 사용자가 참여한 워크스페이스를 조회하면 자신이 생성한 세션 목록을 최근 메시지 순으로 반환한다. (`200 OK`)
- 생성한 세션이 없는 경우 빈 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 경우 세션 목록 조회에 실패한다. (`401 Unauthorized`)
- 사용자가 참여하지 않은 워크스페이스인 경우 세션 목록 조회에 실패한다. (`404 Not Found`)

### 5.3 채팅 세션 검색

#### 사용자 스토리

- 로그인한 사용자는 현재 불러온 채팅 세션을 제목으로 검색할 수 있다.

#### 구현 범위

- 프론트엔드: 현재 불러온 세션 목록을 제목으로 필터링하는 검색이 구현되어 있다.
- 백엔드: 별도의 채팅 세션 검색 API는 없다.

#### 제약조건

- 검색 전후 공백과 영문 대소문자를 구분하지 않는다.
- 제목이 없는 세션은 `새 채팅`으로 검색한다.

#### 성공 시나리오

- 검색어가 세션 제목에 포함된 경우 일치하는 세션만 표시한다.
- 일치하는 세션이 없는 경우 세션이 없다는 안내를 표시한다.

#### 실패 시나리오

- 세션 목록을 불러오지 못한 경우 검색 대신 목록 조회 오류를 표시한다.

### 5.4 채팅 세션 전환

#### 사용자 스토리

- 로그인한 사용자는 자신의 다른 채팅 세션으로 전환할 수 있다.

#### 구현 범위

- 프론트엔드: 활성 세션 ID를 변경하는 세션 전환이 구현되어 있다.
- 백엔드: 세션 전환 상태를 저장하는 별도의 API는 없으며 이후 요청의 세션 ID로 대상을 구분한다.

#### 제약조건

- 전환한 세션은 이후 메시지 조회, AI 질의와 Wiki 편입의 대상이 된다.
- 세션을 전환하면 이전 세션에서 선택한 부분 편입 문답을 초기화한다.

#### 성공 시나리오

- 사용자가 세션을 선택하면 해당 세션의 메시지 기록으로 화면이 교체된다.

#### 실패 시나리오

- 선택한 세션의 메시지를 불러오지 못한 경우 채팅 기록 조회 오류를 표시한다.
- 다른 사용자의 세션이거나 현재 워크스페이스에 속하지 않은 세션인 경우 기록 조회에 실패한다. (`404 Not Found`)

### 5.5 채팅 메시지 기록 조회

#### 사용자 스토리

- 로그인한 사용자는 자신의 채팅 세션에 저장된 메시지 기록을 조회할 수 있다.

#### 제약조건

- `session_id`, `workspace_id`, `user_id`가 모두 일치하는 세션만 조회할 수 있다.
- 메시지는 생성 시각의 오름차순으로 반환한다.
- 메시지에는 문답 식별자, 역할, 내용, 상태와 생성 시각을 포함한다.
- 저장된 경우 관련 Wiki 페이지, 원본 문서 근거, 전체·부분 편입 Wiki 페이지와 오류 메시지를 함께 반환한다.

#### 성공 시나리오

- 사용자가 소유한 세션을 조회하면 저장된 메시지를 생성 순서대로 반환한다. (`200 OK`)
- 메시지가 없는 세션은 빈 메시지 목록을 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 경우 메시지 기록 조회에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 조회에 실패한다. (`404 Not Found`)

### 5.6 채팅 세션 삭제

#### 사용자 스토리

- 로그인한 사용자는 자신이 생성한 채팅 세션을 삭제할 수 있다.

#### 제약조건

- 현재 프론트엔드에서는 활성화된 세션에 대해서만 삭제 메뉴를 표시한다.
- 세션 삭제 시 소속 메시지, 메시지 근거, 관련 페이지와 부분 편입 연결 정보도 함께 삭제한다.
- 세션에서 이미 생성된 export 문서와 Wiki 페이지는 삭제하지 않는다.
- 프론트엔드는 삭제 후 남은 세션 중 첫 번째 세션으로 전환한다.
- 남은 세션이 없으면 새로운 세션을 자동으로 생성한다.

#### 성공 시나리오

- 사용자가 자신이 생성한 세션을 삭제하면 세션과 소속 채팅 데이터가 삭제된다. (`204 No Content`)

#### 실패 시나리오

- 로그인하지 않은 경우 세션 삭제에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 삭제에 실패한다. (`404 Not Found`)

### 5.7 채팅 Wiki 편입 미리보기

#### 사용자 스토리

- 로그인한 사용자는 채팅을 Wiki에 편입하기 전에 생성될 Markdown을 미리 확인할 수 있다.

#### 제약조건

- 사용자가 소유한 채팅 세션만 미리 볼 수 있다.
- `completed` 상태인 사용자 질문과 AI 답변이 모두 존재하는 완전한 문답만 포함한다.
- 문답은 원래 대화 순서대로 직렬화한다.
- credential, token, private key 등 확인 가능한 비밀값 패턴은 `[REDACTED]`로 마스킹한다.
- 마스킹은 정규식 기반의 best-effort 처리이므로 모든 민감정보 차단을 보장하지 않는다.
- 미리보기는 문서를 저장하거나 파이프라인을 실행하지 않는다.
- 현재 미리보기 API는 부분 선택 정보를 받지 않으므로, 부분 편입 문답을 선택해도 전체 세션을 미리보기로 표시한다.

#### 성공 시나리오

- 사용자가 소유한 세션을 미리 보면 전체 세션의 완전한 문답으로 생성한 Markdown을 반환한다. (`200 OK`)
- 완전한 문답이 없는 경우 제목만 포함된 빈 Markdown을 반환한다. (`200 OK`)

#### 실패 시나리오

- 로그인하지 않은 경우 미리보기에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 미리보기에 실패한다. (`404 Not Found`)

### 5.8 채팅 전체 Wiki 편입

#### 사용자 스토리

- 로그인한 사용자는 채팅 세션의 전체 문답을 하나의 원본 문서로 만들어 Wiki pipeline에 편입할 수 있다.

#### 제약조건

- 사용자가 소유한 채팅 세션만 편입할 수 있다.
- 전체 편입은 `selection_mode`에 `full`을 사용한다.
- `completed` 상태인 사용자 질문과 AI 답변이 모두 존재하는 문답만 포함한다.
- 이미 전체 Wiki에 편입된 문답은 다시 포함하지 않는다.
- 저장 전 확인 가능한 비밀값 패턴을 마스킹한다.
- 같은 워크스페이스에 동일한 content hash의 문서가 있으면 새 문서를 생성하지 않는다.
- content hash에는 세션 ID와 완료된 메시지의 역할·내용을 사용하며 `pair_id`는 포함하지 않는다.
- API의 성공 응답은 비동기 처리 접수를 의미하며 Wiki 생성 완료를 의미하지 않는다.

#### 시스템 조건

- 최초 전체 편입 문서는 세션의 정식 export 문서로 연결한다.
- pipeline 처리가 완료되면 편입된 문답과 생성된 Wiki 페이지를 세션에 연결한다.

#### 성공 시나리오

- 유효한 전체 편입 요청은 문서를 저장하고 Wiki pipeline 처리 대상으로 등록한다. (`202 Accepted`, `processing`)
- 동일한 내용의 문서가 이미 존재하면 기존 문서 ID를 반환하고 새 문서를 생성하지 않는다. (`202 Accepted`, `skipped`)

#### 실패 시나리오

- `selection_mode`가 없거나 `full`, `partial` 이외의 값인 경우 편입에 실패한다. (`400 Bad Request`)
- 편입할 완전한 문답이 없는 경우 편입에 실패한다. (`400 Bad Request`)
- 로그인하지 않은 경우 편입에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 편입에 실패한다. (`404 Not Found`)

### 5.9 채팅 부분 Wiki 편입

#### 사용자 스토리

- 로그인한 사용자는 원하는 질문·답변 문답을 선택해 독립된 원본 문서로 Wiki pipeline에 편입할 수 있다.

#### 제약조건

- 사용자가 소유한 채팅 세션만 부분 편입할 수 있다.
- 부분 편입은 `selection_mode`에 `partial`을 사용하고 하나 이상의 `pair_ids`를 전달해야 한다.
- 선택한 문답 중 `completed` 상태인 사용자 질문과 AI 답변이 모두 존재하는 문답만 포함한다.
- 이미 전체 Wiki에 편입된 문답도 별도의 부분 Wiki로 다시 편입할 수 있다.
- 부분 편입은 세션의 정식 전체 export 문서 연결을 변경하지 않는다.
- API의 성공 응답은 비동기 처리 접수를 의미하며 Wiki 생성 완료를 의미하지 않는다.

#### 시스템 조건

- pipeline 처리가 완료되면 선택한 문답과 독립적으로 생성된 Wiki 페이지의 연결 정보를 기록한다.

#### 성공 시나리오

- 하나 이상의 완전한 문답을 선택하면 독립된 문서를 저장하고 Wiki pipeline 처리 대상으로 등록한다. (`202 Accepted`, `processing`)
- 동일한 내용의 부분 편입 문서가 이미 존재하면 기존 문서 ID를 반환한다. (`202 Accepted`, `skipped`)

#### 실패 시나리오

- `pair_ids`가 없거나 비어 있는 경우 부분 편입에 실패한다. (`400 Bad Request`)
- 선택한 ID에 완전한 문답이 없는 경우 부분 편입에 실패한다. (`400 Bad Request`)
- 로그인하지 않은 경우 부분 편입에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 부분 편입에 실패한다. (`404 Not Found`)

### 5.10 채팅 전체 Wiki 편입 갱신

#### 사용자 스토리

- 로그인한 사용자는 전체 편입을 완료한 채팅 세션에 새 문답이 추가되면 기존 export 문서를 갱신할 수 있다.

#### 제약조건

- 세션에 전체 export 문서와 Wiki 페이지가 모두 연결된 경우에만 기존 문서를 재사용한다.
- 기존 export 문서의 원본 Markdown은 세션의 전체 완전한 문답으로 갱신한다.
- pipeline에는 아직 전체 편입되지 않은 새로운 완전한 문답만 전달한다.
- 부분 편입된 문답은 전체 편입 여부를 변경하지 않으므로 이후 전체 편입 대상이 될 수 있다.
- 갱신 요청의 성공 응답은 비동기 처리 접수를 의미한다.

#### 시스템 조건

- Wiki pipeline은 기존 source 페이지의 내용과 새로운 문답을 대조해 내용을 누적한다.
- 처리 완료 후 새로 편입된 문답을 해당 Wiki 페이지에 연결한다.

#### 성공 시나리오

- 전체 편입 이후 새로운 완전한 문답이 존재하면 기존 export 문서를 재사용해 갱신하고 pipeline에 등록한다. (`202 Accepted`, `processing`)

#### 실패 시나리오

- 새로 전체 편입할 완전한 문답이 없는 경우 갱신에 실패한다. (`400 Bad Request`)
- 로그인하지 않은 경우 갱신에 실패한다. (`401 Unauthorized`)
- 세션이 없거나 현재 사용자와 워크스페이스에 속하지 않은 경우 갱신에 실패한다. (`404 Not Found`)

## 6. AI 질의

### 6.1 동기 AI 질의 실행

#### 사용자 스토리

- 로그인한 사용자는 자신의 채팅 세션에서 자연어로 AI 질의를 실행하고 결과를 즉시 받을 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: 동기 AI 질의 실행 경로가 구현되어 있다.
- 프론트엔드: 동기 질의 API를 사용하지 않고 비동기 질의만 사용한다.

#### 제약조건

- 사용자가 참여한 워크스페이스에 속하며 자신이 생성한 채팅 세션에서만 질의를 실행할 수 있다.
- 질문은 공백이 아닌 값을 포함해야 한다.
- 질문의 최대 길이 제한은 적용되어 있지 않다.
- pipeline에는 `workspace_id`와 질문을 전달한다.
- 이전 채팅 내용, 세션 요약, 사용자 ID와 참조 문맥은 pipeline에 전달하지 않는다.
- pipeline HTTP 연결 timeout은 5초이며 읽기 timeout 기본값은 30초이다.

#### 시스템 조건

- pipeline 호출 전에 사용자 질문은 `completed`, AI 답변은 `pending` 상태로 저장한다.
- 사용자 질문과 AI 답변에는 동일한 문답 식별자를 부여한다.
- 질의 성공 시 AI 답변을 `completed` 상태로 저장한다.
- 관련 Wiki 페이지와 원본 block 근거를 AI 답변 메시지에 연결한다.
- 질의 성공 시 채팅 세션의 마지막 메시지 시각을 갱신한다.
- 질의 실패 시 AI 답변을 `failed` 상태로 변경하고 오류 내용을 저장한다.

#### 성공 시나리오

- 유효한 질문을 전송하면 사용자 질문, AI 답변, 관련 Wiki 페이지, 원본 근거, 그래프 문맥과 탐색 경로를 반환한다. (`200 OK`)

#### 실패 시나리오

- 질문이 없거나 공백인 경우 질의 실행에 실패한다. (`400 Bad Request`)
- 로그인하지 않은 경우 질의 실행에 실패한다. (`401 Unauthorized`)
- 사용자가 참여하지 않은 워크스페이스이거나 자신의 세션이 아닌 경우 질의 실행에 실패한다. (`404 Not Found`)
- pipeline이 요청을 거부한 경우 질의 실행에 실패한다. (`502 Bad Gateway`)
- pipeline 연결이 불가능하거나 timeout이 발생한 경우 질의 실행에 실패한다. (`503 Service Unavailable`)
- pipeline 또는 내부 처리에 실패한 경우 선저장한 AI 답변을 `failed` 상태로 변경한다.

### 6.2 비동기 AI 질의 시작

#### 사용자 스토리

- 로그인한 사용자는 자신의 채팅 세션에서 AI 질의를 비동기로 시작할 수 있다.

#### 제약조건

- 동기 질의와 동일한 질문 및 채팅 세션 소유권 제약을 적용한다.
- 비동기 질의 정보는 DB가 아닌 애플리케이션 메모리에 저장한다.
- 각 질의에는 `query_`로 시작하는 고유한 `request_id`를 부여한다.
- 최초 상태는 `pending`이다.
- pipeline에는 `workspace_id`, 질문, `request_id`와 진행 이벤트 callback URL을 전달한다.
- 현재 프론트엔드는 비동기 질의 API를 사용한다.
- 프론트엔드는 질문의 앞뒤 공백을 제거하고 빈 질문은 전송하지 않는다.
- 프론트엔드는 질의 처리 중 추가 질의 전송을 차단한다.

#### 시스템 조건

- 비동기 실행을 예약하기 전에 사용자 질문과 `pending` 상태의 AI 답변을 먼저 저장한다.
- 백그라운드 실행이 시작되면 run을 `running` 상태로 변경한다.
- pipeline 처리에 성공하면 결과를 저장하고 run을 `completed` 상태로 변경한다.
- pipeline 또는 내부 처리에 실패하면 run과 AI 답변을 `failed` 상태로 변경한다.

#### 성공 시나리오

- 유효한 비동기 질의를 시작하면 `request_id`와 `pending` 상태를 반환한다. (`202 Accepted`)

#### 실패 시나리오

- 질문이 없거나 공백인 경우 비동기 질의 시작에 실패한다. (`400 Bad Request`)
- 로그인하지 않은 경우 비동기 질의 시작에 실패한다. (`401 Unauthorized`)
- 사용자가 참여하지 않은 워크스페이스이거나 자신의 세션이 아닌 경우 비동기 질의 시작에 실패한다. (`404 Not Found`)
- 비동기 실행이 접수된 이후 pipeline 처리에 실패하면 run과 AI 답변을 `failed` 상태로 변경한다.

### 6.3 비동기 질의 진행 이벤트 구독

#### 사용자 스토리

- 사용자는 비동기 AI 질의의 진행 이벤트를 실시간으로 구독할 수 있다.

#### 제약조건

- 진행 이벤트는 `request_id`별 SSE로 제공한다.
- pipeline이 전달한 진행 단계는 `query.log` 이벤트로 중계한다.
- 진행 이벤트에는 단계, 메시지, 데이터, 순번과 백엔드 수신 시각을 포함한다.
- 질의 완료 시 `query.completed`, 실패 시 `query.failed` 이벤트를 전달하고 SSE 연결을 종료한다.
- 늦게 구독한 요청에 전달하기 위해 run별로 최근 이벤트를 최대 200개까지 메모리에 보관한다.
- SSE 연결에는 자체 timeout을 적용하지 않으며 15초마다 heartbeat를 전송한다.
- 현재 SSE 구독 API와 pipeline callback API에는 인증 및 사용자·세션 소유권 검증이 적용되어 있지 않다.
- callback 요청 body의 필드에는 별도의 입력 검증이 적용되어 있지 않다.
- 따라서 `request_id`를 알고 있으면 다른 사용자의 진행 이벤트를 구독하거나 임의의 진행 이벤트를 전달할 수 있다.
- 프론트엔드는 Authorization 헤더를 포함할 수 있도록 `EventSource` 대신 fetch stream으로 SSE를 구독한다.
- 프론트엔드는 heartbeat를 무시하고 `query.log` 이벤트의 단계와 메시지를 진행 상태로 표시한다.
- SSE 연결이 완료 이벤트 전에 종료돼도 프론트엔드는 자동으로 재연결하지 않는다.

#### 성공 시나리오

- 존재하는 `request_id`로 구독하면 버퍼에 저장된 이벤트와 이후 발생하는 진행 이벤트를 전달한다.
- 질의가 완료되면 `query.completed` 이벤트를 전달한다.
- 질의가 실패하면 오류 내용을 포함한 `query.failed` 이벤트를 전달한다.
- pipeline callback 이벤트를 정상적으로 수신하면 SSE 구독자에게 전달한다. (`200 OK`)
- 프론트엔드는 수신한 `query.log` 이벤트를 질의 진행 단계로 표시한다.

#### 실패 시나리오

- 존재하지 않거나 정리된 `request_id`로 구독하면 실패한다. (`404 Not Found`)
- 존재하지 않는 `request_id`로 callback 이벤트를 전달하면 실패한다. (`404 Not Found`)

### 6.4 비동기 질의 상태 및 결과 조회

#### 사용자 스토리

- 사용자는 `request_id`로 비동기 AI 질의의 상태와 최종 결과를 조회할 수 있다.

#### 제약조건

- 질의 상태는 `pending`, `running`, `completed`, `failed` 중 하나이다.
- `completed` 상태에는 AI 질의 결과를 포함한다.
- `failed` 상태에는 오류 내용을 포함한다.
- run 정보는 애플리케이션 메모리에만 저장되므로 서버 재시작 시 사라진다.
- 완료되거나 실패한 run은 종료 후 10분이 지나면 정리 대상이 된다.
- 종료되지 않은 run이 생성 후 5분을 초과하면 `failed` 상태로 변경한다.
- timeout 및 만료 검사는 60초 간격으로 수행한다.
- 현재 상태 및 결과 조회 API에는 인증과 사용자·세션 소유권 검증이 적용되어 있지 않다.
- 따라서 `request_id`를 알고 있으면 다른 사용자의 질의 상태와 결과를 조회할 수 있다.
- 프론트엔드는 `query.completed` 이벤트를 받은 후 상태 조회 API에서 최종 결과를 가져온다.
- 프론트엔드는 최종 결과가 없으면 일반 질의 오류로 처리한다.
- 최종 결과를 받은 후에는 채팅 메시지 기록을 다시 조회해 저장된 AI 답변과 근거를 표시한다.

#### 성공 시나리오

- 존재하는 `request_id`를 조회하면 현재 상태를 반환한다. (`200 OK`)
- 완료된 질의를 조회하면 사용자 질문, AI 답변, 관련 Wiki 페이지, 원본 근거, 그래프 문맥과 탐색 경로를 반환한다. (`200 OK`)
- 실패한 질의를 조회하면 `failed` 상태와 오류 내용을 반환한다. (`200 OK`)
- 프론트엔드는 완료된 질의의 저장된 AI 답변과 근거를 채팅 메시지 기록에서 다시 불러온다.

#### 실패 시나리오

- 존재하지 않거나 정리된 `request_id`를 조회하면 실패한다. (`404 Not Found`)
- 서버가 재시작되어 메모리의 run 정보가 사라진 경우 조회에 실패한다. (`404 Not Found`)
- 질의가 5분 이상 종료되지 않으면 timeout 오류와 함께 `failed` 상태로 변경한다.

### 6.5 관련 Wiki 페이지 확인

#### 사용자 스토리

- 사용자는 AI 답변과 관련된 Wiki 페이지 정보를 확인할 수 있다.

#### 제약조건

- 관련 페이지에는 페이지 ID, 페이지 유형, 제목, slug, 관련도 점수, 역할과 탐색 깊이를 포함한다.
- pipeline이 반환한 관련 페이지를 순서대로 모두 질의 결과에 포함한다.
- 관련 페이지는 AI 답변 메시지와 함께 DB에 저장한다.
- 저장 시 pipeline 반환 순서에 따라 1부터 시작하는 순위를 부여한다.
- 관련 페이지 목록이 없는 경우 빈 목록을 반환하고 저장하지 않는다.
- 프론트엔드는 현재 워크스페이스 그래프에서 확인되는 관련 페이지를 최대 3개까지 표시한다.
- 관련 페이지 목록 자체가 비어 있으면 원본 문서 근거와 연결되는 source 페이지를 대신 표시할 수 있다.
- 관련 페이지 목록은 있지만 현재 그래프에서 확인되는 페이지가 없으면 대체 source 페이지를 표시하지 않는다.

#### 성공 시나리오

- pipeline이 관련 페이지를 반환하면 질의 결과에 포함하고 AI 답변 메시지에 연결해 저장한다.
- 채팅 메시지 기록을 다시 조회하면 저장된 관련 페이지 정보를 AI 답변과 함께 반환한다.
- 프론트엔드에서 관련 페이지 카드를 선택하면 해당 Wiki 페이지 상세 내용을 연다.

#### 실패 시나리오

- pipeline이 관련 페이지를 반환하지 않은 경우 빈 관련 페이지 목록으로 처리한다.

### 6.6 원본 문서 및 block 근거 확인

#### 사용자 스토리

- 사용자는 AI 답변에 사용된 원본 문서와 block 근거를 확인할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: 대표 문서·block과 여러 문서의 `source_refs`를 반환한다.
- 프론트엔드: 대표 문서와 block 근거는 표시하지만 `source_refs`는 응답 모델과 UI에서 사용하지 않는다.
- 연동 상태: 대표 근거 확인은 동작하지만 여러 문서로 구성된 근거는 프론트엔드에서 확인할 수 없다.

#### 제약조건

- 근거에는 순위, 대표 원본 문서 ID, block ID 목록, 구조화된 원본 참조 목록과 근거 본문을 포함한다.
- 구조화된 원본 참조는 여러 문서의 `source_document_id`와 `source_block_id`를 함께 보존할 수 있다.
- pipeline이 반환한 근거 목록은 질의 결과에 포함한다.
- 대표 원본 문서 ID와 공백이 아닌 근거 본문이 존재하는 근거만 AI 답변 메시지에 저장한다.
- 저장되는 근거 유형은 `source_block`이다.
- 근거 목록이 없는 경우 빈 목록으로 처리한다.
- 프론트엔드는 답변에 citation rank가 있고 같은 rank의 대표 문서 ID와 block ID가 모두 존재하는 경우에만 citation 선택을 허용한다.
- citation을 선택하면 대표 원본 문서를 열고 해당 block을 강조한다.

#### 성공 시나리오

- pipeline이 유효한 근거를 반환하면 질의 결과에 포함하고 AI 답변 메시지에 연결해 저장한다.
- 여러 문서를 참조하는 근거는 구조화된 원본 참조 목록을 유지한다.
- 채팅 메시지 기록을 다시 조회하면 저장된 원본 문서 및 block 근거를 AI 답변과 함께 반환한다.
- 프론트엔드에서 유효한 citation을 선택하면 대표 원본 문서의 관련 block을 확인할 수 있다.

#### 실패 시나리오

- 대표 원본 문서 ID가 없거나 근거 본문이 비어 있는 근거는 채팅 메시지에 저장하지 않는다.
- pipeline이 근거를 반환하지 않은 경우 빈 근거 목록으로 처리한다.

### 6.7 그래프 문맥 및 탐색 경로 확인

#### 사용자 스토리

- 사용자는 AI 답변을 생성할 때 사용한 Wiki 그래프 문맥과 탐색 경로를 확인할 수 있다.

#### 구현 범위

- 백엔드·AI 파이프라인: 그래프 문맥과 탐색 경로를 질의 결과로 반환한다.
- 프론트엔드: 해당 응답 필드를 모델링하거나 UI에 노출하지 않는다.
- 연동 상태: 사용자는 현재 프론트엔드에서 그래프 문맥과 탐색 경로를 확인할 수 없다.

#### 제약조건

- 그래프 문맥에는 관련 페이지 node와 page 사이의 edge를 포함한다.
- edge에는 시작 페이지 ID, 도착 페이지 ID, link 유형, 역할과 점수를 포함한다.
- 탐색 경로에는 경로 ID, 역할, 답변 사용 여부, 점수, 종료 이유, node 목록과 edge 목록을 포함한다.
- pipeline이 반환한 그래프 문맥과 탐색 경로를 동기 질의 응답 및 완료된 비동기 질의 결과에 포함한다.
- 그래프 문맥과 탐색 경로는 채팅 메시지 DB에 별도로 저장하지 않는다.
- 완료된 비동기 질의의 그래프 정보는 run이 메모리에서 유지되는 동안에만 다시 조회할 수 있다.
- 탐색 경로가 없는 경우 빈 목록을 반환할 수 있다.

#### 성공 시나리오

- pipeline이 그래프 문맥과 탐색 경로를 반환하면 질의 결과에 포함한다.
- 완료된 비동기 질의는 상태 조회 API를 통해 그래프 문맥과 탐색 경로를 반환한다. (`200 OK`)
- 탐색 경로가 없는 경우 빈 경로 목록을 포함한 질의 결과를 반환한다.

#### 실패 시나리오

- 완료된 비동기 run이 만료되거나 서버가 재시작되면 저장되지 않은 그래프 문맥과 탐색 경로를 다시 조회할 수 없다.

## 7. 활동 로그와 시점 복구

### 7.1 활동 목록 조회

#### 사용자 스토리

- 사용자는 워크스페이스에서 수행된 활동 목록을 시간순으로 조회할 수 있다.

#### 구현 범위

- 프론트엔드: 로그 메뉴에 고정된 활동 7개를 표시하는 목업 화면이 구현되어 있다.
- Spring 백엔드: 통합 활동 목록을 제공하는 API와 데이터 모델이 없다.
- AI 파이프라인: 개별 pipeline run의 상태와 로그를 `run_id`로 조회할 수 있지만 워크스페이스 활동 목록은 제공하지 않는다.
- 연동 상태: 프론트엔드 로그 화면은 백엔드 또는 AI 파이프라인의 실제 데이터와 연결되어 있지 않다.

#### 제약조건

- 프론트엔드 목업은 작업명, 대상, 상대 시각과 성공·실패·정보 상태를 표시한다.
- 목업 활동은 코드에 고정되어 있으며 현재 사용자나 워크스페이스에 따라 달라지지 않는다.
- 표시 순서와 상대 시각도 실제 수행 시각을 기준으로 계산하지 않는다.

#### 성공 시나리오

- 사용자가 로그 메뉴를 선택하면 고정된 활동 7개를 표시한다.

#### 실패 시나리오

#### 구현 범위

- 연동 상태: 프론트엔드에 표시되는 대상은 실제 변경 데이터와 연결되어 있지 않다.

#### 제약조건

- 활동을 선택해 여러 문서·Wiki 페이지·block·link·embedding 변경을 상세 조회할 수 없다.

#### 성공 시나리오

- 로그 목업에서 각 활동에 지정된 대상 문자열을 표시한다.
