# 2026-07-03 이슈

## PK ID 생성 시 UUID 8자리 truncate로 인한 충돌 위험

### 배경

`feature/user-workspace-auth` 브랜치 커밋을 하나씩 리뷰하던 중 `User`/`Workspace`/`ChatSession`/`Document`의 ID 생성 방식을 확인했다.

```java
String userId = "user_" + UUID.randomUUID().toString().replace("-", "").substring(0, 8);
```

`UUID.randomUUID()`는 122비트 무작위성을 가지지만, 앞 8자리 hex만 잘라 쓰면 **32비트(2^32 ≈ 43억 개)로 줄어든다.**

### 문제점

생일 역설(birthday paradox) 기준으로,
- 같은 종류 ID가 약 **6~7만 개** 쌓이면 충돌 확률이 50%를 넘는다.
- 약 **9천 개**만 쌓여도 충돌 확률이 1% 수준이다.

ID 컬럼이 `@Id`(PK)라 충돌 시 DB unique 제약 위반으로 `save()`가 예외를 던진다. 데이터가 조용히 깨지진 않지만, 사용자 입장에선 재현 안 되는 500 에러로 회원가입/워크스페이스 생성/문서 업로드/채팅 세션 생성이 가끔 실패하는 것처럼 보인다.

로컬 데모/MVP 단계는 데이터가 몇백~몇천 건 수준이라 당장 터질 확률은 낮지만, 사용자가 늘어나면 언제 터질지 예측 불가능한 잠재 버그다.

### 영향 범위

동일 패턴(`prefix_` + UUID 앞 8자)을 쓰는 곳:

| 파일 | ID prefix |
|---|---|
| `user/service/UserService.java` | `user_` |
| `user/service/OAuthUserService.java` | `user_` |
| `workspace/service/WorkspaceService.java` | `ws_` |
| `chat/service/ChatSessionService.java` | `session_` |
| `document/service/DocumentService.java` | `doc_` |

**영향 없음**(이미 전체 UUID 사용, 안전): `QueryService`의 `chat_user_`/`chat_assistant_` 메시지 ID, `QueryRunStore`의 `query_` request ID.

### 해결 방향 (다음 단계에서 진행)

전체 UUID를 그대로 사용하는 방식으로 통일한다. 검토한 옵션과 결론:

1. **자르는 길이만 늘리기** (예: 12~16자) — 간단하지만 근본 해결은 아님. 채택 안 함.
2. **전체 UUID 사용** — 122비트 무작위성 유지, 50% 충돌 확률 도달에 약 2^61(230경) 개 필요해 사실상 안전. ID가 길어지는 트레이드오프(`user_a1b2c3d4` → `user_a1b2c3d4e5f67890abcdef1234567890`)가 있지만, PostgreSQL은 클러스터드 인덱스가 아니라서 인덱스 지역성 저하도 이 프로젝트 규모에선 무시 가능. **채택.**
3. **저장 시 충돌 감지 후 재시도** — 짧은 ID 유지 가능하지만 구현 복잡도 대비 이득이 적음. 채택 안 함.

### 참고

- 이 이슈는 커밋 리뷰 중 발견됐고, 즉시 수정하지 않고 기록만 남긴 상태다. 수정 시 위 5개 파일과 관련 테스트(ID 형식을 검증하는 `startsWith("user_")` 등 assertion)를 함께 확인해야 한다.

## 회원가입 시 기본 워크스페이스 생성 실패 → 유저 생성도 롤백되는 게 맞는가

### 배경

`UserService.signup()`은 `@Transactional`이고, 그 안에서 `WorkspaceService.createDefault()`(역시 `@Transactional`, 같은 트랜잭션에 참여)를 호출한다. 워크스페이스 생성이 실패하면 트랜잭션 전체가 롤백되어 **유저 row도 함께 사라진다.**

커밋 리뷰 중 "유저 생성은 워크스페이스 생성과 별개로 성공해야 하지 않냐"는 질문이 나와서 트레이드오프를 정리한다.

### 현재 방식(원자적 롤백)을 선택한 이유

- 이 앱은 workspace_id 없이는 문서 업로드, 채팅 등 아무 기능도 쓸 수 없다. workspace는 부가 기능이 아니라 **계정이 쓸모 있으려면 반드시 있어야 하는 전제조건**이다.
- 로그인 후 "workspace가 0개면 자동 생성"하는 복구 폴백이 코드에 전혀 없다. `WorkspaceService.list()`는 있는 것만 그대로 보여준다.
- 트랜잭션을 분리하면: workspace 생성 실패 시 유저는 남지만 workspace가 없는 상태가 되는데, 이메일은 이미 `existsByEmail`에 걸려 재가입도 안 되고, 로그인은 되는데 아무것도 못 하는 상태로 영구히 갇힌다. 즉 "가입 자체가 막힘"보다 "가입은 됐는데 계정이 고장남"이 사용자 입장에서 더 나쁜 실패 모드가 될 수 있다.

### 트랜잭션을 분리하려면 필요한 전제조건

1. 로그인/워크스페이스 목록 조회 시 "workspace 0개면 자동 생성" 폴백, 또는
2. 워크스페이스 없는 유저를 감지해서 복구시키는 별도 운영 로직

둘 중 하나 없이 트랜잭션만 분리하는 것은 권장하지 않는다.

### 실제 실패 빈도

워크스페이스 생성이 실패하는 원인은 사실상 두 가지뿐이다.
1. DB 자체 장애 — 이 경우 유저 insert도 같이 실패하므로 트랜잭션 분리 여부가 무의미하다.
2. **위 "PK ID 충돌" 이슈** (workspace_id 8자리 UUID 충돌) — 이건 해당 이슈를 전체 UUID로 고치면 사실상 사라지는 케이스다.

### 결론

지금 당장은 원자적 롤백 유지. PK ID 충돌 이슈를 먼저 해결하면 이 시나리오 자체의 발생 빈도가 크게 줄어든다. 트랜잭션 분리는 자동 복구 폴백을 함께 설계할 때 재검토한다.

## workspace_id FK CASCADE — chat_sessions는 완료, documents/wiki_pages는 보류

### 배경

`WorkspaceService.delete()`가 하위 리소스를 애플리케이션 코드로 직접 정리하던 걸 DB FK `ON DELETE CASCADE`로 바꾸는 논의를 했다. 정리하면서 두 그룹으로 나뉘었다.

### 완료: chat_sessions → chat_messages → (references/related_pages)

전부 Spring 전용 테이블이라 llmPipeline과 얽힐 일이 없다. `@ManyToOne` + `@OnDelete(action = OnDeleteAction.CASCADE)`로 전환 완료 (`docs/changelog/backend.md` 2026-07-03 "refactor: chat_sessions 하위 리소스 삭제를 DB FK ON DELETE CASCADE로 전환" 참고). Flyway 없이 `ddl-auto=update`만으로 처리했다.

### 보류: documents/wiki_pages → workspaces

`documents`, `wiki_pages` 테이블의 실제 `CREATE TABLE` DDL은 llmPipeline(Python)이 `postgres_wiki_ingestion_repository.py`의 `init_db()`에서 소유하고 있다 (`docs/backlog/issue-2026-07-02.md` 참고). `workspaces` 테이블 자체를 llmPipeline이 모르기 때문에, `workspace_id` FK를 안전하게 걸려면:

1. Flyway 같은 버전 관리되는 마이그레이션 도구 도입 (지금은 없음, `ddl-auto=update`는 기존 테이블에 FK 제약을 안정적으로 추가하지 못함)
2. llmPipeline의 `init_db()`와 Spring 스키마 관리 사이의 실행 순서/소유권 조율

이 두 가지가 Wiki workspace 연동 이슈와 겹치는 지점이라, 별도로 진행하지 않고 그 작업과 함께 다루기로 했다. 지금은 `WorkspaceService.delete()`가 `DocumentService.deleteAllByWorkspaceId()`를 애플리케이션 레벨에서 호출하는 방식을 유지한다.

## OAuth 로그인 후 code 교환 — 프론트엔드에서 구현해야 할 부분

### 배경

Google OAuth 로그인 흐름을 실제로 검증하는 과정에서, 백엔드가 발급한 1회용 `code`를 access/refresh token으로 바꾸는 마지막 단계는 프론트엔드가 없어서 실행되지 않는다는 게 확인됐다. 백엔드 쪽 흐름(`users`/`workspaces`/`user_oauth_accounts` 저장, `code` 발급)은 코드 검토와 실제 리다이렉트 확인으로 검증됐지만, `user_refresh_tokens` insert가 일어나는 마지막 단계는 프론트엔드 구현 없이는 끝까지 확인할 수 없다.

### 프론트엔드가 해야 할 일

1. **`/oauth/callback` 라우트 추가** — `app.oauth.frontend-redirect-uri` 기본값(`http://localhost:3000/oauth/callback`)과 경로가 일치해야 한다. Google 로그인 성공 시 백엔드(`OAuth2AuthenticationSuccessHandler`)가 이 경로로 `?code=...`를 붙여 리다이렉트한다.
2. **URL에서 `code` 쿼리 파라미터 읽기**
3. **`POST /api/auth/oauth/exchange` 호출** — 요청 본문 `{ "code": "..." }`. 이 호출이 일어나야 서버에서 `user_refresh_tokens` insert가 실행된다.
4. **응답으로 받은 토큰 저장** — `access_token`/`refresh_token`/`token_type`/`expires_in`(`AuthController.java`의 `LoginResponse`). `access_token`은 이후 API 요청 시 `Authorization: Bearer <token>` 헤더에 사용하고, `refresh_token`은 만료 시 `POST /api/auth/refresh` 재발급에 사용한다.
5. **저장 위치 설계** — localStorage/메모리 등 어디에 토큰을 둘지는 아직 정해지지 않았다. 프론트엔드 작업 시작 시 별도로 결정이 필요하다.

### 주의사항

- `code`는 `OAuthExchangeCodeStore` 기준 **1회용 + 60초 TTL**이다. 리다이렉트 직후 바로 교환 API를 호출해야 하며, 페이지 새로고침 후 같은 `code`로 재시도하면 401(`InvalidOAuthCodeException`)이 발생한다.
- 이 작업은 프론트엔드 개발이 본격적으로 시작되는 시점에 진행하기로 하고, 지금은 기록만 남긴다.

## 프론트엔드가 workspace-scoped API로 마이그레이션 필요

### 배경

문서 업로드 → 위키 생성 → 질의응답 전체 흐름을 curl로 end-to-end 검증한 뒤, 같은 걸 브라우저(프론트엔드)에서도 확인되는지 보려고 했으나 안 됐다. 원인을 확인해보니 인증 토큰 미전송보다 더 근본적인 문제가 있었다.

### 문제점

`frontend/app/_lib/api.ts`가 호출하는 API 경로가 `feature/user-workspace-auth` 브랜치에서 workspace 구조로 바뀌기 이전의 옛날 경로다. Next.js `next.config.mjs`의 `rewrites()`가 `/api/:path*`를 `http://localhost:8080/api/:path*`로 그대로 프록시하는데, 실제 백엔드에는 아래 경로들이 더 이상 없다.

| 프론트엔드가 호출하는 경로 | 함수 | 백엔드 현재 상태 |
|---|---|---|
| `POST /api/documents` | `uploadDocumentFile()` | 없음 — `POST /api/workspaces/{workspace_id}/documents`로 이동 |
| `GET /api/documents` | `fetchBackendData()` | 없음 — `GET /api/workspaces/{workspace_id}/documents`로 이동 |
| `POST /api/query` | `queryWiki()` | 없음 — `POST /api/workspaces/{workspace_id}/chat/sessions/{session_id}/query`로 이동 |
| `GET /api/chat/messages` | `fetchChatMessages()` | 없음 — session 기반 구조로 대체됨 |
| `GET /api/wiki/graph` | `fetchBackendData()` | 2026-07-04에 `/api/workspaces/{workspace_id}/wiki/graph`로 이동 확정 — `docs/backlog/issue-2026-07-04.md` 참고 |
| `GET /api/documents/{id}/blocks` | `fetchDocumentBlocks()` | 없음 — `GET /api/workspaces/{workspace_id}/documents/{document_id}/blocks`로 이동 |

추가로 `frontend/app` 전체에 `Authorization`, `access_token`, `workspace_id` 문자열이 하나도 없다 — 로그인 UI, 토큰 저장, workspace 선택 로직이 프론트엔드에 전혀 구현되어 있지 않다.

### 영향

지금 프론트엔드에서 문서 업로드나 질의를 시도하면 인증(`401`) 문제 이전에 **경로 자체가 없어서 404**가 먼저 발생한다. `/api/workspaces/**`가 `authenticated()`로 걸려 있어 경로를 다 고쳐도 그 다음엔 인증 문제가 남는다.

### 해결 방향 (다음 단계에서 진행)

1. 프론트엔드 API 클라이언트(`api.ts`)를 workspace-scoped 경로로 전면 수정
2. workspace 선택/생성 UI 및 상태 관리 추가 (지금은 workspace 개념 자체가 프론트엔드에 없음)
3. 로그인 UI, `/oauth/callback` 라우트, 토큰 저장/첨부 로직 구현 (바로 위 섹션 "OAuth 로그인 후 code 교환" 참고)

`frontend/CLAUDE.md` 규칙상 프론트엔드 작업은 Figma 시안 기준으로 별도 진행하는 영역이라, 이번 백엔드 브랜치 작업에서 바로 처리하지 않고 기록만 남긴다.

## Kakao OAuth 로그인 — 이메일 동의항목 제약으로 보류

### 배경

Google/Naver OAuth 로그인은 콘솔 설정 후 브라우저로 실제 로그인까지 end-to-end 검증을 완료했다. Kakao도 이어서 진행하려 했으나, Kakao Developers 콘솔에서 **카카오계정(이메일) 동의항목**을 활성화하려면 비즈 앱 전환(사업자등록번호 필요)이 요구되는 것을 확인했다. 이 프로젝트는 개인 개발자 계정이라 사업자등록번호가 없어 비즈 앱 전환이 불가능하다.

### 문제점

현재 `OAuthUserService.findOrCreateUser()`는 provider가 이메일을 안 주면 무조건 `OAuthEmailNotProvidedException`(400)을 던진다. 즉 이메일 동의항목이 막혀있으면 Kakao 로그인 자체가 항상 실패한다.

### 검토한 대안과 트레이드오프

1. **비즈 앱 전환 신청** — 사업자등록번호 없어서 채택 불가.
2. **이메일 없이도 가입 허용** — `users.email`을 OAuth 계정에 한해 nullable로 바꾸고 이메일 기반 계정 연결(같은 이메일이면 기존 유저에 provider 연결) 로직을 우회. 스키마/서비스 로직 변경이 필요하고, 같은 사람이 Google(이메일 O)과 Kakao(이메일 X)로 각각 로그인하면 자동으로 같은 계정으로 안 묶이는 부작용이 있다.
3. **합성 이메일로 채움**(예: `kakao_{provider_user_id}@kakao.local`) — 실제 알림/계정 복구에 못 쓰고, 이메일 기반 계정 연결 로직을 왜곡시킨다.

### 결론

**지금은 Kakao 로그인을 보류한다.** Google/Naver는 이미 동작 확인이 끝났고, Kakao의 이메일 제약은 계정 모델에 영향을 주는 설계 결정(2번/3번 대안)이 필요한 사안이라 별도 논의 없이 서둘러 처리하지 않기로 했다. 나중에 아래 조건 중 하나가 충족되면 재검토한다.

- 사업자등록번호를 확보해 비즈 앱 전환이 가능해지는 경우
- 이메일 없는 OAuth 계정을 허용하는 방향으로 계정 모델을 다시 설계하기로 하는 경우
