# 2026-07-23 Backend 이슈

## 1. [Backend 해결] workspace 폴더 트리 영속화 API

2026-07-25 기준 backend API가 파일탐색기식 단일 폴더 트리로 구현됐다(폴더 생성·이름변경·이동·삭제·복구, 문서 배치·이동, 형제 위치 드래그, 최상위 navigation, 순환·버전·멱등·workspace 격리). 해결 기록은 [`docs/backlog/issue-2026-07-25.md`](../../../../../docs/backlog/backlog/issue-2026-07-25.md)의 `Backend — 폴더 트리 영속화 API`, 변경 기록은 `docs/changelog/backend.md` 2026-07-25 항목, 계약은 `docs/spec/sdd/markdown-document-hierarchy.md` 참조.

남은 작업: breadcrumb·이름 검색(H005 잔여), frontend가 `localStorage` 대신 navigation·폴더 API로 트리를 복원하는 재배선(H007, 별도 frontend 작업). 이전 요구 배경은 아래에 유지한다.

왼쪽 사이드바는 문서와 폴더를 계층형 트리로 표시하고, 프로젝트 사이에서 문서·하위 폴더를 이동할 수 있다. 그러나 backend에는 폴더를 생성하거나 트리 배치와 정렬 순서를 저장하는 API가 없다.

### 현재 상태

- backend의 문서 목록 API는 workspace 문서를 flat list로 반환한다.
- frontend는 최상위 폴더를 `Project`, 하위 항목을 `TreeItem`으로 관리한다.
- 폴더 생성, 이름 변경, 삭제, 문서·폴더 이동 결과는 workspace별 `localStorage`에 임시 저장한다.
- 따라서 같은 브라우저에서는 새로고침 후 복원되지만, 다른 브라우저·기기·협업자에게는 동기화되지 않는다.
- backend에서 삭제된 문서와 새로 추가된 문서만 문서 목록 응답을 기준으로 frontend 트리에 재동기화한다.

### 필요한 API 계약

endpoint 이름과 응답 DTO는 구현 전에 최종 확정하되 다음 동작을 workspace 범위에서 제공해야 한다.

- `GET /api/workspaces/{workspace_id}/document-tree`
  - 폴더 계층, 문서 배치, 같은 부모 안의 정렬 순서를 반환한다.
- `POST /api/workspaces/{workspace_id}/folders`
  - 폴더 이름, 선택적 상위 폴더 ID와 정렬 위치를 받아 폴더를 생성한다.
- `PATCH /api/workspaces/{workspace_id}/folders/{folder_id}`
  - 폴더 이름, 상위 폴더와 정렬 위치를 변경한다.
- `DELETE /api/workspaces/{workspace_id}/folders/{folder_id}`
  - 비어 있지 않은 폴더의 삭제 정책을 명시하고 적용한다.
- `PATCH /api/workspaces/{workspace_id}/documents/{document_id}/placement`
  - 문서의 폴더 ID와 정렬 위치를 변경한다. 최상위 배치는 `folder_id: null`로 표현한다.

폴더와 문서 이동을 하나의 트리 mutation endpoint로 제공하는 방식도 가능하지만, frontend가 전체 트리를 덮어쓰지 않고 충돌을 감지할 수 있도록 version 또는 `updated_at` 기반 조건부 변경 계약이 필요하다.

### Backend 구현 작업

1. workspace 소유 폴더 entity와 자기 참조 parent 관계를 추가한다.
2. 같은 부모 안의 폴더·문서 정렬 순서를 저장할 모델을 정의한다.
3. 폴더 생성·이름 변경·이동·삭제와 문서 배치 변경을 transaction으로 처리한다.
4. 폴더를 자기 자신이나 자신의 하위 폴더로 이동하는 순환 구조를 차단한다.
5. 모든 조회·변경에서 workspace 구성원 권한과 대상 folder/document 소속을 검증한다.
6. 문서 업로드 시 기본 배치 위치와 폴더 삭제 시 포함 문서 처리 정책을 확정한다.
7. 동시 이동·이름 변경 충돌 응답을 정의한다.

### 완료 조건

- 폴더 생성 후 로그아웃·재로그인하거나 다른 브라우저에서 접속해도 동일한 트리가 조회된다.
- 문서와 하위 폴더를 같은 프로젝트 및 다른 프로젝트로 이동한 결과가 유지된다.
- 폴더·문서의 형제 정렬 순서가 유지된다.
- 다른 workspace의 folder/document를 조회하거나 변경할 수 없다.
- 순환 이동, 존재하지 않는 parent, 비어 있지 않은 폴더 삭제, 동시 변경 충돌이 backend 테스트로 검증된다.
- frontend가 `localStorage`를 원본 저장소로 사용하지 않고 backend 응답으로 트리를 복원한다.

### Frontend 임시 구현과 후속 연결

- 현재 frontend는 `fruition.project_tree.{workspace_id}` 키에 폴더 트리를 임시 저장한다.
- API가 준비되면 `useProjectTree`의 초기 복원과 변경 저장을 backend 호출로 교체한다.
- offline 또는 낙관적 UI가 필요하면 `localStorage`는 원본이 아닌 cache로만 사용한다.
- 변경 실패 시 frontend가 이전 트리로 원복할 수 있도록 backend 오류 code를 안정적으로 제공한다.

### 확인 위치

- frontend 트리 상태·임시 저장: `frontend/app/_hooks/useProjectTree.ts`의 `PROJECT_TREE_STORAGE_PREFIX`, `loadPersistedProjects`, `persistProjects`
- frontend 프로젝트 간 이동: `frontend/app/_lib/tree.ts`의 `moveProjectTreeItem`
- frontend backend 문서 재동기화: `frontend/app/_lib/tree.ts`의 `mergeBackendDataIntoProjects`
- 현재 문서 API client: `frontend/app/_lib/api.ts`의 `fetchBackendData`
- 기존 API 범위: `docs/backlog/Fruition_MVP_API_Contract.md`의 `10. MVP 제외` 내 `폴더형 파일 트리`

## 2. Markdown Agent turn production 동시성·대화 context 후속

Spring의 `POST /api/workspaces/{workspace_id}/agent/turn` 프록시는 구현됐다. workspace·document 접근 권한과 Markdown 문서 여부를 확인하고, `editorSnapshot`을 `active_markdown_context`로 변환해 `llmPipeline`의 `POST /agent/turn`을 호출한다. pipeline의 400/422 응답은 보존하며 결과에 `documentId`, `baseVersion`, `requestId`를 붙인다.

### 남은 Backend 작업

1. 현재 local profile 메모리 mock인 문서 content 저장을 영속 저장소로 교체한다.
2. Agent 요청의 `baseVersion`을 영속 저장된 현재 content version과 비교하고 오래된 요청을 `409`로 거절한다.
3. Agent 요청을 chat session과 연결하고, 최근 대화 요약과 reference context를 Backend에서 구성한다.
4. production content 저장 API까지 포함한 권한·version·timeout 통합 테스트를 추가한다.

### 완료 조건

- 오래된 `baseVersion` 요청이 pipeline 호출 전에 충돌 응답으로 거절된다.
- chat session 기반 요청에서 실제 최근 대화와 reference context가 pipeline에 전달된다.
- Apply 이후 영속 content 저장 API의 optimistic locking으로 version 증가와 충돌이 검증된다.

### 확인 위치

- 전체 계약: `docs/spec/agent-markdown-contract.md`의 `Frontend → Spring backend`, `Spring backend → llmPipeline`, `오류 처리`
- Spring endpoint: `backend/src/main/java/fruition/agent/controller/AgentTurnController.java`의 `POST /turn`
- pipeline 변환: `backend/src/main/java/fruition/agent/repository/PipelineAgentRequester.java`
- frontend 호출: `frontend/app/_lib/api.ts`의 `requestAgentTurn`

## 3. 운영 이메일 인증 메일 서버 연동

회원가입과 비밀번호 재설정의 이메일 인증 API는 구현됐지만, 현재 발송 구현은 인증번호를 로그에 남기는 개발용 stub이다. 로컬 개발에서는 메일 서버 연결 전까지 고정 인증번호 `9700`을 사용하며, frontend도 development build에서 해당 번호 입력을 감지해 자동으로 검증 요청을 보낸다.

### 남은 Backend 작업

1. SMTP 또는 메일 발송 provider를 확정하고 `EmailVerificationSender`의 운영 구현을 추가한다.
2. API key, 발신 주소, provider endpoint 같은 secret과 환경별 설정을 배포 환경에 주입한다.
3. 발송 실패·timeout·재시도 정책과 사용자에게 반환할 오류 응답을 정의한다.
4. 회원가입과 비밀번호 재설정 목적별 메일 제목·본문 template을 적용한다.
5. production에서 `AUTH_EMAIL_DEV_FIXED_CODE`가 비어 있고 개발용 로그 sender가 등록되지 않도록 검증한다.
6. 실제 provider sandbox 또는 test double을 사용한 발급·발송 통합 테스트를 추가한다.

### 완료 조건

- production 인증번호가 무작위로 생성되어 사용자의 이메일로 전달된다.
- 인증번호 원문이 application log와 DB에 남지 않는다.
- production에서 임시 코드 `9700`이 별도 발급 없이 검증을 통과하지 않는다.
- 기존 재요청 cooldown, 일일 상한, 만료, 오입력 제한과 token 1회성 정책이 유지된다.
- 발송 실패를 관측할 수 있으면서 log와 metric에 이메일 주소나 인증번호 원문을 노출하지 않는다.

### 확인 위치

- 인증번호 발급·검증: `backend/src/main/java/fruition/user/service/EmailVerificationService.java`
- 발송 interface와 개발용 구현: `backend/src/main/java/fruition/user/mail/EmailVerificationSender.java`, `backend/src/main/java/fruition/user/mail/LoggingEmailVerificationSender.java`
- 환경별 고정 코드: `backend/src/main/resources/application.properties`, `backend/src/main/resources/application-local.properties`
- frontend 자동 감지: `frontend/app/(auth)/_hooks/useDevelopmentVerificationCode.ts`

### 2026-07-23 갱신 (Frontend Auth 스트림 대조 결과)

Frontend 인증 4흐름(로그인·회원가입·비밀번호 찾기·재설정)의 화면↔API 정합성을 코드 레벨로 재검증했다. **Frontend는 전부 실동작하며 변경 없음**. 유일한 미완은 아래 Backend 메일 발송부다. 상세 근거·작업 패키지는 `docs/issue/frontend/2026-07-23-parallel-streams/stream1-auth.md`를 상호참조한다.

기존 `남은 Backend 작업` 목록에 다음 세부 근거를 추가한다.

- **의존성 추가 위치**: `backend/build.gradle:44-45` 인접 dependencies 블록에 `spring-boot-starter-mail`(또는 SendGrid/SES SDK)를 추가한다. 현재 mail 관련 의존성 없음.
- **개발용 sender 프로필 분리**: `LoggingEmailVerificationSender`가 현재 무조건 `@Component`로 등록된다. 운영 `SmtpEmailVerificationSender` 신규 시 `@Profile("local")`(또는 `@ConditionalOnProperty`)로 dev stub과 배타 등록해, 운영 프로필에서 로그 sender가 뜨지 않도록 한다.
- **환경 변수 현황**: `infra/.env.example:63`에는 현재 `AUTH_EMAIL_DEV_FIXED_CODE=9700`만 있다. 운영 연동 시 `MAIL_*`/`SMTP_*`(host/port/user/pass/발신주소) 또는 provider API key 항목을 `.env.example`과 `application*.properties`(`spring.mail.*`)에 추가한다.
- **production 가드**: `AUTH_EMAIL_DEV_FIXED_CODE`가 비어 있음을 강제하고, dev stub이 미등록임을 기동 시 검증한다(기존 완료 조건과 동일 취지, 프로필 분리로 구조화).

프론트 확인 근거: 화면↔API 매핑은 `frontend/app/login/page.tsx`(login/OAuth), `frontend/app/(auth)/signup/page.tsx`·`signup/verify/page.tsx`(요청→confirm→signup→login), `forgot-password/page.tsx`·`reset-password/page.tsx`(요청→confirm→재설정)에서 확인. API 함수는 `frontend/app/_lib/api/auth.ts`. 로컬은 `9700` 자동인증(`useDevelopmentVerificationCode.ts`)으로 우회.

## 4. 문서 업로드와 Ingest 분리 및 편집 Markdown 재처리

현재 `POST /api/workspaces/{workspace_id}/documents`는 원본 저장 직후 문서를 `processing` 상태로 만들고 pipeline 요청까지 자동 등록한다. 따라서 Frontend는 여러 문서를 먼저 정리·편집한 뒤 사용자가 명시적으로 전체 Ingest를 시작하는 흐름을 구현할 수 없다.

또한 local profile의 문서 draft 저장 API는 편집 내용을 메모리에만 보관한다. 기존 문서의 MinIO 원본을 최신 Markdown으로 교체하고 같은 `document_id`로 다시 처리하는 production API가 없다.

### 필요한 API 계약

- 문서 업로드는 Object Storage와 `documents` 레코드 저장까지만 수행하고 `uploaded` 상태를 반환한다.
- `POST /api/workspaces/{workspace_id}/documents/{document_id}/ingest`
  - 아직 source page가 없는 `uploaded` 문서를 `processing`으로 전환하고 pipeline 요청을 등록한다.
  - 편집된 Markdown을 선택적으로 받는다면 기존 `source_uri`의 원본, `content_hash`, `byte_size`를 같은 transaction 경계에서 갱신한 뒤 재처리한다.
  - 이미 처리 중인 문서에 대한 중복 요청은 idempotent하게 처리하거나 명확한 충돌 응답을 반환한다.
- 여러 문서를 한 번에 처리할 필요가 있다면 batch endpoint 제공 여부와 부분 실패 응답 형식을 확정한다.

### Backend 구현 작업

1. 일반 업로드 문서의 초기 상태와 기존 `chat_export` 자동 처리 경로를 분리한다.
2. workspace 권한과 문서 소속을 확인하는 Ingest endpoint를 추가한다.
3. source page 존재 여부, 현재 처리 상태, 재처리 가능 상태를 검증한다.
4. 편집 Markdown 원본 교체 시 중복 content hash와 Object Storage 저장 실패를 처리한다.
5. Ingest 요청과 문서 상태 변경, pipeline queue 등록의 transaction·재시도 정책을 정의한다.
6. 기존 자동 업로드 처리에 의존하는 client와 migration 호환성을 검토한다.

### 완료 조건

- 업로드만 수행하면 pipeline이 시작되지 않고 문서가 `uploaded` 상태로 조회된다.
- 명시적 Ingest 요청 후에만 `processing`으로 전환되고 pipeline run이 한 번 등록된다.
- 편집된 Markdown으로 재처리하면 같은 문서 ID의 원본과 hash/크기가 갱신되고 새 source 결과가 생성된다.
- 다른 workspace의 문서는 Ingest하거나 원본을 교체할 수 없다.
- 중복 요청, 처리 중 재요청, Object Storage 실패, pipeline 요청 실패가 Backend 테스트로 검증된다.
- Frontend는 Backend 구현 전까지 기존 업로드 즉시 처리 계약을 유지하며 수동·일괄 Ingest UI를 노출하지 않는다.

### 확인 위치

- 현재 업로드와 자동 처리 요청: `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload`, `requestProcessingAfterCommit`
- 현재 문서 상태 초기화: `backend/src/main/java/fruition/document/domain/Document.java`
- 현재 업로드 endpoint: `backend/src/main/java/fruition/document/controller/DocumentController.java`
- Frontend 업로드 호출: `frontend/app/_lib/api.ts`의 `uploadDocumentFile`
- Frontend 자동 처리 상태 polling: `frontend/app/_hooks/useBackendData.ts`의 `hasProcessingDocuments`
- production 문서 content 영속화 선행 작업: 이 문서의 `2. Markdown Agent turn production 동시성·대화 context 후속`
