# 2026-07-28 Backend 이슈

## 사용자 개인 설정 계정 동기화

### 현재 범위

- frontend는 공통 개인 설정을 `fruition.preferences.v1.{user_id}`, Graph 기본 표시를
  `fruition.preferences.graph.v1.{user_id}.{workspace_id}` 키로 브라우저 `localStorage`에 저장한다.
- 현재 설정은 같은 브라우저의 같은 사용자에게만 유지되며, 다른 기기에는 동기화되지 않는다.
- 브라우저 알림 권한 자체는 브라우저가 관리하므로 backend 저장 대상이 아니다.

### 후속 작업

- 인증된 사용자의 설정을 조회·부분 수정하는 `GET/PATCH /api/auth/me/preferences`를 추가한다.
- PATCH는 전달된 필드만 갱신하고, 알 수 없는 enum과 잘못된 타입은 `400`으로 거절한다.
- 미저장 사용자는 frontend 기본값과 동일한 응답을 받도록 기본값 버전을 관리한다.
- 계정 동기화 대상은 `document_font`, `editor.default_mode`, Markdown 표시 옵션,
  문서 처리 완료·실패 알림으로 한다.
- Graph 기본 노드 표시는 workspace별 사용자 override로 저장하는 API 또는 설정 필드를 둔다.
- `motion`은 기기 특성과 연결되므로 계정 동기화 여부를 결정한다. `browser` 알림
  권한 상태는 저장하지 않고, 서비스 알림 수신 의사만 별도 필드로 둘 수 있다.

### 완료 조건

- 사용자가 다른 브라우저에서 로그인해도 계정 설정과 workspace별 Graph 설정이 복원된다.
- 부분 수정이 다른 설정 값을 덮어쓰지 않는다.
- 사용자 A가 사용자 B의 설정을 읽거나 수정할 수 없다.
- 기존 설정이 없는 계정과 구버전 설정의 기본값 회귀 테스트가 통과한다.

### 관련 코드와 확인 위치

- `frontend/src/entities/user/model/preferences.ts` — 설정 스키마와 기본값
- `frontend/src/entities/user/model/UserPreferencesProvider.tsx` — 현재 브라우저 저장 경계
- `backend/src/main/java/fruition/user/controller/AuthController.java` — 기존 `GET /api/auth/me`
- `backend/src/main/java/fruition/security/SecurityConfig.java` — `/api/auth/me` 인증 경계

## AI 응답 개인 설정 전달

### 현재 범위

- frontend에는 아직 AI 응답 언어·분량·외부 웹 검색 정책을 노출하지 않았다.
- Query 요청은 backend가 pipeline 요청으로 변환하며, 현재 개인 설정 필드는 전달하지 않는다.
- pipeline의 `QUERY_WEB_SEARCH_MODE`는 서버가 웹 검색을 제공할 수 있는지 정하는 상한이다.

### 후속 작업

- 계정 설정에 `answer_language`, `response_length`, `web_search_policy`를 추가한다.
- `POST /query/runs`와 agent turn 처리 시 저장된 사용자 설정을 조회해 pipeline 요청에
  `output_language`, `response_length`, `allow_web_search`로 전달한다.
- `web_search_policy=ask`는 질문별 명시적 승인 없이는 `allow_web_search=false`로 변환한다.
- 서버의 웹 검색 기능이 꺼져 있으면 사용자 설정이 이를 강제로 켜지 못하게 한다.
- 필요하면 요청 단위 override를 허용하되, 계정 기본값을 수정하지 않는 계약으로 분리한다.

### 완료 조건

- Query와 Agent 경로가 같은 사용자 설정 해석 규칙을 사용한다.
- 사용자 설정 누락 시 기존 응답 동작이 유지된다.
- `ask` 정책의 승인 여부와 서버 기능 상한이 테스트로 검증된다.

### 관련 코드와 확인 위치

- `backend/src/main/java/fruition/query/controller/QueryController.java` — `POST /query/runs`
- `backend/src/main/java/fruition/query/repository/PipelineQueryRequester.java` — pipeline 요청 변환
- `backend/src/main/java/fruition/agent/repository/PipelineAgentRequester.java` — agent 요청 변환
- `docs/issue/ai/2026-07-28.md` — AI/Pipeline 입력 계약과 적용 규칙

## 앱이 닫힌 상태의 문서 처리 알림

### 현재 범위

- frontend 알림은 앱이 열린 동안 3초 polling으로 확인한 상태 전이에만 동작한다.
- Browser 알림도 앱이 열린 상태에서 숨겨진 탭의 polling이 유지되고 권한이 허용된 경우에만
  표시된다.

### 후속 작업

- 앱이 닫힌 상태까지 지원할지 제품 범위를 먼저 결정한다.
- 지원한다면 Web Push 구독 저장, 사용자·workspace 권한 검증, 완료·실패 이벤트 발행,
  중복 전송 방지 키와 구독 해지 API를 설계한다.
- 문서 이름 등 알림 본문의 민감 정보 노출 수준을 정의한다.

### 관련 코드와 확인 위치

- `frontend/src/widgets/workspace/model/useBackendData.ts` — 처리 중 문서 polling
- `frontend/src/features/document-notifications/model/useDocumentProcessingNotifications.ts`
  — 현재 열린 앱의 상태 전이 감지

## JWT 인증 요청의 Spring Session 저장 경합

### 현재 상태

- 로그인 직후 frontend가 `GET /api/workspaces`와 `GET /api/auth/me`를 병렬 호출한다.
- backend는 JWT 인증 필터로 `SecurityContext`를 설정하지만
  `SessionCreationPolicy.IF_REQUIRED`와 JDBC Spring Session도 함께 사용한다.
- 인증되지 않은 요청으로 `SESSION`이 먼저 생성된 뒤 동일 세션에서 JWT 인증 요청이
  병렬 실행되면, `SPRING_SECURITY_CONTEXT` 저장 과정에서 다음 unique key 충돌이 발생한다.

```text
duplicate key value violates unique constraint "spring_session_attributes_pk"
Key (session_primary_id, attribute_name)=(..., SPRING_SECURITY_CONTEXT) already exists
```

- 브라우저 재현에서 병렬 요청 결과가 `200/500`으로 갈렸으며, 호출 순서를 바꾸면
  `GET /api/workspaces`가 `500`이 되는 것도 확인했다.
- frontend 영향과 화면 검증 범위는
  `docs/issue/frontend/2026-07-28.md`의
  **워크스페이스 초기 진입 시 인증 요청 경합 처리**를 참조한다.

### 후속 작업

- OAuth2 authorization request·callback처럼 세션이 필요한 경로와 JWT 기반 `/api/**`
  인증 경로의 `SecurityFilterChain` 및 `SecurityContextRepository`를 분리한다.
- JWT 인증 경로는 요청마다 Bearer token으로 인증하고 `SecurityContext`를 HTTP Session에
  저장하지 않는 stateless 경계로 구성한다.
- OAuth2 로그인에 필요한 임시 세션과 callback 동작이 유지되는지 회귀 테스트한다.
- 동일 `SESSION`에서 `GET /api/workspaces`와 `GET /api/auth/me`를 병렬 호출하는 통합 테스트를
  추가하고 JDBC Session unique key 충돌 및 `500`이 발생하지 않는지 검증한다.

### 완료 조건

- JWT 인증 API의 병렬 요청이 모두 `200`으로 완료되고
  `spring_session_attributes_pk` 충돌이 발생하지 않는다.
- JWT가 없거나 유효하지 않은 `/api/workspaces`와 `/api/auth/me` 요청은 세션 인증에
  의존하지 않고 `401`을 반환한다.
- OAuth2 redirect·callback 흐름은 필요한 세션 상태를 정상적으로 유지한다.
- frontend 로그인 직후 `/workspaces` 최초 진입이 재시도 없이 성공한다.

### 관련 코드와 확인 위치

- `backend/src/main/java/fruition/security/SecurityConfig.java` —
  `securityFilterChain`, `SessionCreationPolicy.IF_REQUIRED`, OAuth2 설정
- `backend/src/main/java/fruition/security/JwtAuthenticationFilter.java` —
  Bearer token 검증과 `SecurityContextHolder` 설정
- `backend/src/main/resources/application.properties` —
  `spring.session.store-type=jdbc`, `spring.session.jdbc.initialize-schema`
- `frontend/src/views/workspaces/ui/WorkspacesPage.tsx` — `GET /api/workspaces`
- `frontend/src/entities/user/model/UserPreferencesProvider.tsx` — `GET /api/auth/me`
- `docs/issue/frontend/2026-07-28.md` —
  **워크스페이스 초기 진입 시 인증 요청 경합 처리**
