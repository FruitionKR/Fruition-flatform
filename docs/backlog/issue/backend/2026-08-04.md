# 2026-08-04 Backend 이슈

## Agent Skill·Workspace Tool 기능의 Spring 경계 구현

### 배경과 현재 상태

- 상세 설계는 `docs/spec/sdd/agent-skills-and-folder-organization.md`에 정의되어 있다.
- 구현 순서와 역할별 작업은
  `docs/spec/sdd/tasks/agent-skills-and-folder-organization-tasks.md`의
  **TASK-002 DB Migration과 저장 모델**, **TASK-008 사용자 권한 기반 Tool Gateway**,
  **TASK-011 Spring Agent API 통합**, **TASK-015 문서 Tool과 workspace_workflow**,
  **TASK-016 완료 AgentRun 기반 Skill proposal**, **TASK-017 Skill proposal Backend·Frontend 통합**을 기준으로 한다.
- llmPipeline에는 Skill 선택·버전·정책, AgentRun 계획·승인·비동기 실행, PostgreSQL 저장소,
  `workspace_workflow`, 문서 read/mutation Tool 계약과 저장하지 않는 완료 작업 기반 Skill
  proposal이 구현되어 있다. 실제 문서 Tool endpoint, artifact 저장소, source AgentRun 조회·권한
  검증과 Skill 최종 게시 proxy 연결은 Spring Backend에 아직 없다.
- 현재 Spring의 `POST /api/workspaces/{workspaceId}/agent/turn`은 Markdown 문서 편집 계약을
  전제로 하며, `documentId`, `baseVersion`, `editorSnapshot`이 필요하다. 폴더 정리 요청과
  Skill 관리·AgentRun 조회/승인 API는 아직 없다.
- `PipelineAgentRequester`는 llmPipeline 요청에 인증된 `user_id`와 URL의 `workspace_id`를
  AgentRun actor context로 전달하지 않는다.
- 기능은 `AGENT_SKILLS_ENABLED=false`가 기본값이며, 아래 Backend 경계가 완성되기 전에는
  실제 폴더·문서 변경을 활성화하면 안 된다.
- Frontend 작업 범위는 `docs/issue/frontend/2026-08-04.md`의
  **Skill 관리·Workspace AgentRun·완료 작업 Skill proposal UI 구현**을 참조한다.

### 반드시 지킬 권한·보안 경계

- Frontend는 llmPipeline에 직접 접근하지 않고 Spring Backend의 인증된 API만 호출한다.
- llmPipeline은 Backend의 folder/document DB를 직접 읽거나 변경하지 않는다.
- Agent는 로그인한 사용자가 UI에서 직접 수행할 수 있는 작업만 더 빠르게 자동화한다.
  관리자 권한 상승, 다른 사용자의 권한 대행, 범용 DB·SQL·shell·HTTP 실행은 허용하지 않는다.
- Spring은 내부 Tool 요청마다 다음 교집합을 다시 검증한다.

```text
capability 허용 tool
∩ Skill allowed_tools
∩ AgentRun 사용자의 현재 권한
∩ 승인된 plan operation
```

- 계획을 만들 때 권한이 있었더라도 실행 시점에 멤버십이나 리소스 권한이 회수되었다면
  해당 operation을 `forbidden`으로 실패시킨다.
- 폴더·문서 변경은 기존 `FolderService`, `DocumentService`, `DocumentPlacementService`와
  문서 본문 편집 경계를 호출해 수행한다. 기존 hierarchy, edit target, version, permission,
  idempotency 검증을 우회하는 repository 직접 호출을 추가하지 않는다.
- 삭제 Tool은 이번 범위에 포함하지 않는다. 계획이나 Skill에 삭제 지시가 있어도 실행하지 않는다.
- 감사 로그에는 run/job/operation 식별자와 상태만 구조화해 남기며 문서 본문, 전체 prompt,
  사용자 인증 token, 내부 service token은 기록하지 않는다.

### 작업 1. DB Migration과 저장 모델

- Spring Flyway migration으로 다음 테이블과 제약조건을 생성한다.

  - `skills`, `skill_versions`, `skill_version_sources`
  - `agent_runs`, `agent_plans`, `agent_plan_operations`
  - `agent_approvals`, `agent_jobs`, `agent_tool_executions`, `agent_run_artifacts`

- Migration은 llmPipeline의 PostgreSQL repository가 기대하는 컬럼명·enum 값·관계를 먼저
  대조해 작성한다. Java entity 편의에 맞춰 계약을 독자적으로 바꾸지 않는다.
- 최소한 다음 무결성 조건을 DB와 application 양쪽에서 검증한다.

  - 개인 Skill의 owner와 팀 Skill의 workspace scope
  - Skill의 draft/published version 및 현재 enabled version
  - 하나의 Skill에 여러 enabled version이 생기지 않는 조건
  - AgentRun의 현재 plan version과 plan별 immutable operation 목록
  - AgentRun의 conversation·turn 참조와 현재 사용자가 접근 가능한 source run 범위
  - Skill version과 source completed AgentRun 연결
  - 승인 레코드의 `plan_version`, canonical `operation_hash`, 승인 actor
  - Agent job의 lease owner, lease expiry, retry count와 상태 전이
  - Tool 실행의 operation 단위 idempotency key와 중복 실행 방지
  - AgentRun당 최대 Tool 호출 수 40회

- 상태·lease·보관 조회에 필요한 index를 추가한다. 종료된 AgentRun은 90일 보관 후 삭제할 수
  있어야 하며, 종료되지 않은 run은 보관 정리 대상에서 제외한다.
- 기존 `wiki_schemas` 데이터와 API는 Skill로 migration하거나 변경하지 않는다. Wiki Schema와
  Agent Skill은 서로 다른 개념과 저장 모델로 유지한다.
- migration 적용 순서의 단일 소유자를 Spring Flyway로 고정하고 llmPipeline worker보다 먼저
  적용되도록 배포 순서를 문서화한다.

### 작업 2. 기존 Agent turn 계약 확장

- 다음 공개 endpoint의 기존 URL을 유지한다.

```text
POST /api/workspaces/{workspace_id}/agent/turn
```

- Markdown `query/create/edit`의 초안·편집안 응답은 하위 호환을 유지한다.
- `folder_organize` 요청은 문서 편집 필드를 강제로 요구하지 않도록 request validation을
  action별로 분리한다.
- Markdown 결과를 실제 저장·반영하거나 폴더와 문서를 함께 변경하는 `workspace_workflow`는
  `run_id`를 반환하고 승인 전 mutation을 실행하지 않는다.
- 같은 채팅에서 “방금 방식대로 Skill로 만들어줘”를 요청하면 `skill_draft_proposal` action과
  source run 목록, 저장되지 않은 구조화된 Skill proposal을 반환한다.
- 모든 Agent 요청에 URL의 `workspace_id`와 Spring Security에서 확인한 현재 `user_id`를
  llmPipeline에 전달한다. client가 body에 임의로 넣은 actor/workspace 값은 신뢰하지 않는다.
- Backend가 llmPipeline의 Agent·Skill API를 호출할 때 `X-Agent-Service-Token` 헤더에
  `AGENT_INTERNAL_TOKEN`을 전달한다. llmPipeline은 기능 활성 상태에서 이 header가 없거나
  일치하지 않으면 요청을 거절한다.
- `skill_mode`는 `auto`, `explicit`, `off`를 지원하고 explicit 모드에서는 `skill_id`를 전달한다.
- 폴더 정리 계획 생성이 접수되면 동기 실행 결과가 아니라 `run_id`와 초기 상태를 반환한다.
- 여러 Skill이 비슷하게 일치한 경우 후보 목록과 설명을 반환하고, 사용자가 Skill 하나 또는
  “Skill 없이 진행”을 선택하기 전에는 AgentRun을 실행하지 않는다.
- llmPipeline의 validation, forbidden, not-found, conflict, feature-disabled 오류를 기존 Backend
  오류 응답 형식과 HTTP status로 일관되게 변환한다.

### 작업 3. AgentRun 공개 API proxy

- 인증·workspace membership을 선검증한 뒤 다음 API를 제공한다.

```text
GET  /api/workspaces/{workspace_id}/agent/runs/{run_id}
POST /api/workspaces/{workspace_id}/agent/runs/{run_id}/approve
POST /api/workspaces/{workspace_id}/agent/runs/{run_id}/reject
POST /api/workspaces/{workspace_id}/agent/runs/{run_id}/cancel
POST /api/workspaces/{workspace_id}/agent/runs/{run_id}/revise
```

- 조회 응답에는 현재 상태, 선택된 Skill/version, 현재 plan version/hash, operation별 대상·이동
  위치·이유·상태·결과, 최종 검증 결과를 포함한다. Frontend가 llmPipeline 내부 모델을 추측해
  조립하지 않도록 공개 DTO를 명시한다.
- 승인 요청은 사용자가 본 정확한 `plan_version`과 `operation_hash`를 필수로 받는다. 현재 계획과
  하나라도 다르면 `409 Conflict`로 거절하고 실행 job을 만들지 않는다.
- 자연어 “응”, “승인”, “진행”은 현재 사용자에게 승인 대기 중인 계획이 정확히 하나일 때만
  해당 승인 API로 연결할 수 있다. 일반 chat 응답만으로 승인 상태를 변경하지 않는다.
- revise는 같은 AgentRun에 새 plan version을 만들고 이전 승인을 무효화한다. 사용자가 operation
  JSON을 직접 수정하는 API는 제공하지 않는다.
- 다른 사용자 개인 Skill로 만든 run, 다른 workspace의 run, 접근 권한이 없는 run은 조회·승인·
  취소할 수 없어야 한다.
- terminal 상태는 `completed`, `partial_failed`, `failed`, `conflicted`, `rejected`,
  `cancelled`를 구분하고 부분 실패를 전체 성공으로 변환하지 않는다.
- 조회 응답은 폴더 위치뿐 아니라 문서 생성·본문 편집 target과 검증된 document version을 포함한다.

### 작업 4. Skill 관리 공개 API proxy

- 다음 API를 Spring 인증·권한 경계 안에 제공한다.

```text
POST  /api/workspaces/{workspace_id}/skills/preview
POST  /api/workspaces/{workspace_id}/skills/author
POST  /api/workspaces/{workspace_id}/skills/author/publish
GET   /api/workspaces/{workspace_id}/skills
GET   /api/workspaces/{workspace_id}/skills/{skill_id}
PATCH /api/workspaces/{workspace_id}/skills/{skill_id}
POST  /api/workspaces/{workspace_id}/skills/{skill_id}/enable
POST  /api/workspaces/{workspace_id}/skills/{skill_id}/disable
POST  /api/workspaces/{workspace_id}/skills/draft-from-runs/preview
```

- 개인 Skill은 owner만 생성·수정·게시·활성화·사용할 수 있다.
- 팀 Skill은 같은 workspace의 활성 멤버만 사용할 수 있고, 관리 권한은 별도로 제한한다.
- 현재 `WorkspaceRole`이 `OWNER/MEMBER`만 제공한다면 이번 작업에서 임의로 `EDITOR`를
  가정하지 않는다. 역할 모델을 확장하기 전까지 팀 Skill 생성·수정·게시·활성화는 `OWNER`만
  허용하는 안을 확정하거나, `EDITOR` 도입을 별도 설계·migration 작업으로 먼저 결정한다.
- 목록과 조회는 현재 사용자가 접근할 수 있는 Skill만 반환한다. 같은 이름이 존재할 수 있으므로
  `skill_id`, scope(`personal`/`team`), owner/workspace 표시 정보를 함께 반환한다.
- `preview`는 저장하거나 활성화하지 않고 파싱·정책 검증 결과만 반환한다.
- `author`는 짧은 자연어와 최대 3개의 참조 문서 ID를 받아 llmPipeline의 `POST /skills/author`를
  호출한다. 단발 입력이므로 정보가 부족해도 보충 질문을 중계하지 않고 편집 가능한 예시 draft를
  반환한다. 사용자는 capability와 Tool을 직접 입력하지 않고 생성된 Skill Markdown만 확인한다.
- 채팅 `/agent/turn`이 Skill 작성 보충 질문을 반환한 경우 다음 turn의
  `conversation_context.recent_conversation_summary`에 진행 중인 Skill 생성 요청을 유지한다. 그래야
  사용자가 생성 문구를 반복하지 않고 짧게 답해도 같은 authoring 흐름을 재개할 수 있다.
- `draft-from-runs/preview`는 같은 사용자·Workspace·채팅의 completed AgentRun과 명시적으로 선택한
  요청·수정 지시 turn만 받아 내부 권한 상한을 계산한 뒤 공통 `AuthorSkillUseCase`로 재검토한다.
  응답은 Tool을 제외한 `SkillAuthoringResponse`이며 Skill을 저장하지 않는다.
- source를 지정하지 않으면 같은 채팅의 가장 최근 completed AgentRun 하나와 연결 지시만 사용하고
  채팅 전체를 암묵적으로 읽지 않는다.
- proposal에 고정 folder/document ID, 문서 본문, 전체 prompt와 인증정보가 포함되지 않도록 검증한다.
- proposal은 DB에 저장하지 않고 사용자 검토 상태로만 유지한다. 최종 승인 시 `POST /skills/author/publish`가 규칙·LLM 보안 검사를 다시 수행하고 통과한 version을 즉시 published로 저장한다.
- `PATCH /skills/{skill_id}`도 capability와 Tool을 받지 않고 같은 작성 검토 경로에서 내부 권한을 재계산한 뒤 새 published version을 만든다.
- publish 후 version은 immutable하게 취급하며 수정은 검증된 새 published version으로 만든다.
- 여러 Skill을 동시에 enabled할 수 있다. “전체에서 하나만 active”인 기존 Schema 개념을 Skill에
  재사용하지 않는다.

### 작업 5. 사용자 권한 기반 내부 Tool Gateway

- llmPipeline 전용 내부 endpoint를 공개 사용자 API와 분리한다.

```text
POST /internal/agent/tools/read/{tool_name}
POST /internal/agent/tools/execute/{tool_name}
POST /internal/agent/skill-authoring/references/read
```

- 현재 llmPipeline client 계약에 맞춰 `AGENT_BACKEND_URL`을 base URL로 사용하고,
  `X-Agent-Service-Token` 헤더의 `AGENT_INTERNAL_TOKEN`을 검증한다. 운영 환경에서는 token의
  생성·주입·rotation·로그 마스킹 방법까지 배포 문서에 남긴다.
- service token은 사용자 권한을 대체하지 않는다. 요청의 run actor와 workspace를 서버가
  AgentRun 저장 상태와 대조한 뒤 현재 membership과 대상 리소스 권한을 다시 확인한다.
- `skill-authoring/references/read`는 AgentRun이 없는 자연어 작성 전용 조회다. `workspace_id`,
  `user_id`, `document_id`를 받아 현재 membership과 문서 read 권한을 검증하고 `markdown`만
  반환한다. 임의 `run_id`를 만들거나 AgentRun Tool Gateway의 run 검증을 우회하지 않는다.
- read Tool은 아래 목록으로 제한한다.

  - `list_root_items`
  - `list_folder_children`
  - `search_hierarchy`
  - `get_breadcrumb`
  - `get_document_metadata`
  - `get_document_content`
  - `list_agent_run_artifacts`

- mutation Tool은 아래 목록으로 제한한다.

  - `create_folder`
  - `rename_folder`
  - `move_folder`
  - `move_document`
  - `rename_document`
  - `create_document`
  - `apply_document_edit`

- mutation 요청마다 service 인증, run 상태, actor/workspace, 현재 승인된 plan version/hash,
  operation id, 정확한 tool/arguments, 선택된 Skill의 `allowed_tools`, 대상 `base_version`,
  idempotency key를 검증한다.
- 승인된 operation의 인자와 실제 Tool 요청 인자가 다르면 실행하지 않고 conflict로 기록한다.
- 기존 folder 이동/이름 변경의 idempotency 규칙을 재사용하고, document rename에 동등한 중복
  실행 방지가 없다면 이를 명시적으로 추가한다.
- `list_agent_run_artifacts`는 `run_id`, 사용자와 Workspace에 결합된 유효한 artifact의 ID,
  content hash, purpose와 문서 target만 반환하고 본문은 반환하지 않는다.
- `get_document_content`는 실행 사용자가 읽을 수 있는 범위만 반환한다. 전체 본문을 AgentRun 감사
  로그나 Skill source에 복사하지 않는다.
- `create_document`와 `apply_document_edit`는 승인 plan의 저장 위치·본문 참조 또는 편집 target,
  `base_version`과 실제 요청을 정확히 비교한다.
- 비동기 문서 payload는 plan·감사 로그에 본문으로 저장하지 않고 actor·Workspace에 결합된
  `agent_run_artifacts`에서 content hash를 검증해 사용한다. terminal run에서 더 이상 필요하지 않은
  artifact는 Skill source와 분리해 정리한다.
- llmPipeline bounded ReAct executor는 관찰 결과를 바탕으로 실행 가능한 승인 operation을
  한 번에 하나씩 선택한다. Spring은 선택 순서와 관계없이 요청의 operation id, tool, arguments가
  현재 승인 plan과 정확히 일치하는지 매 호출마다 검증한다.
- 실패한 작업에 의존하는 operation은 `skipped`로 처리하고 독립 operation은 이후 decision에서
  계속 선택할 수 있어야 한다.
- `clarification_required` 응답의 `error_code`는 `react_replan_state_changed`,
  `react_replan_insufficient_information`, `react_replan_plan_no_longer_safe`,
  `react_replan_goal_not_achievable`, `react_tool_budget_insufficient`,
  `react_step_limit_exceeded`를 사용자 안내 문구로 안전하게 변환한다.
- 실행 후 read Tool로 관련 상태를 다시 확인한다. 자동 rollback이나 Agent의 임의 복구 작업은
  수행하지 않는다.

### 작업 6. 설정·배포 안전장치

- Spring과 llmPipeline 양쪽에서 `AGENT_SKILLS_ENABLED=false`일 때 신규 Skill 선택과
  AgentRun 생성을 차단한다.
- kill switch가 꺼져 있어도 기존 query와 상태를 변경하지 않는 Markdown 초안·편집안 생성 및
  Wiki Schema 기능은 정상 동작해야 한다.
- DB migration → Spring 공개/내부 API → llmPipeline worker → Frontend 순서의 배포 선행조건을
  명시하고, 모든 구성요소 확인 전에는 worker profile을 활성화하지 않는다.
- 내부 Tool endpoint는 외부 ingress에서 접근할 수 없도록 network 경계를 설정한다.
- 종료 후 90일이 지난 AgentRun 관련 레코드를 하루 한 번 정리하되 FK 순서와 감사 요구사항을
  반영한다.

### 테스트 시나리오

- 기존 query와 Markdown draft create/edit 요청·응답의 회귀 테스트
- folder_organize 요청이 문서 편집 필드 없이 `run_id`를 반환하는 통합 테스트
- workspace_workflow 문서 저장·본문 편집 요청이 plan 승인 전 변경되지 않는 통합 테스트
- get_document_content, create_document, apply_document_edit 권한·version·target 검사 테스트
- 인증 사용자와 workspace가 llmPipeline actor context로 정확히 전달되는 테스트
- 개인 Skill의 타 사용자 접근 및 팀 Skill의 타 workspace 접근 거절 테스트
- 팀 Skill 관리 역할 테스트와 현재 `OWNER/MEMBER` 정책 테스트
- stale plan version/hash 승인, 중복 승인, 승인 후 revise, 취소 경합의 conflict 테스트
- service token 누락·오류, actor 위조, 권한 회수, target version 변경의 Tool 거절 테스트
- 승인되지 않은 operation, 허용 목록 밖 Tool, 변경된 arguments, 41번째 Tool 호출 거절 테스트
- ReAct executor가 선택한 operation id가 현재 승인 plan과 다르거나 아직 실행 가능하지 않으면
  mutation을 거절하는 테스트
- 남은 Tool 호출 예산을 pending mutation에 우선 배정하고 부족하면 계획 축소를 요청하는 테스트
- 동일 idempotency key 재요청 시 folder/document mutation이 한 번만 반영되는 테스트
- operation 부분 실패, 의존 작업 skipped, 독립 작업 계속, 최종 `partial_failed` 테스트
- kill switch가 AgentRun만 차단하고 기존 기능에는 영향을 주지 않는 테스트
- 다른 사용자·Workspace·채팅 run을 Skill source로 지정할 때 거절하는 테스트
- Skill proposal에서 resource ID, 본문, prompt, 인증정보가 제거되는 테스트
- proposal 확인 전 Skill row·version 미생성, 최종 게시 후 published version 생성 테스트
- Flyway를 빈 DB와 현재 운영 schema 양쪽에 적용하는 migration 테스트
- 90일 보관 정리가 terminal run만 삭제하고 진행 중 run을 유지하는 테스트

### 완료 조건

- [ ] Frontend가 llmPipeline을 직접 호출하지 않고 모든 새 기능을 Spring API로 사용할 수 있다.
- [ ] 기존 Agent Markdown 계약과 Wiki Schema 기능에 회귀가 없다.
- [ ] Skill·AgentRun 공개 API가 인증 사용자와 workspace 범위를 강제한다.
- [ ] 승인은 정확한 plan version/hash에 묶이며 계획 변경 시 이전 승인이 무효화된다.
- [ ] 모든 실제 변경은 내부 Tool Gateway와 기존 domain service를 통과한다.
- [ ] service token만으로는 어떤 사용자 작업도 실행할 수 없다.
- [ ] Agent가 로그인 사용자의 현재 권한을 넘거나 삭제·범용 실행을 수행할 수 없다.
- [ ] 중복 요청과 worker 재시도에도 같은 mutation이 두 번 적용되지 않는다.
- [ ] 기능 비활성 상태에서 기존 query와 저장하지 않는 Markdown 초안·편집안 생성이 정상 동작한다.
- [ ] 문서 저장·본문 반영은 승인된 Tool Gateway operation으로만 실행된다.
- [ ] 완료 작업 기반 Skill proposal은 같은 사용자·Workspace·채팅의 성공 기록만 사용한다.
- [ ] migration, controller/service, Pipeline requester, Tool Gateway 통합 테스트가 통과한다.
