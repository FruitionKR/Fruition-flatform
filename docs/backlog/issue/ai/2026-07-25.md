# 2026-07-25 AI/Pipeline 이슈

## Multi-provider 실환경 E2E 검증

`LLM_PROVIDER`와 `LLM_*` 설정 일원화, ingestion·markdown 편집·query·agent
router의 공통 provider 해석, Claude Messages API 변환은 구현했다. 해결 내용은
`docs/backlog/issue-2026-07-25.md`의
`AI/Pipeline — Multi-provider 설정과 Claude Messages API 지원`을 참조한다.

남은 작업은 provider별 실제 API를 사용한 통합 검증이다.

### 현재 상태

- 공통 설정 resolver와 Claude Messages 요청·응답 변환의 단위 계약은 검증됐다.
- `llmPipeline/provider_e2e.py`가 실제 provider API로 ingestion JSON,
  agent router, `markdown_create` 계약을 각각 독립 실행하고 pass/fail,
  latency, HTTP status만 출력한다. 생성 본문과 provider 오류 본문은 출력하지 않는다.
- 현재 shell에는 OpenAI, Gemini, Claude credential이 없다.
- 로컬 `infra/.env`는 `LLM_PROVIDER=openai`, `LLM_MODEL=gpt-4.1-mini`지만
  `LLM_API_KEY`는 없고 legacy `UPSTAGE_API_KEY`만 설정돼 있어 통합 설정이
  일치하지 않는다. runtime은 legacy 값을 fallback하지 않으므로 provider에 맞는
  `LLM_API_KEY`를 별도로 설정해야 한다.
- legacy 키 인증 확인은 OpenAI HTTP 401, Upstage HTTP 200이었다.
- Upstage `solar-pro2` 실제 smoke는 ingestion JSON과 agent router를 통과했지만
  세 번째 `markdown_create`에서 account credit 부족 HTTP 403으로 중단됐다.
- OpenAI, Gemini, Claude의 실제 credential을 사용하는 E2E는 실행하지 못했으므로
  provider 지원 완료로 단정할 수 없다.

### 필요한 작업

- OpenAI, Gemini, Claude의 유효한 테스트 credential을 준비한다.
- provider마다 별도 env 파일에 `LLM_API_KEY`를 설정하고 다음 runner를 실행한다.

  ```bash
  cd llmPipeline
  PYTHONPATH=. .venv/bin/python provider_e2e.py \
    --provider <openai|gemini|claude> \
    --model <model> \
    --env-file <provider-env-file>
  ```

- smoke가 통과하면 실제 서비스에서 문서 업로드→Wiki ingestion 완료와 agent의
  `chat_answer`, `markdown_edit`, `markdown_create`를 실행한다.
- Claude에서 JSON 응답, 일반 text 응답, `max_tokens`, 오류 응답 변환을 확인한다.
- provider별 성공 여부와 사용한 model을 변경 기록에 남긴다. 비밀키와 원문
  provider 응답은 기록하지 않는다.

### 완료 조건

- OpenAI, Gemini, Claude 각각에서 ingestion과 agent 대표 action이 정상 응답한다.
- 한 실행에서 모든 LLM 경로가 동일한 `LLM_PROVIDER` 설정을 사용한다.
- Claude의 구조화 출력이 기존 JSON 계약 검증을 통과한다.
- credential 누락과 provider 오류가 비밀값을 노출하지 않고 실패한다.
