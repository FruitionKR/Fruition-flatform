# 2026-06-27 이슈

## Query/Ingest 변경점 정리

### 배경

이번 작업의 목표는 질의가 source/concept 문서의 요약 블록에만 갇히지 않고, 질문에 맞는 원자 단위 근거를 더 잘 선택하도록 만드는 것이다.
또한 내부 근거가 부족하거나 외부 공개 지식이 필요한 경우 web 보강 판단과 답변 평가가 돌아가도록 query evaluator를 추가했다.

### 문서 업로드부터 질의 결과까지의 플로우

1. 문서 입력

- Spring upload, API inline input, `input_path` 실행이 모두 pipeline 입력이 될 수 있다.
- 이번 수정으로 API inline/input path 실행도 `documents` row와 `source_document_id`를 갖게 했다.
- 이 값이 없으면 pipeline 결과는 파일로만 남고 DB의 source/concept/evidence 조회 흐름에 연결되지 않는다.

2. Ingest 실행

- pipeline은 입력 문서를 normalize하고 source block을 만든다.
- source block은 `B0001` 같은 block id를 가지며, 이후 evidence citation의 원문 위치가 된다.
- LLM semantic extraction이 key point, observation, concept candidate, source/concept page를 만든다.

3. Source/Concept page 저장

- source page는 원문 추적성과 문서별 observation/key point를 담당한다.
- concept page는 여러 source에서 재사용 가능한 개념, 정의, 역할, workflow를 담당한다.
- page 사이의 link와 role은 query 단계에서 관련 page 후보를 고르는 데 쓰인다.

4. Embedding unit 저장

- source/concept markdown 전체를 하나로만 보지 않고, 질문에 근거로 쓸 수 있는 단위로 잘라 저장한다.
- 저장 단위는 `key_point`, `observation`, `category`, `core_concept`, `section_candidate`, `mention`, `source_block`이다.
- 동일한 표현은 `wiki_embedding_vectors`에 canonical representation으로 한 번만 저장하고, 각 page와의 연결은 `wiki_embedding_units`가 가진다.
- 현재 dense vector 자체는 nullable이며, 우선 canonical text/hash와 unit/page 연결 구조를 만든 상태다.

5. Query page retrieval

- 질문이 들어오면 먼저 source/concept page 후보를 기존 graph/page relevance 흐름으로 고른다.
- 이 단계는 “어떤 page를 볼 것인가”를 정하는 단계다.
- source page만 보는 것이 아니라 concept page도 후보가 된다.

6. Page 내부 evidence selection

- 선택된 page 안에서 다시 unit 단위로 질문과의 관련도를 계산한다.
- page 선택 가중치가 높다고 해서 core/key point를 무조건 근거로 쓰지 않는다.
- page가 선택된 뒤에는 그 page 내부에서 질문과 가장 맞는 unit을 evidence로 고른다.
- 고정 top-N 대신 page별 최고 점수 대비 score band 안에 들어오는 evidence를 선택한다.

7. 답변 생성

- answer generator는 선택된 evidence만 보고 답변을 만든다.
- citation은 직접 근거가 되는 문장에만 붙이도록 prompt를 조정했다.
- 후처리에서 문장마다 자동으로 `[1]`을 붙이는 로직은 제거했다.

8. Evaluator와 web 보강

- evaluator는 생성된 답변과 evidence가 질문을 충분히 뒷받침하는지 판단한다.
- 내부 근거만으로 부족하고 질문이 공개 외부 지식도 요구하면 web search를 수행한다.
- 이때 단순 fallback만이 아니라 `internal_web_augmented`처럼 내부 근거와 web 근거를 함께 쓰는 route가 필요하다.
- web evidence도 block ref가 없더라도 evidence snippet으로 들어와야 답변에서 실제 근거로 사용할 수 있다.

9. 최종 응답

- 응답에는 answer, related pages, evidence snippets, graph context, traversal path가 포함된다.
- 사용자는 답변의 `[N]` citation을 evidence rank와 연결해 확인해야 한다.
- citation이 없는 evidence는 최종 사용자 관점에서 “사용된 근거”로 보기 어렵기 때문에 별도 후보/디버그 정보로 다루는 것이 맞다.

### 이전 커밋 대비 주요 변경점

1. `POST /pipeline/runs` inline 입력 저장 보강

- `input` 또는 `input_path`로 실행된 pipeline run에도 `source_document_id`와 `documents` row가 생성되도록 변경했다.
- `finish_pipeline_run()` 단계에서 source page, concept page, source block, embedding unit이 실제 DB에 남도록 했다.
- API 실행 인자에 `input_name`, 생성된 `document_id`, evaluator 관련 기본값을 연결했다.

2. Query evaluator와 web 보강 흐름 추가

- `QueryAnswerEvaluator`와 `query_answer_evaluator.system.md`를 추가했다.
- 답변 생성 후 evaluator가 답변/근거 정합성을 판단하고, 필요 시 web fallback 또는 internal web augmented route를 요청할 수 있게 했다.
- evaluator 설정은 dependency layer와 pipeline compose 환경변수로 주입한다.

3. source/concept 원자 단위 근거 저장 구조 추가

- `wiki_embedding_vectors` 테이블을 추가했다.
  - 동일한 `embedding_model + representation_hash` 조합은 하나의 canonical representation으로 재사용한다.
  - 현재는 `embedding_vector`를 nullable로 두고, canonical text/hash와 unit link를 먼저 저장한다.
- `wiki_embedding_units` 테이블을 추가했다.
  - canonical representation을 각 `page_id`, `source_document_id`, `unit_type`, `block_refs`와 연결한다.
  - 같은 표현이 여러 page에서 쓰여도 vector row는 공유하고 unit row만 추가된다.
- 저장 대상 unit type:
  - `key_point`
  - `observation`
  - `category`
  - `core_concept`
  - `section_candidate`
  - `mention`
  - `source_block`

4. Query context 조립 방식 변경

- `AnswerQueryUseCase`가 related page를 뽑은 뒤 `list_embedding_units_by_page_ids()`로 page별 unit을 함께 조회한다.
- `BuildQueryContextUseCase`는 저장된 unit을 우선 사용하고, 없을 때만 기존 markdown parsing fallback을 사용한다.
- page 선택은 기존 graph/page relevance 흐름을 유지하되, 최종 evidence는 page 내부 unit의 질문 유사도와 구체성을 다시 계산해 고른다.
- source와 concept 모두 evidence 후보로 탐색된다.

5. Evidence 선택 정책 수정

- 고정 top-N 제한을 제거했다.
- page별 최고 점수 대비 일정 비율 이상인 evidence를 score band로 선택한다.
- atomic evidence를 우선하되, 선택된 aggregate block ref에 연결된 source block도 함께 포함할 수 있게 했다.
- 설계 변수, 수치 범위, 단위, 조합, 표/예시, 정의 문구 같은 구체성 신호를 score에 반영했다.

6. Citation 정책 수정

- 답변 문장마다 자동으로 `[1]`을 붙이던 후처리를 제거했다.
- LLM이 실제로 인용한 evidence만 응답의 `evidence_snippets`에 남기도록 했다.
- 답변 prompt에는 직접 뒷받침하는 근거에만 citation을 붙이고, 넓은 citation list를 피하라는 규칙을 추가했다.

7. JSON parsing 보강

- semantic extraction 결과가 깨진 JSON으로 돌아오는 경우를 줄이기 위해 `parse_json_object()` repair 후보를 추가했다.
- 잘못 escape된 backslash를 복구하되, 정상 escape는 보존한다.
- NUL/control char가 섞인 원문은 코드만으로 해결하지 않고 cleaned markdown을 별도로 만들어 ingest했다.

8. Semantic extraction prompt 보강

- workflow, process, pipeline, maintenance task처럼 절차나 역할을 정의하는 문장이 observation으로만 축약되지 않고 section/core 후보가 되도록 prompt를 보완했다.

### 논문 외 실험 이력

이번 변경은 논문 ingest만 보고 만든 것이 아니라, 앞선 query/evidence 실험에서 드러난 문제를 순서대로 고친 결과다.

1. `llm-wiki.md` 단일 문서 ingest/query

- 입력: `<chat-wiki-source-lab>/inputs/llm-wiki.md`
- 목적: LLM Wiki 문서 하나를 pipeline에 넣었을 때 source/concept page가 어떻게 생성되고 query에 쓰이는지 확인했다.
- 확인한 문제:
  - source/concept page는 생성되지만 query에서 원문 근거가 충분히 세밀하게 선택되지 않았다.
  - `Ingest`, `Query`, `Lint` 같은 workflow 설명이 observation으로만 축약되면 역할/흐름 질문에서 근거가 약해졌다.
- 반영:
  - workflow/operation/maintenance task가 section/core 후보가 되도록 semantic extraction prompt를 보완했다.

2. 싱글턴 채팅 원문 문서화 실험

- 입력 산출물: `<chat-wiki-source-lab>/runs/실제 쿼리결과로 한 결과(싱글턴)/chat-transcript-source.md`

- 확인한 문제:
  - 현재 채팅을 원문 문서로 만드는 책임은 llmPipeline보다 Spring/backend 쪽에 두는 편이 자연스럽다.
  - query 결과 저장, source/concept page 생성, evidence 연결을 제품 기능으로 보려면 backend가 원문 문서 id와 pipeline run id를 추적해야 한다.

  - query test set에 싱글턴, 멀티턴, 내부 문서 있음, 내부 문서 없음, 내부+외부 혼합 질문이 모두 필요했다.

- invalid backslash가 포함된 JSON 문자열에서 literal backslash를 보존하며 parsing되는 것을 확인했다.

### 남은 주의사항

- `wiki_embedding_vectors.embedding_vector`는 아직 실제 dense vector 생성까지 연결된 상태가 아니다. 현재 핵심은 canonical representation과 unit/page 연결 구조다.
- cleaned markdown 중 일부는 원문 전체 복원이 아니라 ingest 가능한 수준의 정리본이다. provenance 표시가 필요하다.
- Spring이 DB migration을 소유한다면 `wiki_embedding_vectors`, `wiki_embedding_units` 스키마를 Flyway/Liquibase로 옮겨야 한다.
- query 응답에서 citation은 이제 자동 주입하지 않으므로, LLM이 citation을 누락하면 `evidence_snippets`가 비어 있을 수 있다. 이 경우 evaluator feedback loop에서 재시도하는 정책이 필요하다.
