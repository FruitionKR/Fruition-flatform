# 2026-06-17 이슈

## 미결 이슈

### 1. Query 처리 event 실시간 중계와 Agent 채팅 진행 상태 연동

**현황**

`llmPipeline` Query 처리 과정에서는 `query_started`, `query_rewritten`, `retrieval_scored`, `web_search_started`, `answer_generated` 같은 단계별 event를 발행할 수 있다.
하지만 현재 Spring 백엔드는 해당 event를 프론트엔드에 실시간으로 전달하지 않고, 프론트엔드는 `/api/query` 최종 응답과 `/api/chat/messages` 채팅 기록만 사용한다.

현재 Agent 채팅의 진행 상태 UI는 실제 event 기반이 아니라 프론트엔드의 정적 3단계 표시다.

- `질문 분석`
- `관련 Wiki page 검색`
- `근거 기반 답변 작성`

**문제**

사용자는 Query 처리 중 실제 진행 상황을 확인할 수 없다.
내부 Wiki 검색, graph traversal, web search fallback 같은 분기 정보가 pipeline event에는 존재하지만, 현재 UI에는 반영되지 않는다.

**백엔드 선행 작업**

Spring 백엔드에서 Query 처리 event를 프론트엔드가 구독할 수 있는 형태로 제공해야 한다.

후보 방향:

- `POST /api/query` 요청 시 Query 실행 식별자(`requestId` 또는 `runId`)를 만든다.
- Spring이 pipeline 호출 시 `log_callback_url` 또는 이에 준하는 callback URL을 전달한다.
- pipeline이 callback으로 보낸 `{ event_type, stage, message, data }` 로그를 Spring이 수신한다.
- Spring이 SSE, streaming response, 또는 WebSocket 중 하나로 프론트엔드에 event를 중계한다.
- 최종 답변 응답과 진행 event는 분리하되, 같은 Query 실행 단위로 매칭 가능해야 한다.

권장 방향:

- 프론트엔드 단순화를 위해 SSE 기반 endpoint를 우선 검토한다.
- 예: `GET /api/query/events/{requestId}`

**프론트엔드 후속 작업**

백엔드 event 중계 API 계약이 확정된 뒤 프론트엔드를 수정한다.

수정 방향:

- Agent query 제출 시 Query 실행 식별자를 확보한다.
- event stream을 구독해 `stage`, `message`, `data`를 Agent 진행 상태 UI에 반영한다.
- `retrieval_scored`의 `top_sources`, `top_concepts`는 후보 근거/검색 결과 UI에 연결할 수 있는지 검토한다.
- `web_search_started`, `web_search_answer_generated`는 내부 Wiki fallback이 아니라 웹 검색 fallback 경로임을 UI에서 구분한다.
- 최종 assistant 메시지와 references는 기존처럼 최종 응답 또는 `/api/chat/messages` refresh 결과를 기준으로 표시한다.

**현재 구현 위치**

- 프론트 Query 호출: `frontend/app/_lib/api.ts` `queryWiki()`
- 프론트 채팅 panel: `frontend/app/_components/agent-panel/AgentPanel.tsx`
- 프론트 진행 상태 표시: `frontend/app/_components/agent-panel/StatusList.tsx`, `frontend/app/_components/agent-panel/agentData.ts`
- Spring Query API: `backend/src/main/java/fruition/query/controller/QueryController.java` `POST /api/query`
- Spring pipeline 호출: `backend/src/main/java/fruition/query/repository/PipelineQueryRequester.java`
- pipeline event 발행: `llmPipeline/app/modules/query/application/answer_query.py` `_publish()`
- pipeline event publisher: `llmPipeline/app/modules/query/infrastructure/query_event_publisher.py`

**결정 필요 사항**

- event 중계 방식: SSE, streaming response, WebSocket 중 무엇을 사용할지 결정한다.
- Query 실행 식별자 이름과 수명: `requestId`, `runId` 등.
- event payload 계약: `stage`, `message`, `data` 외에 timestamp, sequence, query id를 포함할지 결정한다.
- 프론트가 stream 연결 실패 시 기존 최종 응답 기반 UI로 fallback할지 결정한다.

**검증 기준**

- Query 실행 중 프론트 Agent 패널에 실제 backend/pipeline event message가 순서대로 표시된다.
- 내부 Wiki 경로와 web search fallback 경로가 UI에서 구분된다.
- 최종 답변과 진행 event가 중복 메시지로 표시되지 않는다.
- event stream이 실패해도 최종 답변 조회 흐름은 깨지지 않는다.
