## L2. ~~본문 key 체계 변경 · 기여 조각 저장~~ — **완료**

> 2026-08-04 확인: `dev`에 구현돼 있습니다. Backend의 검증 규칙과 경로가 정확히 일치합니다. 아래는 계약 기록용으로 남깁니다.

### 2-1. 작업별 불변 key로 쓰기 (덮어쓰지 않기)

현재는 slug/document_id 기준 경로에 **매번 덮어씁니다.**

| 위치 | 현재 key |
|---|---|
| `postgres_wiki_output_persistence.py:99` | `wiki/{user_id}/{workspace_id}/sources/{document_id}.md` |
| `postgres_wiki_output_persistence.py:164` | `wiki/{user_id}/{workspace_id}/concepts/{slug}.md` |
| `postgres_wiki_ingestion_repository.py:621` | 동일 패턴 |

바꿀 형태:

```
wiki/{workspace_id}/pages/{page_id}/ops/{operation_id}.md     본문
wiki/{workspace_id}/pages/{page_id}/ops/{operation_id}.json   기여 조각
```

**덮어쓰지 않아야 하는 이유**: Backend가 콜백을 받아 그 시점 본문을 `wiki_page_versions`에 사본으로 남깁니다. 되돌릴 때는 그 사본을 새 revision으로 쌓으면 되므로 저장소를 다시 쓰지 않습니다. 다만 재조립(L4)은 **기여 조각을 다시 읽어야** 하므로, 조각만큼은 덮어쓰면 안 됩니다.

**`slug`가 아니라 `page_id`를 쓰는 이유**: slug는 rename으로 바뀝니다. 바뀌면 예전에 쓴 파일 경로를 다시 찾을 수 없습니다.

Backend는 이 경로를 **정확히 대조**한 뒤에만 읽습니다. 형식이 다르면 422로 거절합니다.

### 2-2. 기여 조각 저장 (신규)

`.json`에 **"이 문서가 이 페이지에 보탠 부분"** 을 남겨 주세요.

개념 페이지는 여러 원문 문서의 내용이 한 편의 글로 합쳐진 결과입니다. 문서 A를 되돌리려 해도 A 부분만 오려낼 수 없습니다. 그래서 되돌리기는 **남은 조각들을 다시 붙여 새로 쓰는** 방식입니다(L4).

조각이 없으면 재작성 자체가 불가능합니다. 형식은 llmPipeline이 재조립에 쓸 수 있으면 되고, Backend는 **경로만 보관**하고 내용을 해석하지 않습니다.

- 완료 조건: 저장한 조각만으로 페이지 재구성이 가능함
- **2026-08-04 확인: `dev`에 이미 구현돼 있습니다.** `operation_artifacts.py`가 `wiki/{ws}/pages/{page}/ops/{op}.{md,json}`로 남기며, Backend의 검증 규칙과 경로가 정확히 일치합니다.

## L3. ~~결과 콜백에 인증 헤더 추가~~ — **완료 (2026-08-05)**

> **2026-08-04 확인.** 콜백을 보내는 코드(`run_pipeline.py`, `pipeline_result_callback.py`)는 이미 있습니다. **인증 헤더만 빠져 있어 Backend가 401로 거절합니다.** 이 한 줄 때문에 ingest 결과가 하나도 들어오지 않습니다.

### 지금 상태

`pipeline_result_callback.py:63`

```python
request = urllib.request.Request(
    callback_url,
    data=body,
    headers={"Content-Type": "application/json; charset=utf-8"},   # ← X-Internal-Token 없음
    method="POST",
)
```

Backend는 이 헤더가 없으면 **401 `INVALID_CALLBACK_TOKEN`** 으로 거절하고, 저장소 객체를 열어보지도 않습니다. 콜백 경로에 인증이 없으면 아무나 결과를 위조해 남의 워크스페이스 위키를 바꿀 수 있어서 뺄 수 없는 검증입니다.

### 고칠 것

```python
headers={
    "Content-Type": "application/json; charset=utf-8",
    "X-Internal-Token": os.environ["INTERNAL_CALLBACK_TOKEN"],
}
```

토큰 값은 Backend의 `app.internal.callback-token`과 같아야 합니다. 두 서비스가 같은 `INTERNAL_CALLBACK_TOKEN` 환경변수를 공유하도록 배포 설정을 맞춰 주세요. Backend 기본값은 로컬 개발용 placeholder이며 배포 환경에서는 주입해야 합니다.

### 재시도 조건도 함께 봐 주세요

현재 재시도는 **422일 때만** 동작합니다(`pipeline_result_callback.py`). 401은 그대로 실패로 끝나 `notification_pending`에 쌓입니다.

토큰이 붙으면 401이 날 일은 없지만, **네트워크 오류·5xx도 재시도 대상**으로 넣어 두는 편이 안전합니다. 422는 "본문을 다시 쓰고 재전송"이고, 5xx는 "그대로 재전송"이라 처리가 다릅니다.

### 완료 조건

- [x] 콜백에 `X-Internal-Token`이 실려 Backend 인증을 통과함
- [x] Backend의 `app.aihistory.ingest-logging-enabled`를 켠 ingest 전체 흐름의 실제 환경 검증 — `docs/backlog/issue-2026-08-05.md`

> 이것이 풀리면 **ingest → 로그 조회 → 되돌리기 → 재조립**이 한 번에 이어집니다. 복구 지시서(L4)는 이미 맞춰져 있고 재조립 결과도 같은 콜백 경로를 씁니다.

### L3 참고 — 콜백 payload 계약

```http
POST {result_callback_url}
X-Internal-Token: {INTERNAL_CALLBACK_TOKEN}
```

```json
{
  "operation_id": "op_a2_7f3c9",
  "operation_type": "ingest",
  "status": "succeeded",
  "workspace_id": "ws_1",
  "user_id": "user_1",
  "target_document_id": "doc_A",
  "summary": "위키 페이지 3개를 갱신했습니다.",
  "changed_pages": [
    { "page_id": "wp_C2",
      "page_type": "concept",
      "markdown_key": "wiki/ws_1/pages/wp_C2/ops/op_a2_7f3c9.md",
      "contribution_key": "wiki/ws_1/pages/wp_C2/ops/op_a2_7f3c9.json",
      "content_hash": "sha256:3c4d..." }
  ]
}
```

**본문은 싣지 않습니다.** 어디에 썼는지와 지문만 보내면 Backend가 검증 후 읽습니다.

| 필드 | 없으면 |
|---|---|
| `operation_id` | 멱등 불가 |
| `page_id` | 기여 이력 누락 → 버전 계산이 어긋남 |
| `markdown_key` | 그 작업의 본문을 특정 못 함 |
| `contribution_key` | **재조립 불가** |
| `content_hash` | 쓰기가 잘렸는지 확인 불가 |

`workspace_id`·`user_id`·`target_document_id`는 **권한 근거로 쓰이지 않습니다.** 요청 등록 때 저장한 값과 일치하는지 대조만 합니다. 생략하면 대조하지 않습니다.

### 응답별 대응

| 응답 | 할 일 |
|---|---|
| 200 | 없음 |
| 200 (같은 `payload_hash` 재전송) | 없음 |
| 401 `INVALID_CALLBACK_TOKEN` | 토큰 확인 |
| 409 `AI_OPERATION_PAYLOAD_CONFLICT` | **중단.** 같은 작업에 다른 결과를 보냈음 |
| 422 `INVALID_CALLBACK_PAYLOAD` | 경로·해시 검증 실패. **다시 쓰고 재전송** |

응답 body는 `{ "operation_id", "status", "recorded_changes" }`입니다. `status`는 Backend가 실제로 확정한 값이라, 부분 실패면 `partially_succeeded`가 옵니다.

### 부분 실패도 만든 것은 보내주세요

`status: "failed"`로 보내더라도 **이미 만들어진 페이지는 `changed_pages`에 담아야 합니다.** 안 보내면 위키에는 페이지가 있는데 이력에 없어서, 그 페이지만 영영 복구 대상에서 빠집니다.

- 완료 조건: 성공·부분 실패·실패 각각에서 콜백 발송 / 안 바뀐 페이지는 `changed_pages`에 미포함 / 재전송 시 동일 payload

| 항목 | 처리 |

## L6. ~~workspace별 ingest 직렬 실행 보장~~ — **현재 단일 프로세스 구성에서 완료**

같은 워크스페이스의 ingest 2건이 동시에 실행되면, 같은 페이지에 대한 콜백이 동시에 도착해 revision 채번이 겹칠 수 있습니다.

`RunPipelineUseCase.execute()` 전체가 전역 `_PIPELINE_EXECUTION_LOCK` 안에서 실행되므로 현재 단일 worker 구성에서는 모든 workspace의 ingest가 직렬화됩니다. 다중 프로세스·인스턴스로 확장할 때는 이 process-local lock으로 부족하므로 DB advisory lock 같은 공유 잠금이 필요합니다.

- 완료 조건: 같은 workspace의 ingest 2건이 동시에 실행되지 않음 — **현재 구성에서 충족**
