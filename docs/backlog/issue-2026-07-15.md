# 2026-07-15 Backend 이슈 — 해결 항목 기록

## 1. query evidence source_refs 노출 (해결)

- **배경**: llmPipeline은 evidence마다 다중 문서 `source_refs`를 보냈으나, backend `PipelineQueryResponse.EvidenceSnippet`에 필드가 없어 Jackson 역직렬화 단계에서 버려졌다. 하나의 rank가 대표 문서 외 다른 문서 block을 참조하면 두 번째 이후 문서 근거가 저장·노출되지 않았다.
- **조치**: `EvidenceSnippet`에 `source_refs`(`[{source_document_id, source_block_id}]`) + 중첩 `SourceRef` 추가, `ChatMessageReference` 도메인·응답 DTO에 `source_refs` 추가, `QueryService` 저장·`ChatSessionController` 조회 매핑 연결, `chat_message_references.source_refs` 컬럼(Flyway `V8`). legacy `source_document_id`/`source_block_ids` 유지(additive).
- **검증**: query·chat 74개 테스트 + 전체 컨텍스트 로딩(`V8` 적용 + `ddl-auto=validate`) 통과. `PipelineQueryResponseTest`에 source_refs 역직렬화, `QueryServiceTest`에 다중 문서 근거 보존 검증 추가.
- **변경 기록**: `docs/changelog/backend.md` 2026-07-21 항목.
- **후속(프론트 소비)**: `docs/issue/frontend/2026-07-15.md` #7.

## 2. documents/wiki_pages FK CASCADE + migration 도구 (해결)

- **배경**: `workspace_id` FK CASCADE가 chat_sessions만 적용됐고, documents/wiki_pages는 애플리케이션 레벨 삭제 유지 + Flyway 미도입 상태였다.
- **조치**: Flyway 마이그레이션 도구 도입(스키마 단일 소스화, `ddl-auto=validate`). `V3__add_workspace_fk_cascade.sql`이 documents·wiki_pages·chat_sessions에 `ON DELETE CASCADE` 적용(workspace 삭제 시 concept page 고아 버그 해소 포함). `V2`가 잔재 unique constraint 제거.
- **참고**: `WorkspaceService.delete`의 앱 레벨 `deleteAllByWorkspaceId`는 이제 DB CASCADE와 중복이나 버그는 아니다(선택적 정리 대상).
- **상세**: `docs/backlog/issue-2026-07-03.md` FK CASCADE 섹션, ADR `docs/spec/pipeline-db-ownership.md`. Flyway 도입 경위는 `docs/backlog/issue-2026-07-16.md`.

## 1. pipeline run 동시 실행 방지

- 여러 문서 동시 업로드 시 DB 큐(PR 55)는 도입됐으나 worker가 POST 직후 큐 항목을 삭제해 pipeline run 동시 실행이 여전히 가능.
- 해결: module-level process-wide `threading.Lock`을 적용해 일반 문서와 Chat Wiki run을 use case 인스턴스와 무관하게 직렬화했다.
- 검증: `llmPipeline/tests/modules/wiki_ingestion/test_run_pipeline.py`, `test_execute_serializes_runs_across_use_case_instances`
- 상세: `docs/backlog/issue-2026-06-29.md` 이슈 1, `docs/backlog/issue-2026-06-26.md` 동시 업로드 처리 순서.

## 2. pipeline run heartbeat

- `pipeline_runs`에 `updated_at` 없음, `touch_pipeline_run` 미구현. backend 측 수신부(`applyPipelineEvent`, `markProcessingHeartbeat`)는 구현 완료 — 송신부만 남음.
- 해결: Flyway V6로 `updated_at`을 추가하고 `PipelineLog.emit()`의 progress callback을 `touch_pipeline_run(run_id)`에 연결했다.
- 실패 정책: heartbeat DB 갱신 실패는 pipeline을 중단하지 않고 `pipeline.log`에 기록한다.
- 검증: `llmPipeline/tests/modules/wiki_generation/test_pipeline_log.py`, `llmPipeline/tests/modules/wiki_ingestion/test_pipeline_run_heartbeat.py`
- 상세: `docs/backlog/issue-2026-06-26.md` llmPipeline heartbeat, `docs/backlog/issue-2026-06-29.md` 참조 절.

## 3. Markdown 편집 router와 생성 계약 보강

- 일반 `whole_document` 편집과 원문 구조 보존형 cleanup을 template 재구성으로 오분류하던 로컬 guard와 router prompt를 수정한다.
- `insert_after`를 `current_section` 전용 operation으로 추가하고, 현재 섹션 target이 없으면 `clarify`로 반환한다.
- `markdown_create`의 `title`, `summary`, `markdown` 필수 필드를 검증하고, 실패 이유를 포함해 한 번 재시도한 뒤 재실패 시 전용 422를 반환한다.
- `operation_for_edit_goal`로 operation 결정 규칙을 공통화하고, Markdown 생성의 최초 호출과 재시도가 같은 정규화·검증 경로를 사용하도록 정리한다.
- 연동 계약: `docs/spec/agent-markdown-contract.md`, `4.3 edit`, `4.4 generated_markdown`, `7. 오류 처리`; `docs/spec/llmpipeline-backend-output-contract.md`, `3.1 Markdown Edit`, `3.2 Markdown Create`, `3.3 Markdown 계약 오류`
- 구현 위치: `llmPipeline/app/modules/agent/infrastructure/chat_completions_turn_router.py`, `_local_guard`; `llmPipeline/app/modules/markdown_edit/infrastructure/chat_completions_markdown_editor.py`, `generate_markdown`
