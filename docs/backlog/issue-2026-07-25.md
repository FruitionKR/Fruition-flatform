## Backend — wiki maintenance lint 프록시

### 해결 내용

- llmPipeline `POST /wiki/maintenance/lint`를 workspace 범위 public API로 중계하는 Spring 프록시(`fruition.wikimaintenance`)를 추가했다.
- `POST /api/workspaces/{workspace_id}/wiki/maintenance/lint`에서 `workspace_id`를 path, `user_id`를 `@AuthenticationPrincipal`에서 주입한다.
- public body는 `{ materializePromotions, dryRun }`만 받고(둘 다 optional), LLM provider·model 등 pipeline 튜닝 knob은 노출하지 않고 pipeline 기본값을 사용한다.

## AI/Pipeline — Query 후보와 subgraph DB 조회 제한

### 기존 문제

- Query가 Workspace의 활성 Wiki page와 link 전체를 Python으로 읽은 뒤
  `source_candidate_limit`와 `concept_candidate_limit`를 적용했다.
- 최종 답변 후보 수는 작아도 DB 반환 row, Markdown 로드, scoring 비용은
  Workspace 전체 크기에 비례했다.

### 해결 내용

- `WikiRepositoryPort`의 전체 Workspace 조회를 Source/Concept별 bounded 후보,
  후보에 닿는 bounded link, link 반대쪽 page의 bounded ID 조회로 교체했다.
- PostgreSQL은 page metadata와 embedding unit 본문에서 keyword 후보를
  제한하고, Workspace 전체 저장 page embedding에서 semantic 후보를 별도로
  제한해 합친다. 합친 후보만 Markdown을 로드한 뒤
  `embedding 60% + keyword 40%` hybrid 점수로 최종 순위를 정한다.
- Query use case는 최종 Source/Concept 상한의 4배만 scoring pool로 요청하고
  graph link는 최대 200개만 로드한다.
- 초기 lexical 후보 밖의 직접 연결 Concept·Source도 bounded link의 endpoint면
  page를 보충해 graph traversal에서 누락하지 않는다.
- 전역 link 상한 안에서 frontier를 최대 3단계 반복 조회해 `max_depth=3`
  traversal 계약을 유지한다.
- traversal은 각 hop의 감쇠 path score가 아니라 최초 최고 seed 점수의 95%를
  고정 하한으로 사용해 점진적인 relevance drift를 막는다.
- evidence, related page, traversal path 조립 계약은 유지한다.

- Query 호출 경계:
  `llmPipeline/app/modules/query/application/answer_query.py`의
  `_score_wiki_candidates`
- 저장소 계약:
  `llmPipeline/app/modules/query/application/ports.py`의 `WikiRepositoryPort`
- PostgreSQL bounded 조회:
  `llmPipeline/app/modules/query/infrastructure/postgres_wiki_repository.py`의
  `list_candidate_pages`, `list_links_for_page_ids`, `list_pages_by_ids`
- 테스트:
  `llmPipeline/tests/modules/query/test_answer_query.py`,

## AI/Pipeline — Legacy `source_related_to` 정리 절차와 계약 정합화

### 기존 문제

- 재ingest한 Workspace는 저장 과정에서 legacy row가 지워졌지만, 재ingest하지
  않은 Workspace에는 기존 `source_related_to`가 남았다.
- Query와 traversal은 이 edge를 사용하지 않는데 계약 문서는 여전히 원본
  link로 생성·저장한다고 안내했다.

### 해결 내용

- Workspace/user scope의 legacy `source_related_to` row 수를 확인하고 삭제하는
  `llmPipeline/cleanup_source_related_links.py` 운영 명령을 추가했다.
- 명령은 기본 dry-run이며 `--apply`를 명시한 경우에만 같은 scope의 row를
  삭제한다.
- `docs/spec/query-engine.md`에서 `source_related_to` 생성·저장·traversal
  계약을 제거했다.
- `docs/spec/llmpipeline-backend-output-contract.md`에서
  `source_related_to`를 원본 `link_type` 예시에서 제외했다.
- 관련 Source 기능은 실제 소비 endpoint, 결과 상한, 정렬 기준이 확정될 때
  별도 계약으로 작성하며 미리 materialize하지 않는다.

### 운영 절차

```bash
cd llmPipeline

# 삭제 대상 수 확인
PYTHONPATH=. .venv/bin/python cleanup_source_related_links.py \
  --user-id <user_id> \
  --workspace-id <workspace_id>

# 확인한 Workspace만 실제 삭제
PYTHONPATH=. .venv/bin/python cleanup_source_related_links.py \
  --user-id <user_id> \
  --workspace-id <workspace_id> \
  --apply
```

환경별 운영자는 먼저 dry-run의 `matched_count`를 확인한 뒤 같은
`user_id`/`workspace_id`로 `--apply`를 실행한다.

  `FOR SHARE OF d, w`로 잠가 삭제와 완료의 경합을 차단한다.
- 비활성 document에는 완료·실패 상태나 Wiki 산출물을 기록하지 않는다.
- workspace가 삭제 중 완료된 산출물은 폐기하고, 복구 뒤에도 해당 run의
  산출물을 자동 반영하지 않는 정책으로 정했다.
