# 2026-06-29 이슈

## llmPipeline 구현 과제

### 배경

backend에서 문서 처리 DB 큐(`document_processing_queue`)를 구현했다.
큐는 pipeline POST 발송 순서를 보장하고 서버 재시작 시 유실을 방지하지만,
llmPipeline의 `BackgroundTasks`는 요청마다 별도 스레드에서 실행되므로 실제 동시 실행은 막지 못한다.

동시 실행이 발생하면 아래 두 문제가 생길 수 있다.

- 두 pipeline이 같은 concept slug로 동시에 INSERT 시도 → unique constraint violation → pipeline 실패
- LLM API 동시 호출 증가 → rate limit 초과 가능

## 이슈 1: 동시 실행 방지

### 관련 문서

- `docs/backlog/issue-2026-06-26.md` "여러 문서 동시 업로드 시 처리 순서 보장 > 구현 선택지" — 선택지 목록 및 배경 설명

### 현재 상태

backend DB 큐(`docs/backlog/issue-2026-06-26.md` "구현 선택지 1")를 구현했으나,
`POST /pipeline/runs` 응답이 pipeline 완료 전에 즉시 반환되므로 동시 실행이 여전히 발생한다.

### 선택지

**A. asyncio.Lock (llmPipeline 내부 단일 실행)**

`api.py`에 전역 `asyncio.Lock`을 두고 `_execute_pipeline_run` 실행 시 lock을 획득한다.
이전 pipeline이 끝나야 다음이 시작된다.

```python
_pipeline_lock = asyncio.Lock()

async def _execute_pipeline_run_locked(run_id, args):
    async with _pipeline_lock:
        await asyncio.to_thread(_execute_pipeline_run, run_id, args)
```

- 장점: llmPipeline이 순차 실행을 자체적으로 보장
- 단점: FastAPI async 구조 변경 필요

**B. backend가 `wait=true`로 POST**

`POST /pipeline/runs`에 `"wait": true`를 포함하면 llmPipeline이 pipeline 완료 후 응답을 반환한다.
backend worker는 HTTP 응답을 받는 시점에 다음 항목을 처리하므로 자연스럽게 순차 실행된다.
llmPipeline 코드 변경 없이 backend `DocumentProcessingRequester` 수정만으로 해결 가능하다.

- 장점: llmPipeline 수정 불필요, backend 변경만으로 해결
- 단점: HTTP 연결이 pipeline 실행 시간(수 분) 동안 열려 있어야 함. HTTP 타임아웃을 충분히 늘려야 함.

### 검증 기준

- 문서 3개를 동시에 업로드하면 pipeline run이 하나씩 순차 실행된다.
- 첫 번째 pipeline run이 완료 또는 실패한 후 두 번째가 시작된다.

## 이슈 2: concept wiki page INSERT 충돌 방지

### 배경

이슈 1이 해결되지 않은 상태에서 두 문서가 동시에 처리되고 둘 다 같은 concept(예: "Python")을 포함하면,
두 pipeline이 동시에 같은 slug로 `wiki_pages` INSERT를 시도한다.
현재 INSERT 구문에 ON CONFLICT 처리가 없으면 unique constraint violation으로 pipeline이 실패한다.

### 해결 방향

concept wiki page INSERT 시 ON CONFLICT 처리를 추가한다.

```sql
INSERT INTO wiki_pages (id, slug, ...) VALUES (...)
ON CONFLICT (slug) DO NOTHING
-- 또는 필요하면 DO UPDATE SET ...
```

수정 위치: llmPipeline concept page 생성 코드 (wiki_ingestion 또는 wiki_generation 모듈 내 INSERT 구문)

### 검증 기준

- 같은 concept을 포함한 문서 두 개를 동시에 처리해도 unique constraint violation이 발생하지 않는다.
- 먼저 완료된 pipeline의 concept page가 유지된다.

## 이슈 3: 삭제된 문서 pipeline graceful handling

### 배경

backend에서 `DELETE /api/documents/{document_id}`가 추가됐다.
문서가 처리 중(`status=processing`)일 때 삭제하면 pipeline은 계속 실행되다가
완료 시 `finish_pipeline_run()`을 호출한다.
이 시점에 backend의 document row가 없으므로 callback이나 DB 접근에서 오류가 생길 수 있다.

### 해결 방향

`finish_pipeline_run()` 및 pipeline 완료 처리 흐름에서 document row가 없을 때 오류 없이 skip한다.
backend `POST /api/documents/{id}/pipeline-events`는 이미 document 없을 때 404를 반환하며,
llmPipeline의 `PipelineLog.emit()`은 callback 실패를 무시하고 계속 진행하는 구조이므로 이 경로는 안전하다.
확인이 필요한 위치는 `finish_pipeline_run()` 내부의 document 관련 DB 접근이다.

### 검증 기준

- processing 중인 문서를 삭제한 뒤 pipeline이 완료돼도 llmPipeline에서 오류가 발생하지 않는다.

## 참조: heartbeat 구현 (미완료)

상세 설계는 `docs/backlog/issue-2026-06-26.md` "문서 처리 상태 신뢰성 개선 > llmPipeline 구현 범위"에 기술돼 있다.

주요 작업:
- `pipeline_runs.updated_at` 컬럼 추가 및 갱신
- `touch_pipeline_run(run_id)` heartbeat 함수 추가
- `PipelineLog.emit()`마다 `touch_pipeline_run()` 호출
- `GET /pipeline/runs/{run_id}` 응답에 `updated_at` 포함

현재 backend는 `POST /api/documents/{id}/pipeline-events` callback으로 `processing_updated_at`을 갱신하는 구조까지 구현됐다.
llmPipeline의 `PipelineLog.emit()` callback 전송은 이미 있으므로, llmPipeline 측 heartbeat DB 갱신만 남아 있다.
