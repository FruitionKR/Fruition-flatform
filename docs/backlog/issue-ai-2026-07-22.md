## Agent 전체 편집 line 계산과 500 응답 보호

### 기존 문제

- target을 생략한 전체 편집은 `str.splitlines()`로 마지막 line을 계산해 후행 `\n`·`\r\n`의 빈 line을 누락했다.
- Markdown 편집 검증기는 같은 입력을 한 line 더 긴 문서로 판단해 `whole_document target must cover the entire Markdown document` 400을 반환할 수 있었다.
- 예상하지 못한 Agent 예외를 `detail=str(exc)`로 반환해 내부 endpoint·경로·provider 응답이 노출될 수 있었다.

### 해결

- `_whole_document_target()`이 Markdown 편집 도메인의 `markdown_line_count()`를 사용하도록 통일했다.
- generic exception의 상세는 server log에 남기고 HTTP 500은 `internal_server_error` code와 고정 message만 반환한다.
- `\n`·`\r\n` 후행 개행과 내부 예외 문자열 비노출 회귀 테스트를 추가했다.

### 확인 위치

- line 계산: `llmPipeline/app/modules/agent/application/handle_agent_turn.py`의 `_whole_document_target`
- 오류 변환: `llmPipeline/app/modules/agent/interfaces/http/routes.py`의 `handle_agent_turn`
- 테스트: `llmPipeline/tests/modules/agent/test_handle_agent_turn.py`, `llmPipeline/tests/modules/agent/test_agent_routes.py`

## Wiki maintenance lint HTTP 경계와 응답 계약

### 기존 문제

- `POST /wiki/maintenance/lint`가 `llmPipeline/api.py`에서 PostgreSQL repository와 LLM client를 직접 조립해 `wiki_ingestion` HTTP 경계 밖에 있었다.
- 성공 응답이 raw dict로 반환돼 HTTP 경계에서 top-level lint 계약을 검증하지 않았다.

### 해결

- endpoint와 Pydantic schema를 `llmPipeline/app/modules/wiki_ingestion/interfaces/http/`로 이동했다.
- `WikiMaintenanceCommand`와 `WikiMaintenancePort`로 HTTP 입력과 infrastructure 실행 경계를 분리했다.
- 기존 top-level 응답 필드를 `WikiLintOut` response model로 명시해 HTTP 경계에서 검증한다.
- 예상하지 못한 500 응답은 내부 exception 문자열을 노출하지 않는다.

### 확인 위치

- endpoint: `llmPipeline/app/modules/wiki_ingestion/interfaces/http/routes.py`의 `POST /wiki/maintenance/lint`
- 요청·응답 계약: `llmPipeline/app/modules/wiki_ingestion/interfaces/http/schemas.py`의 `WikiLintIn`, `WikiLintOut`
- infrastructure: `llmPipeline/app/modules/wiki_ingestion/infrastructure/wiki_maintenance.py`의 `PostgresWikiMaintenance`
- API 계약 문서: `docs/spec/llmpipeline-backend-output-contract.md`의 `5. Lint`, `POST /wiki/maintenance/lint`
- 테스트: `llmPipeline/tests/modules/wiki_ingestion/test_wiki_maintenance_routes.py`

## PDF 복원 전수 평가와 원본 보존 검증

### 기존 문제

- PDF 4개, 30페이지의 사람 기준 전수 평가 완료 사실이 활성 이슈에 반영되지 않았다.
- 최종 local evaluator의 후보 선별은 수식을 명시적으로 제외했고, 표 Vision 결과가 원본 crop의 숫자·부호·값을 빠뜨려도 형식만 맞으면 통과할 수 있었다.

### 해결

- 제목·본문·표·수식·그림·참고문헌 445 block 전수 평가와 93.03% 결과를 `docs/pdf-to-markdown-guide.md`의 `전체 30페이지 사람 기준 전수 평가`에 기록했다.
- 모든 `equation_candidate`를 원본 crop 필수 검토 대상으로 포함하고 현재 Markdown과 원본의 수식 행·항·계수·연산자·분모·지수·첨자·부호를 대조한다.
- 표의 `corrected`·`match`·text-layout 결과는 PDF word 좌표의 행·열별 cell token과 Tesseract TSV에서 확인한 이미지 부호를 보존해야 채택한다. Tesseract 실행에 실패하면 text-layout 결과를 자동 채택하지 않고 Vision 검증으로 넘긴다.
- 공통 검증에 실패한 text-layout 결과는 자동 채택하지 않고, 실패 근거를 Vision 재검토에 전달한다.
- 변경된 resume 결과가 이전 평가와 섞이지 않도록 evaluator flow를 `local_first_v10`으로 갱신했다.

### 확인 위치

- evaluator: `llmPipeline/app/modules/document_evaluation/infrastructure/local_document_evaluator.py`의 `needs_local_review`, `vision_prompt`, `is_valid_table_result`
- 전수 평가: `docs/pdf-to-markdown-guide.md`의 `전체 30페이지 사람 기준 전수 평가`, `결론과 해석 범위`
- 테스트: `llmPipeline/tests/modules/document_evaluation/test_local_document_evaluator.py`
