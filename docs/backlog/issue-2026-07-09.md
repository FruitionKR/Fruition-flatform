# 2026-07-09 이슈

## llmPipeline 후속 작업: 채팅 full 재생성 inline markdown 계약 지원 (하드 블로커)

### 배경

채팅 full **재생성**(이미 위키가 연결된 세션을 다시 full로 export)에서, 백엔드는 이제 **기존 export 문서를 재사용**하고 다음처럼 요청한다:

- MinIO 원본 문서: 세션 **전체**를 다시 직렬화해 덮어쓰기(누적 기록).
- 파이프라인 요청: 기존 `document_id` **+** `input_markdown`(미편입 문답 delta만 직렬화한 string) 동시 전송.

백엔드 구현은 완료됐지만, **현재 llmPipeline이 이 요청을 못 받는다.** 그래서 파이프라인이 아래대로 바뀌기 전까지 **full 재생성은 실패로 처리**된다(문서 status=failed).

### llmPipeline이 해야 할 일

1. **`document_id` + `input_markdown` 동시 수용.**
   현재 `PipelineRunIn`(llmPipeline `api.py:47~91`)의 `exactly_one_input` 검증은 `document_id`/`input_markdown`/`input_path` 중 **하나만** 허용해 둘을 같이 주면 `ValueError`다. 이 규칙을 완화해 "**`document_id`는 신원, `input_markdown`은 내용**"으로 처리해야 한다.
2. **`document_id`를 신원으로 사용.**
   inline 경로는 지금 `document_id = f"api-inline-{run_id}"`(api.py:372)로 합성 id를 만든다. 이러면 완료·wiki_pages·source_blocks·`source_of` 링크가 우리 `chat_export` 문서 id가 아닌 합성 id로 기록돼, 백엔드 `ChatWikiExportReconciler`(document_id 기준 후처리)와 완료 감지가 전부 깨진다. → 전달된 `document_id`로 완료를 기록해야 한다.
3. **내용은 `input_markdown`에서 읽기.** `document_id`가 있어도 storage를 읽지 말고 inline 값을 처리 입력으로 쓴다.
4. **`selection_mode` 반영.** `PipelineRunIn`에 `selection_mode` 필드가 아예 없어 지금은 무시된다. full 재생성 시 delta를 **기존 세션 source page에 append**(slug=`chat-{session_id}` 등)하도록 이 값을 읽어 분기한다.

### 참고 (위치)

- 백엔드 요청 형태: `DocumentProcessingRequester.PipelineRunRequest`에 `input_markdown`(`@JsonInclude(NON_NULL)`) 추가. 워커 `DocumentService.doRequestProcessing`가 `Document.pipelineInputMarkdown`을 실어 보냄.
- 재생성 판별/직렬화: `chat/service/ChatWikiExportService.export`의 `isRegeneration`(= `full` + `session.wikiPageId != null` + `wikiExportDocumentId != null`). MinIO 갱신·재큐: `DocumentService.regenerateChatExportDocument`.
- 파이프라인 스키마: llmPipeline `api.py:47` `PipelineRunIn`, `:86` `exactly_one_input`, `:356~` `/pipeline/runs`.

### 현재 상태

- 백엔드: 구현·단위테스트 완료. 첫 full·partial·일반 업로드는 기존 `document_id`+storage 그대로(변경 없음). **full 재생성만** inline 경로.
- 남은 것: 위 llmPipeline 4개 항목. 완료 전까지 재생성 실패는 예상된 동작.

## 프론트엔드 후속 작업: 채팅 Wiki화 진행 단계(processing_stage) 폴링 표시

### 배경

채팅 세션 → Wiki page화(export)는 문서 처리 파이프라인을 그대로 탄다. export 요청은 즉시 `202`(문서 `processing` 상태)로 응답하고, 실제 Wiki 생성은 llmPipeline이 비동기로 처리한다.

현재 구조상 **완료(status=completed)를 프론트로 push하는 경로가 없다.** 따라서 프론트는 export 이후 문서 상태를 **폴링**해서 완료를 감지해야 한다. 이때 진행 단계 라벨인 `processing_stage`가 이미 문서 응답에 노출되므로, 같은 폴링 응답에서 함께 읽어 진행 표시에 쓰면 된다(추가 백엔드 작업 없음).

- 백엔드는 파이프라인 heartbeat 콜백에서 `processing_stage`를 저장하고 문서 응답에 노출하는 데까지 완료된 상태다.
- SSE 실시간 push는 도입하지 않는다. 이유와 판단은 아래 "설계 판단" 참고.

### 프론트엔드가 해야 할 일

1. 채팅 export 요청(`202`) 이후, 반환된 문서 id로 문서 상세/목록을 주기적으로 폴링한다.
2. 폴링 응답의 `status`가 `completed`가 되면 완료로 간주하고 폴링을 멈춘다(`failed`면 에러 표시).
3. 폴링 응답의 `processing_stage`(예: `"5. Source Page 생성"`)를 진행 표시 UI에 그대로 노출한다. 값이 없을 수 있으니 null-safe하게 처리한다.
4. 폴링 간격은 1~2초 수준으로 두고, 완료/실패 또는 일정 타임아웃 후 중단한다.

### API 참고 (필드 위치)

문서 응답에 이미 아래 필드가 있다.

| DTO | 필드 | JSON 키 |
|---|---|---|
| `DocumentDetailResponse` | `processingStage` | `processing_stage` |
| `DocumentListResponse.DocumentItem` | `processingStage` | `processing_stage` |
| 위 두 DTO | `processingState` | `processing_state` (running/stalled 계산값) |
| 위 두 DTO | `status` | `status` (completed/failed 등) |

- DTO: `backend/src/main/java/fruition/document/dto/DocumentDetailResponse.java`, `.../DocumentListResponse.java`.
- 두 DTO 모두 `@JsonInclude(NON_NULL)`이라 `processing_stage`가 없으면 키 자체가 빠질 수 있다 → 프론트에서 optional 처리.

### 설계 판단: 폴링 우선, SSE는 보류

- 프론트는 완료 감지를 위해 **어차피 폴링해야 한다**(완료 push 없음). `processing_stage`는 그 폴링에 무료로 얹히므로 별도 실시간 채널이 불필요하다.
- `processing_stage`는 토큰 스트림이 아니라 굵은 단계 라벨이라, 1~2초 폴링 지연은 진행 표시 UX에 충분하다.
- query 기능은 답변을 토큰 단위로 스트리밍하므로 SSE(`QueryEventBroker` + `QueryRunController`)를 쓴다. 이는 스트리밍이라는 강한 이유가 있어서이고, document 단계 표시에는 그대로 적용할 필요가 없다.
- 실시간 진행 로그가 꼭 필요해지거나 동시 문서 폴링 부하가 문제될 때 SSE relay(`DocumentEventBroker` + subscribe 엔드포인트 + `applyPipelineEvent`에서 push)를 query 패턴대로 추가한다.

### 연관 문서

- 백엔드 stage 저장/노출: `backend/src/main/java/fruition/document/domain/Document.java`의 `markProcessingHeartbeat(stage, now)`, `DocumentService.applyPipelineEvent(...)`, 콜백 컨트롤러 `DocumentPipelineController`의 `POST /api/documents/{document_id}/pipeline-events`.
- SSE 참고 구현(query): `backend/src/main/java/fruition/query/service/QueryEventBroker.java`, `.../query/controller/QueryRunController.java`.
