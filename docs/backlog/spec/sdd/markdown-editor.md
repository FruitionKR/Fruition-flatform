## 2. 배경

Markdown 문서의 저장·충돌·이미지·AI 편집 계약은 기능별 SDD에 정의되어 있지만, 사용자가 본문을 작성하고 저장하는 편집기 동작과 프런트엔드 책임 경계는 별도 문서로 정리되어 있지 않다.

현재 `note-editor-prototype.md`와 `NoteEditor` 구현은 CodeMirror·Milkdown 전환과 800ms 자동 저장을 사용한다. 이는 사용성 검증용 프로토타입이며, 운영 제품에서 확정한 Markdown 원문 편집과 수동 저장 정책의 최종 계약이 아니다.

## 3. 목표

- 사용자가 Markdown 원문을 손실 없이 생성·수정할 수 있게 한다.
- 서식·블록·목록·링크·표 입력을 돕되 저장 값은 Markdown으로 유지한다.
- 저장 버튼과 `Cmd/Ctrl+S`를 통한 명시적 저장, 저장 상태, 실패·충돌, 미저장 이탈 동작을 정의한다.
- 이미지 첨부와 AI 편집 기능이 동일한 편집 버퍼 및 문서 버전 계약을 사용하게 한다.
- 제품 정책과 프런트엔드가 결정할 표현·상호작용 세부사항을 분리한다.

## 5. 요구사항

### REQ-ED001 Markdown 원문 편집

- 문서 소유자는 편집 가능한 문서의 전체 Markdown 원문을 불러와 수정할 수 있어야 한다.
- 편집기는 사용자가 입력한 유효한 Markdown을 임의의 block 모델이나 HTML로 영구 변환하지 않는다.
- 제목 기능은 문서 파일명 변경이 아니라 Markdown heading 서식을 뜻한다.
- 문서 전환 시 새 문서의 본문과 버전으로 편집 상태를 초기화한다.

#### 인수 조건

- Given: 문서 소유자가 편집 가능한 Markdown 문서를 연다.
- When: 본문을 수정한다.
- Then: 편집 버퍼에는 수정된 Markdown 원문이 유지되고 서버 본문은 저장 전까지 바뀌지 않는다.

### REQ-ED002 편집 보조 기능

- 편집기는 범위에 명시된 서식·블록·목록·링크·표 기능을 Markdown 문법으로 입력하거나 수정할 수 있게 한다.
- 선택 영역이 있으면 가능한 기능은 선택 영역에 적용하고, 선택 영역이 없을 때의 삽입 규칙은 프런트엔드 정책으로 정한다.
- URL 붙여넣기 자동 링크화, Markdown 자동 변환, 슬래시 커맨드, 외부 서식 붙여넣기의 세부 매핑은 원문 손실과 예기치 않은 변환을 방지할 수 있도록 프런트엔드가 정의하고 테스트한다.
- 지원하지 않는 외부 서식은 실행 가능한 HTML로 삽입하지 않고 일반 텍스트 또는 안전한 Markdown으로 처리한다.

#### 인수 조건

- Given: 사용자가 본문 또는 선택 영역에 편집 명령을 실행한다.
- When: 지원되는 서식이나 구조를 선택한다.
- Then: 같은 의미를 나타내는 Markdown이 편집 버퍼에 반영되고 저장 전까지 서버 상태는 바뀌지 않는다.

### REQ-ED003 로컬 실행 취소와 다시 실행

- 일반 사용자 편집의 undo/redo는 현재 브라우저 편집 세션의 로컬 transaction history로 제공한다.
- undo/redo는 서버 버전 이력이나 AI 복원 이력을 생성하지 않는다.
- 문서를 닫거나 새로고침한 뒤 이전 편집 세션의 undo/redo를 복원하지 않는다.

#### 인수 조건

- Given: 같은 편집 세션에서 사용자가 본문을 여러 번 수정했다.
- When: undo 또는 redo를 실행한다.
- Then: 편집 버퍼만 해당 transaction 이전 또는 이후 상태로 바뀐다.

### REQ-ED004 명시적 수동 저장

- 자동 저장은 제공하지 않는다.
- 저장 버튼과 `Cmd/Ctrl+S`는 동일한 저장 동작을 실행한다.
- 저장은 현재 전체 Markdown, 현재 `base_version`, 신규 이미지가 있으면 attachment를 core·assets SDD의 multipart API로 전송한다.
- 저장 요청 중 추가 편집은 현재 요청에 섞지 않으며 편집 버퍼에 미저장 변경으로 남긴다.
- 저장 성공 응답의 최종 Markdown과 `current_version`을 다음 편집 기준으로 사용한다.
- 본문 변경이 없으면 저장 버튼을 비활성화할 수 있으며, 저장 요청을 보내는 경우 백엔드의 `changed=false` 응답을 정상 처리한다.

#### 인수 조건

- Given: 문서 소유자가 본문을 수정해 미저장 상태이다.
- When: 저장 버튼 또는 `Cmd/Ctrl+S`를 실행한다.
- Then: 한 번의 수동 저장 요청을 보내고 성공한 버전을 새로운 `base_version`으로 표시한다.

### REQ-ED005 저장 상태와 실패

- 편집기는 최소한 `불러오는 중`, `저장됨`, `미저장`, `저장 중`, `저장 실패`, `충돌` 상태를 구분한다.
- 네트워크·서버 오류가 발생하면 현재 편집 버퍼와 미저장 이미지를 유지하고 재저장을 허용한다.
- `409 Conflict`가 발생하면 자동 재시도·자동 병합·서버 본문 덮어쓰기를 하지 않는다.
- 충돌 시 사용자가 최신 서버 본문을 다시 불러오거나 현재 편집 내용을 별도로 보존한 뒤 재편집할 수 있도록 안내한다. 구체적인 충돌 해결 UI는 프런트엔드가 정한다.

#### 인수 조건

- Given: 편집기의 `base_version`이 서버 `current_version`보다 오래되었다.
- When: 사용자가 저장한다.
- Then: `충돌` 상태와 안내를 표시하고 현재 편집 버퍼를 변경하지 않는다.

### REQ-ED006 미저장 이탈 보호

- 저장된 기준 본문과 현재 편집 버퍼가 다르거나 저장되지 않은 이미지가 있으면 미저장 상태로 판단한다.
- 미저장 상태에서 문서 이동, 내부 경로 이동, 새로고침, 탭·창 닫기를 시도하면 이탈 경고를 제공한다.
- 사용자가 이탈을 확정하면 미저장 내용은 폐기한다. 서버와 브라우저 저장소에 draft를 남기지 않는다.
- 권한 상실이나 문서 삭제가 감지되어 더 이상 저장할 수 없는 경우에도 현재 버퍼를 즉시 지우지 않는다.

#### 인수 조건

- Given: 저장하지 않은 변경이 있다.
- When: 사용자가 다른 문서로 이동한다.
- Then: 유지할지 폐기할지 결정하기 전에는 현재 문서를 떠나지 않는다.

### REQ-ED007 이미지 첨부

- 문서 소유자는 파일 선택, 드래그 앤 드롭, 클립보드 붙여넣기로 PNG·JPEG·WebP·GIF 이미지를 편집 버퍼에 추가할 수 있다.
- 저장 전 이미지는 `attachment://<uuid>` placeholder와 브라우저 Blob URL preview로 관리한다.
- 이미지는 별도 업로드 API로 즉시 저장하지 않고 REQ-ED004의 전체 문서 저장에 포함한다.
- SVG와 assets SDD의 크기·개수·형식 제한을 위반한 파일은 저장 가능한 attachment로 추가하지 않는다.
- 저장 성공 후 서버가 반환한 관리 이미지 경로로 placeholder를 치환하고 Blob URL을 정리한다.

#### 인수 조건

- Given: 사용자가 유효한 이미지를 본문에 추가했다.
- When: 문서를 수동 저장한다.
- Then: Markdown과 이미지 bytes를 한 요청으로 보내고 성공 응답의 관리 이미지 경로를 편집 기준으로 사용한다.

### REQ-ED008 읽기 전용 권한

- 문서 소유자가 아닌 워크스페이스 멤버와 읽기 전용 공유 사용자는 문서 본문을 조회할 수 있지만 편집·저장·AI 편집 동작을 사용할 수 없다.
- 프런트엔드에서 편집 UI를 숨기거나 비활성화하더라도 백엔드 권한 검증을 대체하지 않는다.
- 편집 중 소유권이 이전되거나 권한이 회수되어 저장이 거절되면 현재 버퍼를 유지하고 읽기 전용 전환 사실을 알린다.

#### 인수 조건

- Given: 현재 사용자가 문서 소유자가 아니다.
- When: 문서를 연다.
- Then: 내용을 읽을 수 있지만 본문을 변경하거나 저장하는 활성 UI가 제공되지 않는다.

### REQ-ED009 AI 편집 연동

- 편집기는 활성 `document_id`, `base_version`, 현재 편집 버퍼와 선택 범위를 AI 편집 context로 제공한다.
- AI 제안은 현재 버퍼에 바로 반영하지 않고 diff 검토 UI를 먼저 제공한다.
- 사용자가 적용한 AI 결과만 편집기와 서버 본문에 반영한다.
- AI 적용 성공 후 반환된 전체 Markdown과 `current_version`으로 편집 기준과 로컬 undo history를 재설정한다.
- AI 적용·복원·제안 무효화의 상세 계약은 AI editing SDD를 따른다.

#### 인수 조건

- Given: 소유자가 AI 편집 제안을 받았다.
- When: diff를 승인해 적용한다.
- Then: 서버 적용 성공 후에만 편집기가 적용 결과와 새 버전을 표시한다.

### REQ-ED010 미리보기 안전성

- 미리보기 제공 여부와 화면 구성은 프런트엔드가 결정한다.
- 미리보기를 제공하면 Markdown을 신뢰할 수 없는 입력으로 취급하고 raw HTML과 위험한 URL scheme을 실행하지 않는다.
- 인증이 필요한 관리 이미지는 assets·sharing SDD의 접근 경로와 권한을 따른다.
- 미리보기 실패는 편집 버퍼나 저장된 본문을 변경하지 않는다.

#### 인수 조건

- Given: 문서에 script 또는 위험한 링크를 유도하는 Markdown이 포함되어 있다.
- When: 미리보기를 렌더링한다.
- Then: 실행 가능한 스크립트나 금지된 URL이 동작하지 않는다.

### REQ-ED011 접근성과 반응형

- 저장, undo/redo, 주요 서식과 편집 영역은 키보드로 접근 가능해야 한다.
- 키보드 focus는 시각적으로 식별할 수 있어야 한다.
- 모바일 최소 지원 범위에서도 본문 입력, 수동 저장, 저장 상태 확인, 미저장 이탈 경고가 가능해야 한다.
- 지원 브라우저, 화면 너비, 키보드 동작과 WCAG 목표 수준의 정량 기준은 프런트엔드가 확정한다.

#### 인수 조건

- Given: 사용자가 포인팅 장치 없이 편집기를 사용한다.
- When: 편집, 저장, 주요 보조 기능을 이동한다.
- Then: 현재 focus를 식별하며 핵심 문서 편집 흐름을 완료할 수 있다.

## 6. 설계

### 설계 요약

편집기는 서버에서 불러온 Markdown과 버전을 `저장 기준 상태`로, 사용 중인 Markdown과 신규 이미지를 `편집 버퍼`로 관리한다. 두 상태의 차이로 미저장 여부를 계산하며 명시적 저장에만 backend를 호출한다.

서식 UI, slash command, 붙여넣기 변환, 미리보기는 Markdown 편집 버퍼를 입력·출력 경계로 사용한다. 저장·AI 적용 성공처럼 서버 기준이 변경되는 경우에만 응답 본문과 버전으로 저장 기준을 교체한다.

### 상태 흐름

```text
불러오는 중
  → 저장됨
  → 미저장
  → 저장 중
      → 저장됨
      → 미저장       (요청 중 추가 편집)
      → 저장 실패
      → 충돌
```

### 프런트엔드 책임

- 편집 버퍼, 선택 영역, local undo/redo, dirty 상태 관리
- 저장 shortcut과 중복 저장 요청 방지
- 신규 이미지 Blob과 placeholder 수명주기 관리
- 미저장 이탈 경고
- 저장·충돌·권한 상태 표시
- 서식·slash command·paste·table·preview의 상세 UX 결정과 테스트
- 미리보기 sanitization과 접근성 검증

### 백엔드 계약 의존성

- 문서 조회·수동 저장·낙관적 잠금: `markdown-document-core.md`
- multipart 이미지 저장·인증 조회: `markdown-document-assets.md`
- 소유자·멤버·공유 사용자 권한: `markdown-document-sharing.md`
- AI context·diff·적용·복원: `markdown-document-ai-editing.md`

편집기 SDD는 새로운 backend endpoint를 정의하지 않는다.

### 주요 설계 결정

#### DEC-ED001 Markdown을 편집 경계로 유지

- 결정: 운영 편집기의 저장 계약과 기능 간 교환 형식은 Markdown 원문이다.
- 이유: 변환 손실을 막고 기존 backend·AI 계약과 동일한 본문을 사용하기 위해서다.
- 고려한 대안: WYSIWYG block model을 canonical state로 사용.
- 영향 및 단점: 복잡한 표·중첩 구조의 UX는 프런트엔드 구현 난도가 높을 수 있다.

#### DEC-ED002 수동 저장만 제공

- 결정: 저장 버튼과 `Cmd/Ctrl+S`로만 서버에 저장하며 자동 저장과 draft를 두지 않는다.
- 이유: 확정된 문서 core 정책과 충돌·이미지 원자 저장 계약을 일치시키기 위해서다.
- 고려한 대안: 800ms debounce 자동 저장, 브라우저 draft.
- 영향 및 단점: 사용자가 명시적으로 저장해야 하며 이탈 경고가 필수다.

#### DEC-ED003 표현 세부사항은 프런트엔드에 위임

- 결정: 제품 기능의 존재와 데이터·보안 경계는 이 SDD에서 정의하고, 입력 방식과 시각 표현은 프런트엔드가 결정한다.
- 이유: 편집 라이브러리와 상호작용 설계에 따라 최적 동작이 달라지기 때문이다.
- 고려한 대안: SDD에서 모든 키 입력과 화면 배치를 고정.
- 영향 및 단점: 구현 전에 미결정 사항을 프런트엔드 설계 문서 또는 task에서 확정해야 한다.

#### DEC-ED004 프로토타입 자동 저장은 운영 정책으로 승계하지 않음

- 결정: 현재 `useNoteAutosave`와 local mock 저장은 검증용 구현으로만 취급한다.
- 이유: 운영 제품은 수동 저장만 제공하기로 확정했다.
- 고려한 대안: 프로토타입 동작을 운영 요구사항으로 유지.
- 영향 및 단점: 운영 전환 시 자동 저장 호출부와 상태 모델을 수동 저장 흐름으로 변경해야 한다.

### 영향 범위

- 변경 대상: Markdown 편집 화면, 저장 상태 관리, 이미지 첨부 UI, AI 편집 연결부
- 기존 API 영향: 없음. 선행 SDD의 API를 사용한다.
- 데이터 영향: 없음. 편집기 로컬 상태만 추가한다.
- 배포 및 운영 영향: frontend 번들, 브라우저 호환성, sanitization 정책 검증이 필요하다.
