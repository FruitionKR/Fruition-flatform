# 2026-06-26 이슈

## 문서 처리 상태 신뢰성 개선

### 배경

현재 `documents.status=processing`만으로는 실제 pipeline worker가 살아서 처리 중인지 판단할 수 없다.
이 값은 문서가 처리 대상으로 등록됐다는 의미에 가깝고, pipeline run 생성 실패, worker 중단, 장시간 무응답 상태를 구분하지 못한다.

목표는 진행률 표시가 아니라 다음 상태를 신뢰성 있게 구분하는 것이다.

- pipeline 시작 전 또는 요청 중
- 실제 처리 중
- heartbeat가 끊긴 멈춤 의심 상태
- 실패
- 완료

### 결론

`run_id 저장 + heartbeat/updated_at 갱신 + timeout 기반 stalled 판정`을 구현한다.

현재 `llmPipeline`에는 이미 `POST /pipeline/runs`의 `log_callback_url` 입력과 `PipelineLog.emit()` callback 전송 구조가 있으므로, 추천 구현은 callback 방식이다.
Spring이 문서 목록 조회마다 `GET /pipeline/runs/{run_id}`를 호출하는 방식도 가능하지만, 문서 수가 늘면 목록 조회 비용과 장애 결합도가 커진다.

### 추천 상태 모델

문서의 원본 상태는 기존 `status`를 유지하고, 프론트 판단용 파생 상태를 별도로 제공한다.

```json
{
  "id": "doc_123",
  "status": "processing",
  "processing_state": "running",
  "pipeline_run_id": "5a1...",
  "processing_started_at": "2026-06-26T07:00:00Z",
  "processing_updated_at": "2026-06-26T07:00:42Z",
  "elapsed_seconds": 42
}
```

`processing_state` 후보:

- `starting`: 문서는 생성됐지만 pipeline run id가 아직 없음
- `running`: pipeline run이 생성됐고 최근 heartbeat가 있음
- `stalled`: `processing` 상태지만 최근 heartbeat가 없음
- `completed`: 완료
- `failed`: 실패

`queued`는 별도 queue가 생길 때 추가한다. 현재 구조에서는 `starting`과 의미가 겹치므로 1차 구현에서 제외해도 된다.

### llmPipeline 구현 범위

수정 위치:

- `llmPipeline/app/modules/wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py`
- `llmPipeline/run_lab.py`
- `llmPipeline/api.py`

구현 내용:

1. `pipeline_runs.updated_at` 컬럼을 추가한다.

현재 `pipeline_runs` 생성 DDL은 `created_at`, `finished_at`만 가진다.
아래 컬럼을 추가한다.

```sql
updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
```

기존 DB가 이미 생성된 환경도 고려해 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`를 `init_db()`에 추가한다.

2. pipeline run 생성, 완료, 실패 시 `updated_at`을 갱신한다.

- `create_pipeline_run()`: `status='running'`, `updated_at=now()`
- `finish_pipeline_run()`: `status='succeeded'`, `updated_at=now()`, `finished_at=now()`
- `fail_pipeline_run()`: `status='failed'`, `updated_at=now()`, `finished_at=now()`

3. heartbeat 함수 `touch_pipeline_run(run_id)`를 추가한다.

```python
def touch_pipeline_run(run_id: str) -> None:
    with connect() as conn:
        conn.execute(
            """
            UPDATE pipeline_runs
            SET updated_at = now()
            WHERE id = %s AND status = 'running'
            """,
            (run_id,),
        )
```

4. `get_pipeline_run()` 응답에 `updated_at`을 포함한다.

`GET /pipeline/runs/{run_id}`는 fallback 조회나 디버깅에 계속 쓸 수 있어야 한다.

5. `PipelineLog.emit()`마다 heartbeat를 갱신한다.

가장 단순한 구현은 `PipelineLog.emit()`에서 `run_id`가 있으면 `touch_pipeline_run()`을 호출하는 것이다.
단, `run_lab.py`가 DB repository를 직접 import하면 pipeline 실행 코드와 저장소 의존이 섞인다.

권장 구현은 `PipelineLog`에 `touch_callback`을 주입하는 방식이다.

- `PipelineLog.__init__(..., touch_callback: Callable[[str], None] | None = None)`
- `emit()`에서 `self.run_id`와 `touch_callback`이 있으면 호출
- `api.py`가 `run_pipeline(args)` 호출 전 또는 args 구성 시 callback을 전달

단기 구현에서는 import 순환이 없다면 직접 import도 가능하지만, callback 주입이 더 명확하다.

6. 기존 `log_callback_url`은 유지한다.

`PipelineLog.emit()`은 이미 callback URL로 event JSON을 전송한다.
Spring은 이 이벤트를 받아 `documents.processing_updated_at`을 갱신한다.

구현 내용:

`spring.jpa.hibernate.ddl-auto=update`가 켜져 있으므로 JPA 필드 추가로 개발 환경 컬럼 생성은 가능하다.
운영 또는 공유 DB가 있다면 별도 migration이 필요하다.

- `pipeline_run_id`
- `processing_started_at`
- `processing_updated_at`

기존 `error_message`는 실패 사유 기록에 계속 사용한다.

2. `Document`에 상태 변경 메서드를 추가한다.

필요 메서드:

- `markPipelineStarted(String pipelineRunId, Instant now)`
- `markProcessingHeartbeat(Instant now)`
- `markProcessingFailed(String errorMessage, Instant now)`

`markPipelineStarted()`는 `pipeline_run_id`, `processing_started_at`, `processing_updated_at`을 함께 기록한다.
`markProcessingFailed()`는 `status=failed`, `processed_at=now`, `processing_updated_at=now`, `error_message`를 함께 기록한다.

3. `DocumentProcessingRequester.request()`가 `run_id`를 반환하게 변경한다.

현재 구현은 `PipelineRunResponse`를 private record로 받고 로그만 남긴 뒤 예외를 삼킨다.
이 구조에서는 service가 pipeline 요청 실패를 알 수 없다.

변경 방향:

- `PipelineRunResponse`를 외부에서 사용할 수 있게 분리하거나 public record로 변경
- `request(documentId, callbackUrl)` 형태로 callback URL 전달
- 실패 시 예외를 삼키지 않고 throw
- 정상 응답이면 `runId`를 반환

요청 body 예:

```json
{
  "document_id": "doc_123",
  "log_callback_url": "http://backend:8080/api/documents/doc_123/pipeline-events"
}
```

4. pipeline 요청 결과를 문서에 반영한다.

업로드 트랜잭션 커밋 후 pipeline 요청을 보내는 구조는 유지한다.
다만 `afterCommit()` 안에서 단순히 requester만 호출하지 말고, 새 트랜잭션에서 문서를 다시 열어 결과를 저장해야 한다.

권장 구조:

- `DocumentService.requestProcessing(documentId)`를 `@Transactional`로 분리
- 요청 성공 시 `document.markPipelineStarted(response.runId(), now)`
- 요청 실패 시 `document.markProcessingFailed("Pipeline run request failed: ...", now)`

같은 service 내부 자기 호출은 Spring proxy 트랜잭션이 적용되지 않을 수 있으므로, 필요하면 별도 service로 분리한다.

5. pipeline log callback endpoint를 추가한다.

예:

- `POST /api/documents/{documentId}/pipeline-events`

요청 body는 `llmPipeline`의 `PipelineLog.emit()` event 구조를 그대로 받는다.

필수 검증:

- document가 존재해야 한다.
- event의 `run_id`가 문서의 `pipeline_run_id`와 다르면 무시하거나 409로 거절한다.

처리:

- `documents.processing_updated_at = now()`
- 필요하면 마지막 stage/message는 별도 컬럼 없이 로그에만 남긴다.

6. 문서 응답에 `processing_state`를 추가한다.

`DocumentListResponse.DocumentItem`과 `DocumentDetailResponse`에 추가한다.

계산 규칙:

- `status == completed` → `completed`
- `status == failed` → `failed`
- `status == processing && pipeline_run_id == null` → `starting`
- `status == processing && processing_updated_at == null` → `starting`
- `status == processing && processing_updated_at < now - 60초` → `stalled`
- 그 외 `processing` → `running`

`elapsed_seconds`는 있으면 좋지만 1차 구현 필수는 아니다.

7. fallback으로 `GET /pipeline/runs/{run_id}` client를 둘 수 있다.

callback 누락이나 디버깅을 위해 client를 만드는 것은 가능하다.
다만 1차 목록 API에서 매번 pipeline API를 호출하는 구조는 피한다.

- `stalled`: 경고 표시 또는 `stalled` 텍스트
- `failed`: 실패 표시
- `completed`: 완료 표시

표시 문구는 사용자에게 바로 보이는 영역이므로 한글로 바꿔도 된다.
예: `지연`, `실패`, `완료`

### 최소 구현 순서

1. `llmPipeline`의 `pipeline_runs.updated_at`과 `touch_pipeline_run()`을 추가한다.
   - 검증: pipeline run 생성 후 `updated_at`이 존재한다.

2. `PipelineLog.emit()`에서 heartbeat를 갱신한다.
   - 검증: 긴 pipeline 실행 중 log event마다 `pipeline_runs.updated_at`이 갱신된다.

3. backend가 pipeline 요청 성공 시 `pipeline_run_id`를 저장하고 실패 시 `failed` 처리한다.
   - 검증: `POST /api/documents` 이후 문서에 `pipeline_run_id`가 채워진다.
   - 검증: pipeline API가 죽어 있으면 문서가 `failed`가 된다.

4. backend callback endpoint가 `processing_updated_at`을 갱신한다.
   - 검증: `llmPipeline` log event 수신 시 문서의 `processing_updated_at`이 갱신된다.

5. backend 문서 목록/상세 응답에 `processing_state`를 추가한다.
   - 검증: 최근 heartbeat는 `running`, 60초 초과 heartbeat는 `stalled`로 응답한다.

6. frontend가 `processing_state`를 표시하고 polling 조건에 반영한다.
   - 검증: 실제 실행 중, 멈춤 의심, 실패, 완료 상태가 UI에서 구분된다.

### 검증 기준

- pipeline 요청 성공 시 문서에 `pipeline_run_id`가 저장된다.
- pipeline 요청 실패 시 문서가 즉시 `failed`가 되고 `error_message`가 남는다.
- pipeline 실행 중 log event가 발생하면 `pipeline_runs.updated_at`과 `documents.processing_updated_at`이 갱신된다.
- `processing_updated_at`이 60초 이상 오래된 processing 문서는 `processing_state=stalled`로 내려온다.
- 완료 문서는 `status=completed`, `processing_state=completed`로 내려온다.
- 실패 문서는 `status=failed`, `processing_state=failed`와 `error_message`가 함께 내려온다.
- frontend는 `processing` 상태 하나만 보고 spinner를 표시하지 않고, `processing_state`에 따라 running/stalled/failed/completed를 구분한다.

### 주의사항

- callback URL은 컨테이너 네트워크 기준으로 `llmPipeline`에서 접근 가능한 backend 주소여야 한다.
- callback 실패가 pipeline 자체 실패로 이어지면 안 된다. `PipelineLog.emit()`은 현재처럼 callback 실패를 로그만 남기고 계속 진행해야 한다.
- `status`와 `processing_state`를 동시에 내려보내면 일시적으로 값이 어긋날 수 있다. 프론트는 `processing_state`를 표시용으로 우선 사용하고, 최종 완료/실패 판단은 `status`와 함께 본다.
- 문서 목록에서 pipeline API를 직접 조회하는 fallback은 장애 분석용 또는 임시 복구용으로만 사용한다.

## 업로드 문서 실제 삭제 API 추가

### 배경

현재 프론트의 삭제 메뉴는 화면의 tree item만 제거한다.
`frontend/app/_hooks/useProjectTree.ts`의 `deleteContextTarget()`은 `removeTreeItem()`으로 로컬 상태만 갱신하고, backend API를 호출하지 않는다.

backend에도 `DELETE /api/documents/{document_id}`가 없다.
`DocumentController`에는 업로드, 목록, 상태 업데이트, 상세, 원본 조회, block 조회, 이름 변경만 있다.

따라서 지금 동작은 실제 삭제가 아니라 “사이드바에서 숨김”에 가깝다.
새로고침하거나 `GET /api/documents`를 다시 동기화하면 DB에 남아 있는 문서가 다시 나타날 수 있다.

### 결론

문서 삭제는 backend 소유 작업으로 구현하고, frontend는 삭제 API 성공 후 tree 상태를 갱신한다.
단순히 `documents` row만 지우면 source block, wiki link, source wiki page, object storage 원본이 남을 수 있으므로 삭제 범위를 명확히 정해야 한다.

### backend 구현 범위

수정 위치:

- `backend/src/main/java/fruition/document/controller/DocumentController.java`
- `backend/src/main/java/fruition/document/service/DocumentService.java`
- `backend/src/main/java/fruition/document/repository/DocumentRepository.java`
- 필요 시 `SourceBlockRepository`, `DocumentWikiLinkRepository`, `WikiPageRepository`

구현 내용:

1. `DELETE /api/documents/{document_id}`를 추가한다.

응답은 삭제 성공 시 `204 No Content`로 충분하다.

2. 삭제 대상을 정리한다.

최소 삭제 대상:

- `documents` row
- `source_blocks` 중 해당 `document_id`
- `document_wiki_links` 중 해당 `document_id`
- MinIO 원본 object: `documents.source_uri`
- MinIO 추출 text object: `documents.extracted_text_uri`가 있으면 삭제

추가 검토 대상:

- 해당 문서에서 생성된 source wiki page: 현재 source page id는 `source:{document_id}` 형식이다.
- source wiki page markdown object
- 해당 source page와 연결된 `wiki_page_links`
- pipeline run 산출물과 `pipeline_runs`

concept wiki page는 여러 문서가 공유할 수 있으므로 문서 삭제와 함께 바로 삭제하면 안 된다.
source wiki page는 문서 1개에 종속되므로 삭제 대상에 포함하는 편이 자연스럽다.

3. FK와 삭제 순서를 확인한다.

`source_blocks`와 `document_wiki_links`는 문서에 종속된다.
DB FK에 `ON DELETE CASCADE`가 있더라도 JPA 엔티티 삭제 경로에서 실제 DB 제약과 일치하는지 확인해야 한다.

권장 삭제 순서:

- 문서 조회
- 관련 source page id 계산: `source:{documentId}`
- `source_blocks` 삭제
- `document_wiki_links` 삭제
- source wiki page 관련 link 삭제
- source wiki page 삭제
- document 삭제
- DB commit 이후 MinIO object 삭제

MinIO 삭제 실패 정책은 별도로 정해야 한다.
1차 구현에서는 DB 삭제 전에 object를 지우면 DB만 남는 문제가 생길 수 있으므로, DB 삭제 성공 후 object 삭제를 시도하고 실패는 warning log로 남기는 방식이 단순하다.

4. 처리 중 문서 삭제 정책을 정한다.

`status=processing` 문서를 삭제할 수 있게 할지 결정해야 한다.

1차 구현 권장:

- `processing` 문서 삭제는 허용한다.
- pipeline 취소 기능은 별도 이슈로 분리한다.
- 삭제 이후 pipeline callback이 들어오면 문서가 없으므로 404 또는 무시 처리한다.

더 엄격한 구현:

- `processing` 문서 삭제를 409로 막고, 먼저 취소 API를 요구한다.

현재 취소 API가 없으므로 1차 구현에서는 삭제 허용이 더 단순하다.

### frontend 구현 범위

수정 위치:

- `frontend/app/_lib/api.ts`
- `frontend/app/_hooks/useProjectTree.ts`
- 필요 시 삭제 확인 UI가 있는 component

구현 내용:

1. `deleteDocument(documentId)` API 함수를 추가한다.

```ts
export async function deleteDocument(documentId: string): Promise<void> {
  const response = await fetch(`/api/documents/${encodeURIComponent(documentId)}`, {
    method: "DELETE"
  });

  if (!response.ok) {
    throw new Error(await parseErrorResponse(response, "문서 삭제에 실패했습니다."));
  }
}
```

2. 삭제 대상이 backend 문서인지 확인한다.

tree item에 `documentId`가 있으면 backend 문서 삭제 API를 먼저 호출한다.
`documentId`가 없는 로컬 폴더는 기존처럼 로컬 tree에서만 제거한다.

3. 삭제 성공 후 tree item을 제거한다.

API 실패 시 tree에서 제거하지 않고 에러를 표시한다.
현재 전역 toast가 없다면 1차 구현에서는 `apiError` 또는 간단한 alert 정책을 정해야 한다.

4. backend 데이터 refresh를 호출한다.

삭제 후 `GET /api/documents`, `GET /api/wiki/graph`를 다시 받아 graph와 source/concept 목록을 동기화한다.

### llmPipeline 구현 범위

문서 삭제 자체는 backend가 소유한다.
다만 pipeline DB에 다음 데이터가 남을 수 있다.

- `pipeline_runs.document_id`
- run output directory
- object storage에 저장된 wiki markdown

1차 구현에서는 backend DB와 MinIO 원본 삭제를 우선하고, pipeline run 기록은 감사 로그로 남겨도 된다.
source wiki markdown object까지 삭제하려면 backend가 source wiki page의 `markdown_uri`를 조회해서 함께 삭제한다.

pipeline 실행 중 삭제된 문서에 대해 callback이나 finish 처리가 들어올 수 있다.
이 경우 backend 문서 callback은 문서 없음으로 무시하고, llmPipeline의 `finish_pipeline_run()`은 document row가 없을 때 실패하지 않아야 한다.

### 검증 기준

- 프론트에서 업로드 문서를 삭제하면 `DELETE /api/documents/{document_id}`가 호출된다.
- 삭제 API 성공 후 새로고침해도 삭제한 문서가 다시 나타나지 않는다.
- `GET /api/documents`에 삭제한 문서가 포함되지 않는다.
- 삭제한 문서의 `source_blocks`, `document_wiki_links`가 남지 않는다.
- 삭제한 문서의 MinIO 원본 object를 다시 조회할 수 없다.
- 문서에 종속된 source wiki page가 삭제된다.
- 공유될 수 있는 concept wiki page는 문서 삭제만으로 삭제되지 않는다.
- 삭제 API 실패 시 프론트 tree에서 항목이 사라지지 않는다.

## 여러 문서 동시 업로드 시 처리 순서 보장

### 배경

프론트에서 새 문서 여러 개를 한 번에 등록할 때, 서버 측에서 해당 처리 명령이 순차적으로 이행되는지 확인했다.

현재 구조에서는 순차 처리 보장이 없다.

- `frontend/app/_hooks/useDocumentUpload.ts`의 `dropUploadFiles()`는 `uploadItems.forEach(...)` 안에서 각 파일의 `uploadDocumentFile(file)`을 즉시 호출한다.
- 각 업로드 요청은 `await`로 이전 요청 완료를 기다리지 않으므로 브라우저에서 병렬로 나갈 수 있다.
- `backend/src/main/java/fruition/document/service/DocumentService.java`의 `upload()`는 요청 1건마다 문서를 저장하고, commit 이후 `requestProcessingAfterCommit(documentId)`로 pipeline 실행을 요청한다.
- `backend/src/main/java/fruition/document/repository/DocumentProcessingRequester.java`는 pipeline endpoint에 즉시 `POST`를 보낸다.
- `llmPipeline/api.py`의 `POST /pipeline/runs`는 `BackgroundTasks.add_task(_execute_pipeline_run, ...)`로 실행 작업을 등록한다.
- 위 경로 어디에도 전역 queue, lock, 단일 worker executor, 순차 처리 상태 머신이 없다.

따라서 현재 흐름은 다음과 같다.

```text
프론트 병렬 업로드
→ Spring 요청별 문서 저장
→ 각 요청 commit 후 pipeline POST
→ FastAPI background task 등록
```

이 구조에서는 여러 문서를 한 번에 등록했을 때 처리 시작 순서와 완료 순서를 보장할 수 없다.

### 결론

문서 처리 순서가 기능 요구사항이라면 서버 측에서 보장해야 한다.

프론트에서 순차 업로드로 바꾸는 방법도 가능하지만, 다른 클라이언트, 재시도, API 직접 호출, 서버 재시작 이후 재처리까지 제어하지 못하므로 시스템 보장으로 보기 어렵다.

권장 구현은 backend 또는 pipeline 앞단에 문서 처리 queue를 두고 worker concurrency를 `1`로 제한하는 것이다.

### 구현 선택지

1. backend 내부 단일 처리 queue

- 업로드 요청은 기존처럼 문서를 저장하고 즉시 응답한다.
- pipeline 요청은 바로 보내지 않고 queue table 또는 in-memory queue에 넣는다.
- 별도 worker가 `created_at` 또는 queue 순번 기준으로 하나씩 pipeline 요청을 보낸다.
- in-memory queue는 서버 재시작 시 유실될 수 있으므로, 운영까지 고려하면 DB 기반 queue가 더 적절하다.

2. pipeline API 단일 worker queue

- Spring은 지금처럼 pipeline API에 요청한다.
- `llmPipeline`이 run 요청을 queue에 저장하고 단일 worker가 하나씩 실행한다.
- pipeline 처리 순서를 pipeline 서비스가 소유하므로 책임 위치가 명확하다.
- 단, Spring 문서 상태와 pipeline queue 상태를 동기화할 방법이 필요하다.

3. frontend 순차 업로드

- `useDocumentUpload()`에서 `forEach` 대신 `for...of`와 `await uploadDocumentFile(file)`을 사용한다.
- 사용자 선택 파일의 업로드 요청 순서는 맞출 수 있다.
- 서버 측 보장은 아니므로 임시 완화책 또는 UX 정책으로만 보는 것이 안전하다.

### 검증 기준

- 여러 문서를 한 번에 업로드해도 pipeline run이 동시에 실행되지 않는다.
- 첫 번째 문서의 pipeline run이 완료 또는 실패한 뒤 다음 문서의 pipeline run이 시작된다.
- 처리 순서는 사용자가 선택한 파일 순서 또는 서버 queue 생성 순서 중 하나로 명확히 정의된다.
- pipeline API 실패 또는 서버 재시작 후에도 대기 중인 문서가 유실되지 않는다.
- 중복 실행 방지를 위해 한 문서에 대해 active/pending run이 2개 이상 생기지 않는다.
