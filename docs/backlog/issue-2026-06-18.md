# 2026-06-18 이슈

## 미결 이슈

### 1. MinIO 원본 문서 조회 API 추가 필요

**현황**

프론트엔드에서 원본 문서를 클릭하면 실제 raw 원본 파일이 아니라 `source:{document_id}` Wiki page를 연다.
현재 원본문서 패널은 `GET /api/wiki/pages/{wiki_page_id}`를 호출하고, 백엔드는 `wiki_pages.markdown_uri`가 가리키는 MinIO markdown을 읽어 `markdown` 필드로 반환한다.

원본 raw 파일은 업로드 시 MinIO의 `sources/documents/{document_id}/original`에 저장되고, DB `documents.source_uri`에 해당 경로가 기록된다.
하지만 이 MinIO 원본 객체를 프론트엔드가 직접 조회하거나 preview/download할 수 있는 백엔드 API는 아직 없다.

**문제**

사용자가 기대하는 "원본 문서"와 현재 화면에 표시되는 "source page"가 다르다.
PDF 또는 Markdown 원본을 그대로 확인하려면 `documents.source_uri`를 기준으로 MinIO 객체를 읽어 내려주는 백엔드 endpoint가 필요하다.

**백엔드 작업**

후보 endpoint:

```text
GET /api/documents/{document_id}/original
```

구현 방향:

- `document_id`로 `documents` row를 조회한다.
- `Document.sourceUri`의 MinIO object key를 사용해 `MinioClient.getObject()`로 원본 파일을 읽는다.
- 응답에는 `Document.mimeType` 기반 `Content-Type`을 설정한다.
- browser preview/download 정책에 맞춰 `Content-Disposition`을 정한다.
- 문서가 없으면 404를 반환한다.
- MinIO 객체가 없거나 읽기 실패 시 사용자에게 구분 가능한 오류를 반환한다.

**프론트엔드 후속 작업**

백엔드 API가 추가된 뒤 원본문서 클릭 흐름을 정리한다.

- raw 문서 클릭: `GET /api/documents/{document_id}/original` 사용
- source page 클릭: 기존 `GET /api/wiki/pages/{wiki_page_id}` 사용
- 패널 제목과 label을 raw 원본과 source page가 혼동되지 않게 분리한다.

**현재 구현 위치**

- 프론트 원본문서 패널: `frontend/app/_components/SourcePreviewPanel.tsx`
- 프론트 Wiki page 조회 API: `frontend/app/_lib/api.ts` `fetchWikiPage()`
- 프론트 raw 문서 선택 흐름: `frontend/app/_hooks/useTreeSelection.ts` `selectTreeGraphNode()`
- 백엔드 문서 조회 controller: `backend/src/main/java/fruition/document/controller/DocumentController.java`
- 백엔드 문서 service: `backend/src/main/java/fruition/document/service/DocumentService.java`
- 원본 저장 경로 생성: `backend/src/main/java/fruition/document/service/DocumentService.java` `DocumentService.upload()`
- Wiki markdown MinIO 조회 참고 구현: `backend/src/main/java/fruition/wiki/service/WikiService.java` `readMarkdown()`

**검증 기준**

- 업로드된 Markdown 원본을 `GET /api/documents/{document_id}/original`로 조회하면 원문 content가 반환된다.
- 업로드된 PDF 원본을 같은 API로 조회하면 `application/pdf`로 스트리밍된다.
- 존재하지 않는 `document_id`는 404를 반환한다.
- DB에는 있지만 MinIO 객체가 없는 문서는 일반 404와 구분 가능한 오류로 반환된다.
- 프론트에서 raw 문서와 source page preview가 서로 다른 API를 사용한다.

### 2. 채팅 찾은 자료를 `related_pages` 기준으로 복원하도록 저장 구조 정리 필요

**현황**

`llmPipeline` Query 응답은 `related_pages`와 `evidence_snippets`를 모두 반환한다.

- `related_pages`: 질문과 관련된 Wiki page 목록이다. 프론트엔드의 "찾은 자료" 카드 기준이 되어야 한다.
- `evidence_snippets`: 답변 작성에 사용된 문장 단위 근거다. 답변 본문의 `[1]`, `[2]` 같은 citation과 대응해야 한다.

하지만 현재 Spring 백엔드는 `POST /api/query` 처리 후 `related_pages`를 DB에 저장하지 않는다.
대신 `evidence_snippets`만 `chat_message_references`에 저장하고, `GET /api/chat/messages`는 이 저장된 `references`만 반환한다.

현재 프론트엔드 Agent 패널은 `GET /api/chat/messages`의 assistant message `references`를 기준으로 "찾은 자료"를 출력한다.
그 결과 "찾은 자료"가 실제 관련 Wiki page 목록이 아니라 답변 문장 근거 목록 기준으로 표시된다.

**문제**

찾은 자료와 답변 근거의 데이터 성격이 섞여 있다.

- 같은 Wiki page에서 여러 문장이 `evidence_snippets`로 뽑히면 "찾은 자료" 카드가 중복되거나 과다하게 보일 수 있다.
- `related_pages`의 `title`, `slug`, `relevance_score`, `role`, `depth`가 채팅 기록에서 사라진다.
- 새로고침하거나 채팅 기록을 다시 조회하면 `POST /api/query` 당시의 관련 Wiki page 목록을 복원할 수 없다.
- 프론트엔드가 source/concept page 카드 목록과 답변 citation 근거를 명확히 분리할 수 없다.

**권장 백엔드 방향**

`related_pages`는 별도 테이블로 저장하고, `chat_message_references`는 `evidence_snippets` 전용으로 유지한다.

후보 테이블:

```text
chat_message_related_pages
```

권장 컬럼:

| 컬럼 | 설명 |
| --- | --- |
| `id` | row 식별자 |
| `chat_message_id` | assistant message id |
| `wiki_page_id` | related page id. 예: `source:doc_123`, `concept:rag` |
| `page_type` | `source`, `concept`, `web` 등 pipeline 응답의 page type |
| `title` | 관련 page 제목 |
| `slug` | 관련 page slug |
| `relevance_score` | 관련도 점수 |
| `role` | 탐색 중 역할. 예: `seed_source`, `focus_concept`, `neighbor_concept` |
| `depth` | 그래프 탐색 깊이 |
| `rank` | 프론트 표시 순서. `related_pages` 응답 순서 또는 score 정렬 순서 |

`chat_message_references`는 기존처럼 답변 문장 근거만 저장한다.

| 테이블 | 저장 기준 | 프론트 용도 |
| --- | --- | --- |
| `chat_message_related_pages` | `pipelineResponse.relatedPages()` | "찾은 자료" 카드 목록 |
| `chat_message_references` | `pipelineResponse.evidenceSnippets()` | 답변 citation, 문장 근거, quote 표시 |

**API 변경 방향**

새 endpoint를 추가하기보다는 기존 채팅 기록 API를 확장한다.

```text
GET /api/chat/messages
```

assistant message 응답에 `related_pages` 필드를 추가한다.
`references`는 evidence snippet 근거로 유지한다.

예시:

```json
{
  "id": "chat_assistant_xxx",
  "role": "assistant",
  "content": "답변 본문 [1]",
  "status": "completed",
  "created_at": "2026-06-18T10:00:00Z",
  "related_pages": [
    {
      "id": "source:doc_123",
      "page_type": "source",
      "title": "원본 문서 A",
      "slug": "doc-123",
      "relevance_score": 0.91,
      "role": "seed_source",
      "depth": 0,
      "rank": 1
    }
  ],
  "references": [
    {
      "id": 1,
      "reference_type": "source",
      "wiki_page_id": "source:doc_123",
      "page_role": "seed_source",
      "relevance_score": 0.88,
      "rank": 1,
      "paragraph_index": 2,
      "sentence_index": 0,
      "quote": "답변에 실제 사용된 문장..."
    }
  ]
}
```

`POST /api/query` 응답은 현재처럼 `related_pages`와 `evidence_snippets`를 둘 다 반환해도 된다.
다만 query 처리 과정에서 두 데이터를 모두 assistant message id에 묶어 저장해야 한다.

**구현 방향**

1. `ChatMessageRelatedPage` entity를 추가한다.
2. `ChatMessageRelatedPageRepository`를 추가한다.
3. `QueryService.query()`에서 assistant message 저장 후 `pipelineResponse.relatedPages()`를 `chat_message_related_pages`에 저장한다.
4. `QueryService.buildReferences()`는 `evidence_snippets` 전용 저장 로직으로 유지한다.
5. `ChatController.getMessages()`에서 message id 목록으로 related pages와 references를 각각 일괄 조회한다.
6. `ChatMessageResponse` DTO에 `related_pages`를 추가한다.
7. 프론트엔드는 "찾은 자료" 출력 기준을 `message.references`에서 `message.related_pages`로 변경한다.
8. 답변 citation 또는 문장 근거 UI가 필요하면 `message.references`를 별도로 사용한다.

**현재 구현 위치**

- 프론트 찾은 자료 렌더링: `frontend/app/_components/agent-panel/AgentBody.tsx`
- 프론트 채팅 타입: `frontend/app/_lib/types.ts` `ChatMessageResponse`, `ChatMessageReferenceResponse`
- 프론트 채팅 조회 API: `frontend/app/_lib/api.ts` `fetchChatMessages()`
- Spring Query 저장 흐름: `backend/src/main/java/fruition/query/service/QueryService.java` `query()`, `buildReferences()`
- pipeline 응답 DTO: `backend/src/main/java/fruition/query/repository/PipelineQueryResponse.java` `RelatedPage`, `EvidenceSnippet`
- 채팅 조회 API: `backend/src/main/java/fruition/chat/controller/ChatController.java` `getMessages()`
- 현재 evidence 저장 entity: `backend/src/main/java/fruition/chat/domain/ChatMessageReference.java`
- 현재 evidence 응답 DTO: `backend/src/main/java/fruition/chat/dto/ChatMessageReference.java`

**주의할 점**

- `related_pages`와 `evidence_snippets`를 하나의 `references` 배열에 섞지 않는다.
- "찾은 자료" 카드 수는 `related_pages.length`를 기준으로 한다.
- 같은 `wiki_page_id`가 중복 저장되지 않도록 `chat_message_id + wiki_page_id` 기준 중복 제거를 검토한다.
- `related_pages.rank`는 pipeline 응답 순서를 보존하거나 `relevance_score` 내림차순으로 결정한다. 프론트 표시 순서와 일관되어야 한다.
- `evidence_snippets.rank`는 답변 본문의 `[N]` citation과 대응하므로 related page rank와 섞으면 안 된다.

**검증 기준**

- `POST /api/query` 이후 assistant message에 대해 `chat_message_related_pages`와 `chat_message_references`가 각각 저장된다.
- `GET /api/chat/messages` assistant message 응답에 `related_pages`와 `references`가 모두 포함된다.
- 프론트 "찾은 자료 N건"은 `related_pages.length` 기준으로 표시된다.
- 같은 Wiki page에서 여러 evidence 문장이 생성되어도 "찾은 자료" 카드는 page 기준으로 중복 표시되지 않는다.
- 새로고침 후 `GET /api/chat/messages`만 호출해도 이전 답변의 "찾은 자료" 목록이 복원된다.
- 답변 본문의 `[N]` citation은 기존처럼 `references[].rank` 또는 `evidence_snippets.rank`와 대응한다.
