## 미결 이슈

### 1. chat_message_references 테이블 설계: evidence_snippets만 저장, related_pages 영속화 보류

**현황**

현재 `chat_message_references` 테이블은 Query API 응답의 `evidence_snippets`(답변 근거 문장) 기반으로만 구성되어 있다.
Query API 응답에는 `related_pages`(탐색된 Wiki page 목록, `relevance_score`/`role`/`depth` 포함)도 존재하지만, 현재 연결 단계에서는 영속화하지 않는다.

**2026-06-16 결정**

백엔드와 `llmPipeline` Query 연결을 우선 검증하기 위해 `related_pages` 영속화는 보류한다.
현재 단계에서는 `POST /api/query` 응답에 `related_pages`를 포함하되, DB에는 `evidence_snippets` 기반 reference만 저장한다.
이전 채팅 기록에서 관련 Wiki page 목록까지 복원해야 하는 요구가 확정되면 별도 설계를 진행한다.

**추후 결정할 질문**

- `related_pages`를 `chat_message_references`에 `reference_type = "wiki_page"`로 함께 저장할 것인가, 아니면 별도 테이블(`chat_message_related_pages` 등)로 분리할 것인가?
- **같은 테이블에 두면**: `reference_type`으로 구분하되 evidence 전용 필드(`paragraph_index`, `sentence_index`, `quote`)와 related_page 전용 필드(`depth`)가 혼재해 nullable 컬럼이 늘어난다.
- **분리하면**: 테이블은 두 개가 되지만 각 테이블의 스키마가 명확해지고, 조회 시 JOIN 대상이 늘어난다.
- 현재 API 계약(`§ 8.1`)의 `references[]`는 `reference_type`으로 두 종류를 구분하는 단일 배열 구조다. DB 분리 여부와 API 응답 통합 여부를 함께 결정해야 한다.

**현재 구현 상태**

- `chat/domain/ChatMessageReference.java` — evidence snippet 기반 필드 구조 (현재 related_pages 필드 없음)
- `chat/repository/ChatMessageReferenceRepository.java` — 메시지 ID 기준 일괄 조회
- `ChatController` — `ChatMessageReferenceRepository` 조회 결과를 `ChatMessageReference` DTO로 반환
- Query API 응답의 `related_pages`는 현재 `chat_message_references`에 저장되지 않음

**참고 위치**

- API 계약 references 구조: `docs/Fruition_MVP_API_Contract.md` § 8.1
- Query 응답 related_pages 구조: `docs/Fruition_MVP_API_Contract.md` § 7.1
- ChatMessageReference 엔티티: `backend/src/main/java/fruition/chat/domain/ChatMessageReference.java`
- ChatMessageReference DTO: `backend/src/main/java/fruition/chat/dto/ChatMessageReference.java`

### 4. Query 근거 자료에 원문 확인이 어려운 reference가 표시됨

**현황**

오른쪽 채팅의 근거 자료 목록은 `chat_message_references`에 저장된 reference를 그대로 표시한다.
현재 저장 로직은 pipeline의 `evidence_snippets` 중 `page_id`만 있으면 reference로 저장하며, 해당 Wiki page가 실제 상세 화면에서 원문 markdown 또는 source document 연결을 제공하는지 검증하지 않는다.

이 때문에 사용자는 근거 자료를 클릭했을 때 concept/source 원문이 없거나, 원문 자료로 보기 어려운 항목까지 근거 자료로 표시된다고 느낄 수 있다.

**원인**

- `QueryService.buildReferences()`가 `snippet.pageId() == null`만 제외한다.
- `wiki_pages` 존재 여부, `markdown_uri` 존재 여부, `document_wiki_links` 연결 여부, `quote` 공백 여부를 저장 전에 검증하지 않는다.
- 프론트엔드는 `message.references`를 신뢰하고 그대로 표시한다.

**수정 방향**

- 백엔드에서 `chat_message_references` 저장 전 reference 유효성 검증을 추가한다.
- 최소 조건 후보:
  - `wiki_page_id`가 실제 `wiki_pages`에 존재해야 한다.
  - `quote`가 공백이면 제외한다.
  - 원문 viewer에서 열 수 있도록 `markdown_uri`가 있거나 `document_wiki_links` 연결이 있어야 한다.
- concept reference를 계속 노출할지, source reference만 “근거 자료”로 노출할지 UI 문구와 함께 결정한다.

**참고 위치**

- 저장 로직: `backend/src/main/java/fruition/query/service/QueryService.java` `buildReferences()`
- 채팅 조회: `backend/src/main/java/fruition/chat/controller/ChatController.java` `GET /api/chat/messages`
- 프론트 표시: `frontend/app/_components/agent-panel/AgentBody.tsx`
- Wiki page 상세 조회: `backend/src/main/java/fruition/wiki/service/WikiService.java` `findById()`
