# 2026-06-20 이슈

## 미결 이슈

### 1. 프론트엔드를 SSE 기반 진행상황 표시로 전환

**현황**

Spring 백엔드에 Query run/SSE 중계 구조(`POST /api/query/runs`, `GET /api/query/runs/{requestId}/events`, `POST /api/query/runs/{requestId}/events/callback`, `GET /api/query/runs/{requestId}`)를 구현했다.
같은 날 `dev`에 병합된 pipeline 커밋(`16118e1 feat: 쿼리 이벤트 콜백 계약 추가`)이 `request_id`/`log_callback_url`을 받아 요청별로 동적 callback publisher를 생성하도록 이미 구현해뒀다 — 즉 pipeline 쪽 선행 작업은 끝난 상태다.

프론트엔드는 현재 `POST /api/query`(동기)만 호출하고, `StatusList`/`agentData.ts`는 실제 event가 아니라 정적인 3단계(`질문 분석` → `관련 Wiki page 검색` → `근거 기반 답변 작성`)를 보여준다.
`POST /api/query`는 이번 작업에서 변경하지 않고 그대로 유지했으므로, 프론트엔드는 지금 당장 아무것도 바꾸지 않아도 기존처럼 동작한다. 전환은 blocking이 아니다.

**필요한 작업**

- `POST /api/query/runs` 호출 → 응답의 `request_id`로 `GET /api/query/runs/{requestId}/events` SSE 구독으로 전환
- `StatusList`/`agentData.ts`의 정적 3단계 표시를 실제 `stage`/`message` 기반으로 교체
- SSE 실패 시 `GET /api/query/runs/{requestId}` polling으로 fallback
- 최종 답변은 SSE `query.completed`가 아니라 기존처럼 `/api/chat/messages` 갱신 결과로 표시 (중복 방지)
- `retrieval_scored`의 `top_sources`/`top_concepts`를 후보 근거/검색 결과 UI에 연결할 수 있는지 검토
- `web_search_started` 계열 event는 내부 Wiki 경로가 아니라 웹 검색 fallback 경로임을 UI에서 구분

**참고 문서**

- 설계 전체: `docs/spec/backend-query-events-api.md` ("후속 작업 (이슈 문서로 이동) > frontend" 절, SSE 이벤트 포맷은 "API > GET /api/query/runs/{requestId}/events" 절)
- 프론트 진행 상태 표시: `frontend/app/_components/agent-panel/StatusList.tsx`, `frontend/app/_components/agent-panel/agentData.ts`
- 프론트 채팅 panel: `frontend/app/_components/agent-panel/AgentPanel.tsx`

**검증 기준**

- Query 실행 중 Agent 패널에 실제 backend/pipeline event message가 순서대로 표시된다
- 내부 Wiki 경로와 web search fallback 경로가 UI에서 구분된다
- 최종 답변과 진행 event가 중복 메시지로 표시되지 않는다
- SSE 연결이 실패해도 기존 최종 응답 조회 흐름은 깨지지 않는다

### 2. 인용 클릭 → 원본 문서 block 하이라이트 (풀스택)

**배경**

query 답변의 `[n]` 인용을 클릭하면 근거가 된 원본 문서를 열고 해당 block(문단)을 하이라이트하려 한다.
가정한 query evidence 응답 구조는 아래와 같다.

```json
{
  "rank": 1,
  "source_document_id": "doc_1f9a74af",
  "source_block_ids": ["B0005", "B0006"],
  "text": "원본 block citation이 붙어 있던 근거 문장"
}
```

- `rank`: query 답변에 붙는 `[1]`, `[2]` 같은 인용 번호와 매칭되는 근거 순번
- `source_document_id`: 클릭 시 열어야 하는 원본 문서 id
- `source_block_ids`: 원본 문서를 `\n\n` 빈 줄 기준으로 나눈 block id 목록. 예를 들어 `B0005`, `B0006`은 각각 5번, 6번 block이 근거라는 뜻

이 구조는 현재 코드에 존재하지 않으며, 세 계층 모두 수정이 필요하다.

**선결 난점 — 설계 결정 필요**

- query `EvidenceSnippet`은 wiki page 텍스트에서만 산출되어 원본 `document_id`/`block_id` 링크가 없다 (`build_query_context.py:102-138`). 현재 llmPipeline이 생성 단계에서 쓰는 `B0005` 형태 block id를 그대로 유지한다면, query evidence에는 `source_document_id`와 `source_block_ids`만 전달하면 된다.
- 원본이 PDF 등 바이너리면 추출 텍스트 기준 block(`block_id`)을 렌더된 PDF 위에 매핑하기 어렵다. **1차 범위는 markdown/text 원본으로 한정 권장.**

**현재 상태 (근거 파일)**

| 항목 | 현황 | 근거 파일 · 라인 |
|---|---|---|
| `B0005` 형태 block_id | 생성 단계 임시 생성, DB 미저장 · API 미노출 | `wiki_generation/infrastructure/extract.py:45` |
| `SourceBlock` 구조 | 현재 코드에는 `source_reference_id`, `line_start`, `line_end`, `section_path`, `block_type`도 있지만, 이번 하이라이트 요구에는 원본 block 전체를 찾기 위한 `document_id`, `block_id`, `text`만 필요 | `wiki_generation/domain/entities.py:18-28` |
| DB 스키마 | `documents/wiki_pages/links/runs/embeddings`만 존재, `source_blocks` 테이블 없음 | `wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py:29-127` |
| query `EvidenceSnippet` | `page_id/paragraph_index/sentence_index`만 있고 `document_id/block_id` 없음 | `query/application/build_query_context.py:102-138` |
| 원본 문서 조회 API | 파일 바이트 스트림만 반환, block 조회 API 없음 | `backend/.../document/controller/DocumentController.java` (`GET /api/documents/{id}/original`) |
| 프론트 인용 렌더링 | `[n]` 클릭 기능 없음, 문단 하이라이트 · 스크롤 없음 | `AgentBody.tsx`, `MarkdownViewer.tsx`, `SourcePreviewPanel.tsx` |

**필요한 작업**

*llmPipeline*

- `source_blocks` 테이블 신설: `(document_id, block_id, text)` — `app/modules/wiki_ingestion/infrastructure/postgres_wiki_ingestion_repository.py:init_db`
  - Primary key: `(document_id, block_id)`
  - `source_reference_id`, `section_path`, `block_type`, `line_start`, `line_end`는 이번 요구사항에는 포함하지 않음
- block 저장 배선: `wiki_generation/infrastructure/extract.py` 산출 블록을 ingestion persist 경로에 연결
- 원본 block 역추적 기준은 `source_document_id` + `source_block_ids`로 통일
- query 응답 evidence에 `rank`, `source_document_id`, `source_block_ids`, `text` 추가: `query/application/build_query_context.py`의 `EvidenceSnippet` 및 `query/interfaces/http/schemas.py:EvidenceSnippetResponse` 확장

*backend (Java)*

- block 조회 API 신설: `GET /api/documents/{documentId}/blocks` — `fruition.document` 내 Entity/Repository/DTO/Controller/Service 추가
  - 응답 block 필드는 `block_id`, `text`만 포함
- pipeline query 응답 중계 시 `rank` + `source_document_id` + `source_block_ids` + `text` 전달: `query/repository/PipelineQueryResponse.java`, `query/dto/QueryResponse.java`, 필요 시 `chat/dto/ChatMessageReference.java`

*frontend* (frontend/CLAUDE.md: 프론트만, API 계약 준수)

- `app/_components/MarkdownViewer.tsx`: `[n]` 인라인 인용을 클릭 가능 요소로 렌더
- `app/_components/agent-panel/AgentBody.tsx`: 인용 클릭 시 클릭한 `[n]`과 같은 `rank`의 `source_document_id` + `source_block_ids`를 패널로 전달하는 배선
- `app/_components/SourcePreviewPanel.tsx`: block 조회 API 호출 → `source_block_ids`에 해당하는 block 전체를 하이라이트
- `app/_lib/api.ts` / `app/_lib/types.ts`: block 조회 함수 · 타입 추가, evidence 타입에 `rank` / `source_document_id` / `source_block_ids` / `text` 필드 추가

**검증 기준**

- 답변의 `[n]` 클릭 시 올바른 원본 문서가 열린다
- 해당 `source_block_ids`의 block 전체가 하이라이트된다
- evidence가 가리키는 원본 block이 실제 근거 문단과 일치한다
- markdown/text 원본에서 동작한다 (PDF는 범위 외, 또는 추출 텍스트 뷰로 처리)

## 참고: 백엔드 작업 중 확인된 사항

이번 백엔드 작업 도중 `dev`를 pull하면서, pipeline의 `request_id`/`log_callback_url` 지원(원래 이슈로 남기려던 항목)이 이미 다른 커밋(`16118e1`)으로 구현되어 있는 것을 확인했다. 별도 미결 이슈로 등록하지 않고 여기 기록만 남긴다.

- pipeline이 보내는 callback payload에는 `request_id`, `event_type`, `stage`, `message`, `sequence`, `timestamp`, `data`가 포함된다 (`llmPipeline/app/modules/query/infrastructure/query_event_publisher.py`).
- 다만 Spring `QueryEventBroker`는 pipeline의 `sequence`/`timestamp`를 사용하지 않고 자체적으로 다시 부여한다 — `query.completed`/`query.failed`(pipeline이 보내지 않는 합성 event)까지 하나의 순번으로 묶기 위함. `PipelineEventCallbackRequest`(`backend/src/main/java/fruition/query/dto/PipelineEventCallbackRequest.java`)에 두 필드를 바인딩은 해두되 미사용 처리했다.
- 아직 end-to-end로 실제 서버를 띄워 pipeline → callback → SSE 흐름을 수동 검증하지는 못했다 (이 환경에 Docker가 없어 `BackendApplicationTests.contextLoads()`도 실패하는 상태). `docker-compose`로 backend+pipeline을 같이 띄울 수 있는 환경에서 `docs/spec/backend-query-events-api.md`의 "검증 기준" 절 기준으로 한 번 수동 확인이 필요하다.
- `CALLBACK_BASE_URL` 기본값을 처음에 `http://backend:8080`으로 잘못 넣었다가, `scripts/dev-up.sh`/`docs/local-runbook.md`를 보고 backend가 docker-compose 서비스가 아니라 호스트에서 `./gradlew bootRun`으로 직접 뜬다는 걸 확인하고 `http://host.docker.internal:8080`으로 고쳤다 (`infra/.env.example`, `application.properties`, `infra/compose.ai.yml`의 `extra_hosts` 추가). 실제 환경에서 한 번 더 확인이 필요하다.
