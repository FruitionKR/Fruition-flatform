## 배포 순서와 불일치 구간 (`scripts/aws_deploy.py`)

migration Job(access → document → ai) 뒤 교체 순서는 converter → access-svc → document-svc → pipeline-api → 나머지(frontend, AI worker) 동시다. PR215·PR232가 권장한 document → AI → 프론트와 맞는다.

- 새 document가 옛 AI에 `read_only_document_id`, `mode=chat`을 보낼 수 있는 구간이 있다. 옛 화면은 `mode=chat`을 보내지 않으므로 이 구간에 실제로 나가는 일은 드물 것으로 본다(코드로 판단한 추측, 재현하지 않음).
- frontend와 AI worker는 함께 교체되므로, 새 화면의 채팅 탭 요청을 옛 agent worker가 받는 짧은 구간이 있을 수 있다(추측).
- 옛 화면이 끝난 turn을 취소하면 새 409를 받을 수 있다.

## 첫 document 기동 때 일어나는 삭제 (읽기 조회, 2026-11-05 20:37~20:40 UTC)

`DocumentTrashPurgeWorker`는 새 Pod가 뜨는 즉시 돈다. 지운 내용은 복구되지 않는다.

- **`scrubOrphans` 대상은 모두 0건**이다: `ORPHAN_SOURCE_REF_CITATION` 인용, `ORPHAN_CITATION` 인용, 실행 command, projection(근거 포함), receipt, 변경 기록.
- **30일이 지난 휴지통 문서 3건(워크스페이스 1개)이 영구 삭제된다.** 이 문서를 가리키는 비울 인용 원문 0건, projection과 근거 0건, 실행 2건(진행 중 0건), 변경 기록 15건이다. 운영에서 이 경로의 첫 실제 실행이다.
- 건수는 조회 시점 값이다. 시간이 지나면 대상이 늘 수 있다.
- 이번에는 운영 AI가 이미 `document_purged`를 처리하는 버전이라, 지난 배포와 같은 유실 구간은 없다(코드로 확인, 운영에서 처리한 적은 아직 없음).

## 시험

PR CI와 병합된 main CI가 모두 통과했다. Document main CI: https://github.com/FruitionKR/Fruition-document/actions/runs/42105621561

DB 격리 시험: https://github.com/FruitionKR/Fruition-flatform/issues/158
- PostgreSQL 16.14, 외부 통신 없음, 합성 데이터, 운영과 같은 계정 구성
- Document는 운영·후보 bootJar의 `--migrate-only`(실제 Flyway), AI는 `migrate_ai_schema` 모듈로 적용했다.
- 적용 전후 논리 백업·복원, INVALID 인덱스 0, 옛·새 형태 쓰기 성공, `MIGRATION_AND_LOGICAL_RESTORE_OK`
- `ORPHAN_SOURCE_REF_CITATION`이 `idx_cmr_multi_source_quote`를 쓰는 것은 `enable_seqscan=off`에서 확인했다.

로컬 실서버 확인(`local/integration-20261106b`, `ui-e2e/it-final/PF/`)의 범위는 issue에 적었다. Document는 #216 전 `91458888`이고 frontend에는 묶음에 없는 랜딩 커밋이 더해져 있어 **묶음과 정확히 같은 코드가 아니다.** 운영 인프라와 롤아웃 구간은 검증하지 않는다.

운영 DB 읽기 점검: `source_refs`가 JSON이 아닌 행 0건(전체 117행).
