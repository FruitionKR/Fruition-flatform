# S3 인증 수정 릴리스 검증

대상 릴리스: `c27fd5a4a588231b366edd89b9e98574137d6bac`

기존 bootstrap 이미지의 Document 저장 요청은 AWS 환경 변수 자격 증명이 없는 경우 `AccessKey must not be null`로 실패했다. [Document 수정 PR #7](https://github.com/FruitionKR/Fruition-document/pull/7)은 MinIO Java SDK의 환경 변수 provider 실패를 IAM provider로 전달하도록 수정했다. AWS 저장소는 S3이며, 장기 Access Key/Secret Key를 추가하지 않는다.

## AWS S3 실증

2026-09-20에 위 Document digest로 임시 Kubernetes Job을 실행했다. 실제 Document ServiceAccount의 IRSA와 현재 S3 설정을 사용했다. 앱 Secret과 DB 자격 증명은 주입하지 않았으며, SDK 구성은 이미지에 포함된 `MinioConfig`를 호출했다.

- IAM 역할로 임시 자격 증명을 얻어 고유한 시험 객체를 생성했다.
- 객체를 다시 읽어 원래 바이트와 일치함을 확인했다.
- 생성한 객체를 삭제했다.
- Job 성공과 `STORAGE_PUT_GET_PASS`, `STORAGE_DELETE_PASS` 로그를 확인했다.
- 임시 Job·ConfigMap·NetworkPolicy를 삭제했다. 서비스 Deployment와 bootstrap 이력은 변경하지 않았다.

기존 운영 Pod의 STS 교환 성공만 확인한 시험과 달리, 이번에는 **새 이미지의 실제 Java SDK가 S3 요청에 성공**한 것을 확인했다.

## DB 변경과 호환성

기존 릴리스 `a2b46a13a49f5850a6a9febb367546d97e47da73` 대비 Access 소스는 동일하다. Document에 추가되는 DB 변경은 V49의 `chat_messages.progress jsonb NOT NULL DEFAULT '[]'::jsonb` 컬럼이다. AI의 DB 마이그레이션 코드는 변경되지 않았다. HTTP 요청·응답 schema 변경과 DB schema 변경은 구분했다.

검증은 운영 데이터가 없는 별도 Docker 네트워크의 PostgreSQL 16.14와 시험용 DB 계정, Redis, MinIO를 사용한다. DB 3개를 기존 게시 이미지로 생성한 뒤 데이터를 넣고 업그레이드한다. 로컬 MinIO는 DB/API 호환성 시험용이고, AWS S3/IRSA는 위 별도 시험에서 확인했다.

| 확인 항목 | 결과 |
| --- | --- |
| 기존 이미지의 세 DB 실제 마이그레이션 | 통과 |
| V49 전 기존 Access 로그인·Document 생성/조회·채팅 조회 | 통과 |
| 기존 채팅 1만 건의 V49 기본값과 데이터 보존, relfilenode 유지 | 통과 |
| 실제 새 Document 이미지 V49 적용 / 재실행 | 7.99초 / 8.24초, 재실행 후 schema 동일 |
| V49 후 기존 Document·AI API 조합과 로그인·문서·채팅 조회 | 통과 |
| 새 Document·AI API 조합과 로그인·문서·채팅 조회, 기존 문서 조회 | 통과 |
| runtime 계정의 기존 컬럼 INSERT에 progress 기본값 적용 | 통과 |
| 구 AI → 신 AI → 구 AI의 개인 Skill 생성·읽기·상태 변경과 신 AI 삭제 | 통과 |

AI Skill 시험은 실제 이미지의 repository와 runtime DB 계정을 사용했다. 외부 LLM을 호출한 ingest 성공으로 표시하지 않는다.

별도 PostgreSQL 인스턴스에 역할과 각 DB의 `pg_dump -Fc` 백업을 `pg_restore --create --exit-on-error`로 복원했다. public의 모든 테이블을 대상으로 정렬한 행 JSON의 digest를 비교했으며, API/Skill 시험 데이터도 포함했다. schema의 PostgreSQL cast 직렬화 표현만 정규화해 비교했다.

| DB | 비교한 테이블 | 백업 크기 | 복원·비교 소요 | 결과 |
| --- | --- | --- | --- | --- |
| access | 16 | 46983 bytes | 1.46초 | schema·전체 행 일치 |
| core | 51 | 217296 bytes | 4.34초 | schema·전체 행 일치 |
| ai | 26 | 74198 bytes | 2.21초 | schema·전체 행 일치 |

원본·복원 DB 모두 runtime/migration 역할 분리 검사를 통과했다. 시험 컨테이너·네트워크와 SSM 터널은 정리했다.

Access는 소스가 동일한 기존 게시 이미지를 사용한다. Document·AI는 기존 digest와 새 릴리스 digest를 직접 실행하며, 운영 프로필의 Document Flyway 자동 실행을 끄고 전용 migration 진입점으로 V49를 적용한다.

AWS의 세 DB schema fingerprint가 기존 bootstrap 준비 완료 기록과 모두 일치함도 배포 전 확인했다. 이 검사는 schema/권한 조회용 preflight Job으로 수행했으며 DB 마이그레이션을 실행하지 않았다.

## 검증 범위와 배포 조건

외부 LLM을 사용하는 Kafka ingest 전체 흐름, 운영 규모의 잠금·부하, RDS snapshot/PITR 복원은 이 격리 시험에 포함하지 않는다. PostgreSQL minor 버전도 운영 16.13과 시험 16.14가 다르다. S3의 장시간 토큰 갱신과 동시 요청 부하는 별도 시험 대상이다.

새 릴리스에는 V49가 있으므로 `migration_mode=expand-only`로 검토한다. 기존 SHA의 `initial-install` 검토를 재사용하거나 bootstrap 기록을 삭제하지 않는다. `bootstrap` 재실행이나 OAuth/health 복구 옵션을 새 SHA와 함께 사용하지 않는다.

검토 기록의 main 반영과 `feedback` 승인을 거친 뒤 `action=deploy`로 실행한다. 배포 workflow의 로그인 → 문서 생성·조회 → AI ingest 완료 → 시험 문서 정리가 통과해야 첫 성공 release가 기록된다. 아직 성공 release가 없어 기존 성공 SHA를 이용한 자동 코드 rollback은 사용할 수 없다. 실패 시 DB를 자동으로 되돌리지 않으며, 실패 단계에 맞는 호환 수정 릴리스를 검토한다.
