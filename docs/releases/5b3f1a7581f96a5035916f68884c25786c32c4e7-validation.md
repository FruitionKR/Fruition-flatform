- AI: `39928a4e3f5ec9470fa8b2bb72450d8d666da59a` ([PR #26](https://github.com/FruitionKR/Fruition-ai/pull/26), [PR #27](https://github.com/FruitionKR/Fruition-ai/pull/27), [PR #28](https://github.com/FruitionKR/Fruition-ai/pull/28))

이전 릴리스 `0105e848`은 같은 Access·Document 소스에 AI만 `02a2a227`이었고 배포하지 않았다. 그 검토 내용은 [0105e848 검토](0105e848a0a5f1a38c77990582a4ab122b67537b-validation.md)에 있으며 이 릴리스에 모두 포함된다. 운영 마지막 배포는 `8f7d60b8`(Access `b73cf750`, Document `0b32a3d`, AI `be6cbeb`)이다.

## 포함 변경

0105e848의 변경 전부에 더해:

- AI #28: worker 사망으로 중단된 작업을 재전달할 때 `pending`으로 되돌린 뒤 자동 재실행한다. `ai_task_runs.attempt`로 재시도 횟수를 센다.
- Platform #36: AI 워커·converter의 종료 유예를 900초로 늘려 진행 중 작업을 마치게 한다.
- Platform #30: 질의·에이전트·유지보수 작업자에서 `QUERY_EMBEDDING_MODE=bge-m3`로 의미 검색을 켠다. 세 작업자만 메모리 요청 2.5Gi·한도 3.5Gi, CPU 요청 500m을 쓴다. 나머지 AI Pod는 `text-only`를 유지한다.

Platform 변경은 manifest만 바꾸므로 릴리스 ID에 영향을 주지 않는다. 배포 시점 main의 manifest가 적용된다.

## DB 변경과 호환성 (`expand-only`)

운영 마지막 배포(`8f7d60b8`)는 Document V53, AI 스키마 `be6cbeb` 시점이다.

- Document V54·V55·V56: `meetings`·`meeting_streams`·`meeting_segments`·`meeting_notes` 신규 테이블과, 같은 릴리스가 만든 빈 `meetings`에 컬럼·부분 인덱스 추가. 기존 테이블 변경 없음. 상세는 0105e848 검토와 동일하다.
- AI: `ai_task_runs`에 `attempt integer NOT NULL DEFAULT 0` 추가. `ADD COLUMN IF NOT EXISTS`이며 PostgreSQL 11 이상에서 기본값 추가는 테이블 재작성 없이 메타데이터만 바꾼다. 긴 잠금을 만들지 않는다.
- 컬럼 삭제·이름 변경·즉시 NOT NULL 강제 같은 파괴적 변경은 없다.

**배포 전 필수:** 없음. 데이터 충돌 조건이 없다. 배포 전 백업 시점 확보는 통상 절차대로 한다.

**되돌림:** 이미지 롤백 시 V54~V56 테이블과 `attempt` 컬럼은 남지만 이전 앱은 참조하지 않는다. 롤백 후보 `8f7d60b8`의 네 이미지는 ECR에 모두 보존되어 있다.

## 이번 릴리스에 포함하지 않은 것

- **Access dev의 V20**: `workspace_name_reservations` 테이블과 트리거 2개·함수 3개를 DROP한다. 파생 데이터라 데이터 손실은 없으나 schema fingerprint가 바뀌어 코드 rollback 전제가 깨지므로 `expand-only`가 아니다. 또 같은 변경이 `WorkspaceCreateRequest.name`의 `@NotBlank`를 제거해, 배포 후 클라이언트가 name 없이 요청하기 시작하면 이미지 롤백 시 이전 코드에서 NPE가 난다. 별도 점검 릴리스로 분리한다.
- AWS 경로의 WebSocket 실환경 확인과 실제 IRSA로 녹음 원본 S3 업로드. 0105e848 검토에서 이월된 항목이다.

## 배포 후 확인

0105e848 검토의 확인 항목에 더해:

- `ai_task_runs`에 `attempt` 컬럼이 생기고, 중단된 작업이 재전달될 때 증가하며 자동 재실행되는지.
- 질의·에이전트·유지보수 작업자 Pod가 2.5Gi 요청으로 AI 노드에 배치되는지, OOMKilled가 없는지. AI 노드는 m5/m6i.xlarge(16GiB) 최대 2대이며 세 작업자 각 1개는 1대에 들어간다. KEDA가 질의·에이전트 작업자를 늘리면 노드 상한에 닿아 Pending이 생길 수 있다.
- `pipeline` Pod 로그에 Hugging Face 다운로드 시도가 없는지(이미지 내장 오프라인 로드 확인).
- 기존 위키 페이지 임베딩 백필 실행. `docs/aws-maintenance.md`의 "의미 검색(BGE-M3) 켜기와 기존 위키 임베딩" 절차를 따른다. 백필 전까지 기존 페이지는 의미 검색 대상이 아니다.
- AI 워커·converter의 `terminationGracePeriodSeconds`가 900인지.
