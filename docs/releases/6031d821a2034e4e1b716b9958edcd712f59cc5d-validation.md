## DB 변경과 복원 시험

이전 성공 소스와 비교해 Document V119만 추가됐다. Access 및 AI schema 변경은 없다. V119는 `ALTER TABLE ai_task_runs ADD COLUMN cost_quote JSONB;`로 nullable 컬럼을 추가하며 기존 컬럼·데이터를 삭제하지 않는다. `migration_mode=expand-only`로 배포한다.

2026-11-14 네트워크 없는 일회용 PostgreSQL 16-alpine 컨테이너와 tmpfs, 합성 데이터로 다음을 실행했다.

1. 정확한 Document 소스의 V1–V118 SQL을 순서대로 적용했다. `.sql.conf`가 있는 비트랜잭션 마이그레이션을 구분했다.
2. 기존 형태의 ai_task_runs 합성 행을 만들고 pg_dump -Fc → 별도 DB pg_restore --exit-on-error 후 행 전체 JSON이 같은지 검증했다.
3. 복원된 V118 DB에 V119 적용 성공을 확인했다.
4. 원본 시험 DB에 V119를 적용하고 기존 행의 cost_quote가 NULL임을 확인했다. 기존 형태 INSERT 및 새 JSONB UPDATE가 모두 성공했다.
5. V119 적용 후 다시 dump/restore하여 합성 행 전체 JSON 일치와 INVALID 인덱스 0개를 확인했다.

모두 통과. V119 SQL SHA256: `cb8400904e62a4a364c99d1407d3ca0d814a8d9d9e1ec18cbe132455c702cc5e`.

시험 한계: 게시 이미지의 Flyway 실행 대신 정확한 소스 SQL을 사용했다. 운영 데이터·운영 규모의 잠금 시간·RDS PITR·구/신 앱 동시 실행을 검증하지 않았다. 최초 시험은 SQL별 트랜잭션을 생략해 V34 임시 테이블 오류가 발생했으며, 새 DB에 트랜잭션 설정을 반영한 전체 시험은 통과했다.

## 배포와 복구

배포 workflow에서 DB 권한·fingerprint, 실제 migration Job, 순차 rollout, 인증 업무 smoke와 대용량 PDF smoke를 확인한다. Document가 새 pipeline 비용 분석 API를 호출하므로 서비스 교체 사이 요청이 일시 실패할 수 있다. V119 적용 후 이전 성공 릴리스와 DB fingerprint가 달라지므로 기존 rollback을 무조건 실행할 수 없다. 실패 시 현재 스키마를 유지하고 배포기의 복구 절차에 따라 처리한다.
